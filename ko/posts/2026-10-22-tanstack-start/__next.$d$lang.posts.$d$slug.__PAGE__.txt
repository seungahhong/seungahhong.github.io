23:T317a0,<h2 id="tanstack-start-10-정식-출시-개요--사용법--마이그레이션-가이드">TanStack Start 1.0 정식 출시: 개요 · 사용법 · 마이그레이션 가이드<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#tanstack-start-10-정식-출시-개요--사용법--마이그레이션-가이드"><span class="icon icon-link"></span></a></h2>
<h3 id="️-한-줄-요약">✍️ 한 줄 요약<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#️-한-줄-요약"><span class="icon icon-link"></span></a></h3>
<blockquote>
<p><strong>TanStack Start는 TanStack Router 위에 SSR · 스트리밍 · 서버 함수 · 미들웨어를 얹은 풀스택 React 프레임워크이고, 2026년 10월 13일 1.0(npm <code>1.169</code>)으로 정식 안정화됐습니다.</strong> 기본값은 "서버에서 그리고 브라우저에서 하이드레이션하는 익숙한 앱"이고 서버가 필요한 일만 <code>createServerFn</code> 같은 명시적인 API로 넘긴다는 점이, 서버 컴포넌트가 기본인 Next.js App Router와 가장 크게 갈리는 지점입니다.</p>
</blockquote>
<h4 id="요약">요약<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#요약"><span class="icon icon-link"></span></a></h4>
<ul>
<li><strong>출시</strong>: 2026년 10월 13일 TanStack 블로그 공지("TanStack Start 1.0 is Stable"). 첫 안정 패키지는 <code>@tanstack/react-start@1.169.0</code>이고, 글을 쓰는 시점(2026-10-22)의 최신은 <code>1.169.3</code>입니다. '1.0'은 제품 버전 이름이라 <code>@tanstack/react-start@1.0</code>이 아니라 <code>1.169</code> 이상을 설치합니다(RC 기간에도 이미 1.1xx였기 때문에 숫자만으로는 RC와 정식을 구분할 수 없습니다).</li>
<li><strong>정체성</strong>: 라우팅은 <strong>전부 TanStack Router</strong>가 맡고, Start는 그 위에 풀 도큐먼트 SSR · 스트리밍 · 서버 함수(타입 안전 RPC) · 서버 라우트(API) · 미들웨어/컨텍스트 · 클라이언트/서버 빌드 · 유니버설 배포를 더합니다. 공식 홈페이지 기준으로 React와 Solid를 지원합니다.</li>
<li><strong>빌드 도구</strong>: <strong>Vite 8 이상</strong> 또는 <strong>Rsbuild 2</strong>. Node는 22.12 이상입니다.</li>
<li><strong>실행 모델</strong>: 모든 코드는 기본이 <strong>isomorphic</strong>(서버·클라이언트 양쪽에서 실행)입니다. 라우트 <code>loader</code>도 첫 요청에선 서버에서, 이후 내비게이션에선 브라우저에서 돕니다. 비밀값과 DB 접근은 서버 함수나 <code>.server.ts</code> 파일로 경계를 그어야 합니다.</li>
<li><strong>렌더링 선택지</strong>: 라우트별 <code>ssr: true | 'data-only' | false</code>(Selective SSR), 앱 전체 SPA 모드, 정적 프리렌더링, HTTP 캐시 헤더 기반 ISR을 한 프레임워크 안에서 고릅니다.</li>
<li><strong>RSC</strong>: <strong>실험적 · opt-in</strong> 입니다. Next.js처럼 기본 컴포넌트 모델이 아니라, 서버 함수가 서버에서 렌더링한 UI를 돌려주고 클라이언트가 그것을 조합하는 방식입니다. Next.js식 <code>'use server'</code> 액션은 <strong>의도적으로 지원하지 않고</strong> 명시적인 서버 함수만 씁니다.</li>
<li><strong>마이그레이션</strong>: RC → 1.0은 Vite 8 필수, <code>.inputValidator()</code> → <code>.validator()</code>, <code>useSession</code> 제거, Nitro 플러그인 교체, 에러·응답 동작 변경이 핵심입니다. Next.js App Router → Start는 공식 가이드와 before/after 예제가 있고, Remix 2 / React Router 7 가이드는 아직 "coming soon"입니다.</li>
<li><strong>보안 이력</strong>: 2026년 9월 30일 공개된 <strong>CVE-2026-102989</strong>(서버 함수 응답 처리의 반사형 XSS, CVSS 9.3). 실제로 설치된 <code>@tanstack/start-server-core</code>가 <strong>1.169.39 이상</strong>인지 확인하고 재배포해야 합니다. 5월 11일에는 42개 <code>@tanstack/*</code> 패키지에 악성 버전이 올라간 npm 공급망 공격(CVE-2026-45321)도 있었습니다.</li>
</ul>

<h3 id="개요-tanstack-start는-무엇인가">개요: TanStack Start는 무엇인가<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#개요-tanstack-start는-무엇인가"><span class="icon icon-link"></span></a></h3>
<p>TanStack Start는 <strong>TanStack Router로 움직이는 풀스택 React 프레임워크</strong> 입니다. 풀 도큐먼트 SSR, 스트리밍, 서버 함수, 클라이언트/서버 빌드를 제공하고, Vite와 Rsbuild를 지원하기 때문에 원하는 호스팅이나 런타임에 그대로 배포할 수 있습니다.</p>
<p>구성 요소는 두 개뿐입니다.</p>
<ul>
<li><strong>TanStack Router</strong> — 중첩 라우팅, search params, 데이터 로딩을 타입 안전하게 다루는 라우터</li>
<li><strong>Vite 또는 Rsbuild</strong> — HMR과 프로덕션 빌드를 담당하는 빌드 도구</li>
</ul>
<h4 id="router만-쓸까-start를-쓸까">Router만 쓸까, Start를 쓸까<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#router만-쓸까-start를-쓸까"><span class="icon icon-link"></span></a></h4>
<p>공식 문서는 "프레임워크의 90%는 라우터"라고 말합니다. Start는 라우팅을 <strong>전적으로</strong> TanStack Router에 맡기고, 그 위에 서버 쪽 기능을 얹습니다. 그래서 질문은 "서버 기능이 필요한가"로 바뀝니다.</p>



































<table><thead><tr><th>필요한 것</th><th align="center">Router만</th><th align="center">Start</th></tr></thead><tbody><tr><td>타입 안전 라우팅 · search params · loader</td><td align="center">✅</td><td align="center">✅</td></tr><tr><td>풀 도큐먼트 SSR · 스트리밍</td><td align="center">△</td><td align="center">✅</td></tr><tr><td>서버 함수(타입 안전 RPC) · 서버 라우트(API)</td><td align="center">—</td><td align="center">✅</td></tr><tr><td>요청/서버 함수 미들웨어 · 컨텍스트</td><td align="center">—</td><td align="center">✅</td></tr><tr><td>클라이언트+서버 풀스택 빌드 · 유니버설 배포</td><td align="center">—</td><td align="center">✅</td></tr></tbody></table>
<p>△는 TanStack Router에도 실험적인 SSR · 스트리밍 API가 있지만 직접 조립해야 한다는 뜻입니다. Start는 이를 기본 제공 형태로 묶어 줍니다. 위 기능이 <strong>하나도 필요 없다고 확신할 때만</strong> Router 단독(SPA)을 권한다는 게 공식 입장입니다.</p>
<h4 id="어떤-철학으로-만들었나">어떤 철학으로 만들었나<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#어떤-철학으로-만들었나"><span class="icon icon-link"></span></a></h4>
<p>1.0 공지에서 Tanner Linsley가 밝힌 출발점은 분명합니다. React 생태계가 "애플리케이션은 이래야 한다"는 상을 한 가지로 좁히고 있다고 느꼈고 — Next.js는 RSC에 크게 베팅하며 서버 중심 모델로, React Router와 Remix는 각자의 변화로 — 자신은 <strong>지난 10년간 만들어 온 방식</strong>(상태 관리, 클라이언트 내비게이션, 데이터 캐싱)을 그대로 유지하면서 서버 렌더링 · 스트리밍 · 서버 함수 같은 새 기능을 <strong>필요한 곳에만</strong> 쓰고 싶었다는 것입니다.</p>
<p>그래서 Start의 기본값은 이렇습니다.</p>
<ul>
<li>컴포넌트는 그냥 컴포넌트, 라우트는 그냥 라우트입니다. <code>'use client'</code> 경계를 그릴 필요가 없습니다.</li>
<li>라우트는 서버에서 렌더링할 수도, 데이터만 서버에서 불러오고 컴포넌트는 클라이언트에서 그릴 수도, 전부 클라이언트에서 처리할 수도 있습니다.</li>
<li>서버가 필요하면 <strong>명시적인 API</strong>(<code>createServerFn</code>, 미들웨어)로 넘어갑니다.</li>
<li>RSC도 앱 모델을 바꾸지 않는 <strong>선택 기능</strong>으로 붙습니다.</li>
</ul>

<p>RSC에 대한 솔직한 회고도 있습니다. 팀은 RSC를 Start의 앱 모델을 바꾸지 않는 방식으로 통합하는 데 많은 시간을 들였지만, 정작 tanstack.com에서는 "무엇이 어디로 배포되는지" 추적하기가 너무 복잡해져 <strong>RSC를 다시 걷어냈다</strong>고 합니다. 그리고 그걸 걷어내는 데 앱을 다시 짤 필요가 없었다는 점을 opt-in 설계의 근거로 듭니다.</p>

<p>서버 함수는 정적 import 하면 어디서든 안전하지만 <strong>동적 <code>import()</code>는 번들러 문제를 일으킬 수 있으니 피하라</strong>고 합니다.</p>
<p>알아 둘 기본값도 있습니다.</p>
<ul>
<li><strong>CSRF 보호</strong> — 서버 함수는 같은 출처(same-origin) RPC입니다. <code>src/start.ts</code>가 없으면 Start가 <code>createCsrfMiddleware()</code>를 자동으로 설치하지만, <strong><code>src/start.ts</code>를 직접 만들면 이 미들웨어를 명시적으로 추가해야 합니다.</strong> 이 미들웨어는 <code>Sec-Fetch-Site</code> · <code>Origin</code> · <code>Referer</code> 헤더로 출처를 확인하고 세 헤더가 모두 없는 요청은 기본으로 거부하므로, 이런 헤더를 지우는 프록시 뒤에 배포한다면 미리 확인해 두세요.</li>
<li><strong>직렬화 타입 검사</strong> — 입력과 반환값이 직렬화 가능한지 TypeScript가 검사합니다(<code>strict</code> 기본). <code>FormData</code>(POST)와 <code>Response</code>는 허용됩니다.</li>
<li><strong>캐시 헤더</strong> — <code>setResponseHeaders</code>로 <code>Cache-Control</code>을 지정할 수 있는데, 세션이나 쿠키에 따라 달라지는 응답에 <code>public</code>을 쓰면 <strong>다른 사용자에게 응답이 재생될 수 있으니</strong> <code>private</code>(+ <code>Vary</code>) 또는 <code>no-store</code>를 써야 합니다.</li>
</ul>

<p>모든 요청이나 모든 서버 함수에 적용할 전역 미들웨어는 <code>src/start.ts</code>의 <code>createStart</code>에 <code>requestMiddleware</code> / <code>functionMiddleware</code> 배열로 등록합니다. 클라이언트 → 서버로 컨텍스트를 보내는 <code>sendContext</code>는 타입은 맞춰 주지만 <strong>런타임 검증은 하지 않으므로</strong>, 서버 미들웨어에서 다시 검증해야 합니다. 세션처럼 신뢰가 필요한 값은 절대 <code>sendContext</code>에서 꺼내면 안 됩니다.</p>

<p>Start의 가장 실용적인 장점은 렌더링 방식을 <strong>라우트 단위로</strong> 고를 수 있다는 점입니다.</p>

<p><strong>상속 규칙</strong>이 중요합니다. 자식 라우트는 부모 설정을 물려받고, <strong>더 엄격한 쪽으로만</strong> 바꿀 수 있습니다(<code>true</code> → <code>'data-only'</code> → <code>false</code>). 부모가 <code>ssr: false</code>면 자식에 <code>ssr: true</code>를 써도 효과가 없습니다. 기본값 자체를 바꾸려면 <code>src/start.ts</code>의 <code>createStart(() => ({ defaultSsr: false }))</code>를 씁니다. 그리고 이 설정은 <strong>첫 요청</strong>에만 해당합니다. 이후 클라이언트 내비게이션에서는 모드와 상관없이 <code>beforeLoad</code>와 <code>loader</code>가 브라우저에서 실행됩니다.</p>
<h4 id="spa-모드">SPA 모드<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#spa-모드"><span class="icon icon-link"></span></a></h4>
<p>SSR이 없다고 서버 기능을 포기하는 건 아닙니다. 빌드 후 루트 라우트를 프리렌더해 <code>/_shell.html</code>을 만들고(매칭된 라우트 자리에는 pending 컴포넌트가 들어갑니다), 서버 함수와 서버 라우트는 그대로 쓸 수 있습니다. 다른 라우트도 함께 프리렌더할 수 있고, 공식 문서는 가능한 한 많이 프리렌더하라고 권합니다. 대신 호스팅 쪽에 리라이트 규칙이 필요합니다(Netlify <code>_redirects</code> 예).</p>

<p>알아 둘 제약도 있습니다. RSC는 React의 Flight 프로토콜을 그대로 쓰기 때문에 서버 컴포넌트 안에서는 Start 고유의 직렬화를 아직 쓸 수 없고(원시값 · Date · React 요소는 가능), TanStack Query로 서버 컴포넌트를 캐시할 때는 <code>structuralSharing: false</code>가 필수입니다.</p>
<p>RSC를 공개한 글("React Server Components Your Way", 2026-04-13)은 <strong><code>'use server'</code> 액션을 의도적으로 지원하지 않는다</strong>고 밝힙니다. 이미 알려진 공격 벡터가 있고, 네트워크 경계를 암묵적으로 만든다는 이유입니다. 같은 글은 Start가 클라이언트에서 온 Flight 데이터를 파싱하지 않기 때문에 다른 RSC 프레임워크를 덮친 최근 CVE가 해당하지 않는다고 설명하는데, 독립 감사가 아니라 TanStack의 자체 평가라는 점은 감안해야 합니다.</p>
<p>공식 비교 문서는 이 기능을 <strong>"Next.js와 동등한 프로덕션 기능처럼 소개하면 안 된다"</strong> 고 직접 선을 긋고 있습니다. RSC가 앱의 중심이라면 이 점을 먼저 고려해야 합니다.</p>

<p><code>.validator()</code>에는 사연이 있습니다. 원래 이름이 <code>.validator()</code>였는데 RC(1.132)에서 <code>.inputValidator()</code>로 바뀌었고, 2026년 6월(1.168.25, PR #7566)에 다시 <code>.validator()</code>가 정식 이름이 되면서 <code>.inputValidator()</code>는 deprecated 경고와 함께 남아 있다가 1.169.0에서 제거됐습니다. 그래서 <strong>RC 시절의 튜토리얼 코드는 1.0에서 그대로 깨집니다.</strong> 반대로 이 이력 덕분에 업그레이드를 쪼갤 수 있습니다.</p>
<ol>
<li>1.168.25 이상(Vite 7을 지원하는 마지막 버전은 1.168.61)에서 <code>.inputValidator()</code>를 <code>.validator()</code>로 먼저 바꾼다</li>
<li>같은 버전에서 <code>useSession</code>을 세션 라이브러리로 교체하고, <code>set-cookie</code>를 <code>setCookie</code>/<code>appendResponseHeader</code>로 바꾸는 등 두 버전에서 모두 동작하는 변경을 먼저 반영한다</li>
<li>Vite 8과 1.169.x로 올린 뒤 Nitro 플러그인을 교체하고, 아래 동작 변경 표를 점검한다</li>
</ol>

<p>RC 이전의 베타를 쓰고 있었다면 두 번의 큰 전환을 먼저 거쳐야 합니다. 공식 추적 토론(GitHub Discussion #2863)에 정리된 내용을 요약하면 이렇습니다.</p>

<p>그 밖에 <code>registerGlobalMiddleware</code>가 제거됐고(지금은 <code>src/start.ts</code>의 <code>createStart</code>), Nitro가 기본 결합에서 분리됐으며(RC에서는 <code>nitroV2Plugin</code>, 1.0에서는 <code>nitro/vite</code>), React 플러그인(<code>viteReact()</code>)도 직접 추가하게 됐습니다. 당장 올릴 수 없다면 <code>npx create-start-app@latest pin-versions</code>로 버전을 고정해 두라는 안내도 있습니다.</p>

<h3 id="마이그레이션--nextjs-app-router--start">마이그레이션 ② Next.js App Router → Start<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#마이그레이션--nextjs-app-router--start"><span class="icon icon-link"></span></a></h3>
<p>Next.js에서 옮겨 오는 경우를 위해 공식 가이드는 <strong>같은 기사 사이트를 두 프레임워크로 구현한 before/after 예제</strong>(<code>examples/react/start-next-migration</code>)와, 두 앱에 똑같이 돌리는 Playwright 테스트를 제공합니다. 공개 URL, 서버 렌더링된 메타데이터, 쿼리 필터링, 리다이렉트, 404, sitemap, 로그인 오류, 세션 유지, 비공개 응답 캐싱, 뮤테이션, 로그아웃 후 서버 거부까지 확인합니다. "동작을 계약으로 고정하고 프레임워크 경계만 번역한다"는 접근이 이 가이드의 핵심입니다.</p>
<p>먼저 알아 둘 전제가 하나 있습니다. <strong>Start에는 <code>'use server'</code>가 없습니다.</strong> Server Actions는 전부 <code>createServerFn</code>으로 다시 써야 하고, <code>'use client'</code> 지시어도 필요 없으니 지웁니다. <code>@tanstack/react-start</code> 패키지 안에는 Next.js 이전용 에이전트 스킬(<code>skills/lifecycle/migrate-from-nextjs/SKILL.md</code>)도 들어 있어 에이전트에게 작업을 맡길 때 참고 자료가 됩니다. 다만 이 스킬은 초반에 Next.js를 제거하는 순서로 적혀 있으니, 아래 공식 가이드처럼 두 앱을 나란히 돌리는 쪽이 더 안전합니다.</p>
<h4 id="0단계-바꾸기-전에-목록부터">0단계: 바꾸기 전에 목록부터<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#0단계-바꾸기-전에-목록부터"><span class="icon icon-link"></span></a></h4>
<ul>
<li><strong>관찰 가능한 동작</strong> — 동적 경로, 쿼리 파라미터, 리다이렉트, trailing slash, 로케일 접두사, 응답 상태, title/description/canonical/robots, sitemap 포함 여부</li>
<li><strong>Next.js 전용 코드</strong> — <code>next/*</code> import, <code>'use server'</code>, 서버 전용 모듈, metadata export, <code>generateStaticParams</code>, <code>revalidatePath</code>/<code>revalidateTag</code>, 캐시 지시어, Proxy/middleware, 이미지·폰트 설정</li>
</ul>
<p>렌더링이 성공해도 인증, 캐시 무효화, 중요한 검색 URL을 잃어버렸을 수 있다는 게 가이드의 경고입니다.</p>
<h4 id="1단계-기존-앱-옆에-start를-세운다">1단계: 기존 앱 옆에 Start를 세운다<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#1단계-기존-앱-옆에-start를-세운다"><span class="icon icon-link"></span></a></h4>
<p>Next.js 앱은 이전한 라우트가 검증을 통과할 때까지 <strong>계속 실행 가능한 상태로</strong> 둡니다. Next.js와 설정을 지우지 않아도 Start를 테스트할 수 있습니다.</p>
<h4 id="2단계-경로는-지키고-파일만-옮긴다">2단계: 경로는 지키고 파일만 옮긴다<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#2단계-경로는-지키고-파일만-옮긴다"><span class="icon icon-link"></span></a></h4>

<p><code>src/routes</code>는 URL 접두사가 아니라 소스 디렉터리입니다. 중첩 레이아웃, 라우트 그룹, 선택적 파라미터, 병렬·인터셉팅 라우트는 파일 이름만 기계적으로 바꾸지 말고 개별로 매핑해야 합니다(공식 예제도 병렬·인터셉팅 라우트는 재현하지 않습니다).</p>
<h4 id="3단계-api-대응표">3단계: API 대응표<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#3단계-api-대응표"><span class="icon icon-link"></span></a></h4>

<p>여기서 놓치기 쉬운 차이가 하나 있습니다. Next.js의 Server Action 폼은 <strong>JavaScript 없이도</strong> 동작하지만, 이벤트 핸들러로 서버 함수를 부르는 폼은 JS가 필요하고 하이드레이션 전에는 동작하지 않습니다. 점진적 향상이 요구사항이라면 FormData를 받는 서버 함수의 <code>.url</code>이나, 서버 라우트로 보내는 일반 폼 POST(검증 · CSRF 포함)를 써야 합니다. 가이드도 <code>createServerFn</code>을 React 폼 Action 프로토콜의 drop-in 대체로 보지 말라고 합니다.</p>
<h4 id="4단계-인증--메타데이터--캐시">4단계: 인증 · 메타데이터 · 캐시<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#4단계-인증--메타데이터--캐시"><span class="icon icon-link"></span></a></h4>
<ul>
<li><strong>인증</strong> — Start는 세션 API를 제공하지 않습니다. 공식 예제는 <code>iron-session</code>을 유지하고 Next.js <code>cookies()</code>를 <code>getCookie</code>/<code>setCookie</code> 어댑터로 바꿨습니다. 컷오버나 롤백 중에도 세션이 살아 있어야 한다면 쿠키 이름 · 도메인 · 경로 · 서명/암호화 형식 · 만료 · 키 교체 · 로그아웃을 양쪽 배포에서 모두 검증해야 합니다.</li>
<li><strong>비공개 페이지 캐시</strong> — 개인화된 HTML이 다른 사용자에게 가지 않도록 <code>Cache-Control: private, no-store</code>를 확인하고, CDN을 거친 최종 응답으로 검증합니다. 비공개 데이터가 있는 페이지는 프리렌더하거나 공개 캐시하지 않습니다.</li>
<li><strong>메타데이터</strong> — JS 실행 전 HTML 응답과 클라이언트 내비게이션 후의 head를 모두 비교합니다. sitemap, robots.txt, 아이콘, manifest, 소셜 이미지는 명시적으로 옮기고, 없는 콘텐츠에는 진짜 404를 돌려줍니다.</li>
<li><strong>캐시</strong> — 브라우저 데이터, Router loader, Query, 서버 데이터, 생성된 페이지, CDN 응답을 <strong>각각</strong> 나열하고 무엇이 채우고 무엇이 무효화하는지 정의합니다. Next.js의 캐시 지시어와 재검증은 자동으로 옮겨지지 않습니다.</li>
</ul>
<h4 id="5단계-롤백-경로를-쥐고-전환한다">5단계: 롤백 경로를 쥐고 전환한다<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#5단계-롤백-경로를-쥐고-전환한다"><span class="icon icon-link"></span></a></h4>
<ol>
<li>두 앱을 빌드하고, Start의 스테이징 배포에 실제 데이터 · 인증 세션 · CDN을 포함해 계약 테스트를 돌립니다.</li>
<li>전환 기간에는 DB 스키마를 두 버전 모두와 호환되게 유지하고, 파괴적인 스키마 변경은 프레임워크 전환과 분리합니다.</li>
<li>공개 origin과 경로를 최대한 유지하고, 바뀌는 경로는 리다이렉트 · 내부 링크 · canonical · sitemap을 함께 갱신합니다.</li>
<li>이전 배포와 라우팅 설정을 기록하고, 트래픽을 되돌릴 방법과 그때 세션 · 쓰기가 어떻게 되는지 알아 둡니다.</li>
<li>전환 후에는 에러율, 로그인 · 뮤테이션 실패, 응답 상태, 색인 신호, 전환 이벤트를 기준선과 비교해 모니터링합니다.</li>
</ol>
<p>Next.js와 남은 설정은 이 모든 동작과 롤백 계획이 검증된 <strong>뒤에</strong> 지웁니다. 이전에 정리한 <a href="/ko/posts/2024-11-23-nextjs-v15-migration/">Next.js 15 마이그레이션</a>과 비교해 보면, 같은 프레임워크 안의 버전 업과 달리 이 작업은 <strong>"API 치환"이 아니라 "실행 모델 번역"</strong> 이라는 점이 가장 큰 차이입니다.</p>
<h4 id="remix--react-router-7에서-온다면">Remix / React Router 7에서 온다면<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#remix--react-router-7에서-온다면"><span class="icon icon-link"></span></a></h4>
<p>Start 전용 가이드는 아직 "coming soon"입니다. 대신 TanStack Router 문서의 <strong>"Migrate from React Router v7"</strong> 이 라우터 수준의 대응을 정리해 두었고, 풀스택 기능이 필요하면 Start를 쓰라고 안내합니다.</p>

































<table><thead><tr><th>React Router v7</th><th>TanStack Router / Start</th></tr></thead><tbody><tr><td><code>useLoaderData()</code></td><td><code>Route.useLoaderData()</code></td></tr><tr><td><code>useParams()</code></td><td><code>Route.useParams()</code></td></tr><tr><td><code>useSearchParams()</code> / <code>setSearchParams</code></td><td><code>validateSearch</code> + <code>Route.useSearch()</code> / <code>navigate({ search: (prev) => … })</code></td></tr><tr><td><code>&#x3C;Link to="/posts/123"></code></td><td><code>&#x3C;Link to="/posts/$postId" params={{ postId: '123' }}></code></td></tr><tr><td><code>defer</code></td><td>직접 대응 없음 — <code>pendingComponent</code> 등으로 로딩 상태 처리</td></tr><tr><td><code>action</code></td><td>직접 대응 없음 — Router 가이드는 뮤테이션 · 폼 라이브러리를 권장</td></tr></tbody></table>
<p>Start로 넘어올 때 개념상 가장 큰 차이는 앞에서 말한 <strong>loader의 실행 위치</strong>입니다. React Router Framework 모드의 <code>loader</code>는 서버에서 실행되지만 Start의 <code>loader</code>는 isomorphic이므로, 서버 전용 코드는 서버 함수로 옮겨야 합니다. 그 위에서 <code>action</code>은 POST 서버 함수, resource route는 서버 라우트, <code>meta</code>는 <code>head</code>로 옮긴다고 보면 출발점으로는 충분합니다(이 세 가지는 공식 매핑이 아니라 제 정리입니다).</p>
<h3 id="장점">장점<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#장점"><span class="icon icon-link"></span></a></h3>
<ol>
<li><strong>끝까지 이어지는 타입 안전성</strong> — 링크, 경로 파라미터, 검증된 search params, loader 데이터, 라우트 컨텍스트, 서버 함수의 입력과 출력이 하나의 타입 그래프로 연결됩니다. 무언가를 바꾸면 영향받는 곳을 에디터(그리고 에이전트)가 바로 찾습니다.</li>
<li><strong>익숙한 앱 모델</strong> — 기본이 SSR + 하이드레이션이라 <code>'use client'</code> 경계나 서버/클라이언트 컴포넌트 구분 없이 지금까지 만들던 React 앱처럼 짤 수 있습니다. RSC 없이도 서버 함수와 SSR을 다 쓸 수 있습니다.</li>
<li><strong>명시적인 실행 경계</strong> — <code>createServerFn</code>, <code>createServerOnlyFn</code>, <code>createIsomorphicFn</code>, Import Protection으로 "이 코드가 어디서 도는가"가 코드에 드러납니다.</li>
<li><strong>라우트 단위 렌더링 제어</strong> — Full SSR, data-only, client-only, SPA 모드, 프리렌더링을 한 앱 안에서 섞어 쓸 수 있습니다.</li>
<li><strong>클라이언트와 서버를 가로지르는 미들웨어</strong> — 서버 함수 미들웨어는 RPC 전후로 클라이언트와 서버 양쪽에서 실행되고, 컨텍스트가 타입과 함께 전달됩니다.</li>
<li><strong>빌드 도구 · 호스팅 선택의 자유</strong> — Vite와 Rsbuild를 모두 지원하고, Nitro와 파트너 플러그인으로 Cloudflare, Netlify, Railway, Vercel, Node, Bun 등에 배포합니다.</li>
<li><strong>TanStack 생태계와의 결합</strong> — Query(데이터 캐시), Form, Table 등 이미 쓰고 있는 TanStack 라이브러리와 같은 설계 철학으로 맞물립니다.</li>
</ol>
<h3 id="단점과-주의할-점">단점과 주의할 점<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#단점과-주의할-점"><span class="icon icon-link"></span></a></h3>
<ol>
<li><strong>RSC는 실험적입니다.</strong> 서버 컴포넌트 중심으로 설계된 앱이라면 Next.js의 성숙도가 더 높습니다.</li>
<li><strong>이미지 · 폰트 최적화가 내장돼 있지 않습니다.</strong> <code>next/image</code>, <code>next/font</code>에 해당하는 기능은 직접 고르고 구성해야 합니다.</li>
<li><strong>isomorphic loader의 함정</strong> — loader에 비밀값이나 DB 코드를 넣으면 클라이언트 내비게이션에서 깨지거나, 서버 코드가 클라이언트 번들에 딸려 갈 수 있습니다. 습관적으로 "loader = 서버"라고 생각하던 팀일수록 리뷰 규칙이 필요합니다.</li>
<li><strong>서버 함수는 공개 엔드포인트입니다.</strong> <code>beforeLoad</code> 가드만으로는 데이터를 보호할 수 없고, 비공개 데이터를 다루는 서버 함수마다 인가가 필요합니다. <code>src/start.ts</code>를 만들면 CSRF 미들웨어도 직접 등록해야 합니다.</li>
<li><strong>세션 API가 없습니다.</strong> 1.0에서 <code>useSession</code>이 빠졌으므로 iron-session 같은 라이브러리나 Clerk · WorkOS 같은 관리형 서비스를 써야 합니다.</li>
<li><strong>빠른 릴리스 주기</strong> — npm 기준으로 1.168 라인 한 줄기에서만 5월 15일부터 10월 10일까지 패치가 61번 나왔습니다. 락파일을 커밋하고, 업그레이드 때 변경 로그를 읽는 습관이 필요합니다.</li>
<li><strong>아직 비어 있는 문서</strong> — Remix 2 / React Router 7 마이그레이션 가이드는 "coming soon"이고, Nitro 통합 문서에도 "활발히 개발 중"이라는 경고가 붙어 있습니다.</li>
<li><strong>보안 이력</strong> — CVE-2026-102989(GHSA-qx66-fv34-fjm8, CVSS 9.3)는 인증 없이 조작한 서버 함수 URL로 애플리케이션 origin에서 공격자의 HTML을 돌려줄 수 있는 반사형 XSS였습니다. <code>@tanstack/react-start</code> 1.143.12부터 1.168.60 직전까지가 영향 범위이고, 로컬 설치만 올려서는 이미 배포된 앱이 패치되지 않으므로 <strong>재빌드 · 재배포</strong>까지 해야 합니다. 프레임워크 설계 문제는 아니지만, 2026년 5월 11일에는 GitHub Actions 설정의 허점을 이용한 공급망 공격(CVE-2026-45321)으로 <code>@tanstack/react-start</code> 1.167.68 · 1.167.71을 포함한 42개 패키지에 자격 증명을 훔치는 악성 버전 84개가 몇 분 사이에 배포됐습니다. 같은 날 모두 deprecated 처리 · 제거됐지만, 그날 설치한 기록이 있다면 공식 포스트모템대로 해당 버전 여부를 확인하고 자격 증명을 교체해야 합니다.</li>
<li><strong>명시적인 버전 정책이 아직 없습니다.</strong> 1.0 공지에는 앞으로 breaking change를 어떻게 다룰지(메이저 주기, 지원 기간) 같은 정책이 따로 적혀 있지 않습니다. <a href="/ko/posts/2026-09-19-react-router-v8/">React Router v8</a>이 "연 1회 메이저"를 명시한 것과 대비됩니다. RC 기간에 <code>.validator()</code> 이름이 두 번 바뀐 것처럼 API가 움직여 온 이력이 있으니, 당분간은 업그레이드마다 변경 로그를 읽는 비용을 잡아 두는 게 좋습니다.</li>
</ol>
<h3 id="실제-도입-사례와-반대-사례">실제 도입 사례와 반대 사례<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#실제-도입-사례와-반대-사례"><span class="icon icon-link"></span></a></h3>
<p>문서와 공지는 결국 만든 쪽의 이야기입니다. 균형을 위해 실제로 옮겨 본 팀들의 기록도 찾아봤습니다. 버전과 시점이 제각각이고 독립 벤치마크가 아니라는 점은 감안해서 읽어 주세요.</p>

<p>여기서 읽히는 공통점은 세 가지입니다.</p>
<ul>
<li><strong>개발 서버 속도와 번들 크기에서는 Start 쪽에 유리한 보고가 있었고</strong>(Inngest, LogRocket), 그 대가는 셋업 비용과 서버/클라이언트 경계 디버깅이었습니다.</li>
<li><strong>Next.js가 기본으로 주던 것</strong>(이미지 최적화, OG 이미지 생성, 메타데이터 규칙)을 직접 채워야 한다는 점이 사례마다 반복됩니다. LLM Gateway 사례는 "Start가 느려서"라기보다 이 공백을 채우지 않았을 때 무슨 일이 생기는지를 보여 줍니다.</li>

<h3 id="nextjs--react-router와-비교">Next.js · React Router와 비교<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#nextjs--react-router와-비교"><span class="icon icon-link"></span></a></h3>
<p>공식 비교 문서(2026-09-11 기준, Next.js 16.3 App Router · React Router 8.3 Framework Mode 대상)를 요약하면 다음과 같습니다. TanStack이 작성한 문서라는 점은 감안해야 하지만, 성능 승자를 단정하지 않고 Next.js가 유리한 지점도 명시하는 등 비교적 절제된 문서입니다. 반면 overview 페이지의 "Next.js · Remix와 같은 기능에 더 많은 기능과 더 강력한 개발 경험"이라는 문장은 근거가 제시되지 않은 벤더 주장입니다.</p>



























































<table><thead><tr><th>항목</th><th>TanStack Start</th><th>Next.js App Router</th><th>React Router Framework Mode</th></tr></thead><tbody><tr><td>서버 렌더링</td><td>기본 SSR + 하이드레이션</td><td>Server/Client Components가 초기 HTML 생성</td><td>설정 가능한 SSR</td></tr><tr><td>렌더링 제어</td><td>라우트별 full / data-only / off</td><td><code>use client</code> 경계(초기 SSR은 유지)</td><td>전역 SSR 설정 + 라우트 <code>clientLoader</code></td></tr><tr><td>RSC</td><td>실험적, opt-in</td><td>핵심 컴포넌트 모델</td><td>unstable</td></tr><tr><td>서버 호출 · 변경</td><td>타입 서버 함수(GET/POST)</td><td>Server Actions</td><td>route action · fetcher</td></tr><tr><td>미들웨어</td><td>요청 + 서버 함수(클라이언트/서버)</td><td>Proxy</td><td>서버 · 클라이언트 라우트 미들웨어</td></tr><tr><td>API 엔드포인트</td><td>서버 라우트</td><td>Route Handlers</td><td>Resource routes</td></tr><tr><td>빌드</td><td>Vite 또는 Rsbuild</td><td>Turbopack</td><td>프레임워크 툴링(Vite 플러그인)</td></tr><tr><td>이미지 · 폰트</td><td>직접 선택</td><td><code>next/image</code> · <code>next/font</code> 내장</td><td>직접 선택</td></tr></tbody></table>
<p>공식 문서가 정리한 선택 기준은 이렇습니다.</p>
<ul>
<li><strong>TanStack Start</strong> — 타입이 붙은 라우트 컨텍스트와 URL 상태, 명시적인 loader와 서버 함수, 라우트별 렌더링 제어가 필요할 때</li>
<li><strong>Next.js</strong> — 서버 컴포넌트 모델과 내장 이미지 · 폰트 · 메타데이터 · 폼 기능이 필요하거나, 팀의 경험과 기존 통합이 이미 Next.js에 쌓여 있을 때</li>
<li><strong>React Router Framework Mode</strong> — loader · action · fetcher 중심의 폼 기반 워크플로와 점진적 향상이 중요할 때</li>
</ul>
<p>그리고 개인적으로 가장 공감한 문장은 이것입니다. <strong>멀쩡히 돌아가는 Next.js 앱을, 라우팅 모델이 다르다는 이유만으로 다시 쓸 필요는 없다.</strong> 대신 실제 데이터 로딩, search params 검증, 뮤테이션, 비인가 접근 처리, 배포까지 포함한 <strong>대표 라우트 하나</strong>를 Start로 만들어 보고, 그게 더 유지보수하기 쉬워지는지로 판단하라는 게 공식 권고입니다.</p>
<h3 id="마무리">마무리<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#마무리"><span class="icon icon-link"></span></a></h3>
<p>TanStack Start 1.0을 한 문장으로 정리하면 <strong>"라우터를 제대로 만들다 보니 풀스택 프레임워크가 됐고, 이제 그 API를 약속하겠다는 릴리스"</strong> 입니다. 새 기능의 발표라기보다, 이미 프로덕션에서 쓰이던 설계에 안정성 보증을 붙인 이정표에 가깝습니다.</p>
<p>Next.js가 "서버를 기본으로, 클라이언트를 예외로" 둔다면 Start는 반대로 <strong>"익숙한 앱을 기본으로, 서버를 명시적으로"</strong> 둡니다. 어느 쪽이 맞는지는 앱의 성격이 정하지만, 타입 안전한 라우팅과 TanStack Query에 이미 익숙한 팀이라면 진입 비용이 가장 낮은 풀스택 선택지라는 건 분명해 보입니다.</p>
<p><strong>도입 체크리스트:</strong></p>
<ul>
<li>✅ Vite 8+(또는 Rsbuild 2) · Node 22.12+ 준비</li>
<li>✅ <code>@tanstack/react-start</code> 1.169.x, 설치된 <code>@tanstack/start-server-core</code>가 1.169.39 이상인지 확인(CVE-2026-102989)</li>
<li>✅ loader에 비밀값 · DB 코드가 없는지 — 있으면 서버 함수로</li>
<li>✅ 비공개 데이터를 다루는 서버 함수마다 <code>authMiddleware</code>(또는 핸들러 내 인가)</li>
<li>✅ <code>src/start.ts</code>를 만들었다면 <code>createCsrfMiddleware()</code> 명시 등록</li>
<li>✅ <code>QueryClient</code>는 <code>getRouter</code> 안에서 생성</li>
<li>✅ 개인화 응답은 <code>Cache-Control: private</code>(또는 <code>no-store</code>)</li>
<li>✅ (RC 사용자) <code>.inputValidator</code> → <code>.validator</code>, <code>useSession</code> 대체, Nitro 플러그인 교체, <code>set-cookie</code> 처리 점검</li>
<li>✅ (Next.js 이전) <code>'use server'</code> → <code>createServerFn</code>, 동작 목록 → 대표 라우트 PoC → 계약 테스트 → 롤백 경로를 쥔 전환</li>
<li>✅ (오래된 튜토리얼 주의) <code>.inputValidator()</code> · <code>nitroV2Plugin</code> · <code>createServerFileRoute</code> · <code>app.config.ts</code>가 보이면 1.0 이전 코드이니 최신 문서와 대조</li>
<li>✅ 2026-05-11에 의존성을 설치한 기록이 있다면 공급망 공격 악성 버전 여부 확인(GHSA-g7cv-rxg3-hmpx)</li>
</ul>
