f:Td07b,<h2 id="전역-상태-관리-라이브러리-등장-배경">전역 상태 관리 라이브러리 등장 배경<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#전역-상태-관리-라이브러리-등장-배경"><span class="icon icon-link"></span></a></h2>
<p>리액트는 처음 출시될 때 Model View Controller 중 View만 담당하는 라이브러리로 발표되었기 때문에 상태를 구성하거나 관리하는 방안이 필요해졌고, 초창기에는 상태와 비즈니스 로직을 Container/Presenter에 몰아넣고 View로직을 props로 받아 뿌려주기만 하는 패턴으로 개발을 진행해 나갔습니다.</p>
<p>하지만 애플리케이션 단위가 커지면서 양방향 데이터 이동이 가능한 MVC/MVP 구조에서 관리해야할 상태와 상태를 핸들링하는 컴포너트가 많아지면서 구조가 복잡해지고 또한 부모에서 로직을 처리하고 자식에게 props로 전달하다보니 props drilling 문제가 발생하게 되었고, 이슈를 해결하기 위해서 전역 상태 관리 라이브러리가 등장하게 되었습니다.</p>
<p><img src="/blog-assets/2023/09/assets/10/Untitled.png" alt="Untitled"></p>
<h3 id="전역-상태-관리-라이브러리가-해결하고자-하는-문제">전역 상태 관리 라이브러리가 해결하고자 하는 문제<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#전역-상태-관리-라이브러리가-해결하고자-하는-문제"><span class="icon icon-link"></span></a></h3>
<p><strong>저장된 상태를 컴포넌트 트리 어디에서든지 읽어 올 수 있는 기능</strong></p>
<ul>
<li>리액트 런타임 내부
<ul>
<li>공유되는 값을 전파하기 위해 리액트 context와 결합하여, <code>useState</code>, <code>useRef</code> 또는 <code>useReducer</code> 같은 기능 활용 → 주요과제는 리렌더링 최적화에 대한 처리는 고민해봐야함.</li>
</ul>
</li>
<li>리액트 외부의 모듈 상태를 활용
<ul>
<li>모듈 상태를 사용하면 싱글톤과 유사하게 상태를 저장</li>
<li>구독을 통해 상태가 변경될 때 리렌더링 하도록 최적화가 용이</li>
<li>단, 메모리 내부의 단일 값이기 때문에 다른 하위 트리에서만 사용되는 다른 상태를 가질 수 없음</li>
</ul>
</li>
</ul>
<p><img src="/blog-assets/2023/09/assets/10/Untitled1.png" alt="Untitled"></p>
<p><strong>저장된 상태를 수정하는 기능</strong></p>
<ul>
<li>리액트 UI 모델은 참조 평등과 불변(immutable) 업데이트를 지원하지만, 자바스크립트는 변경 가능한(mutable) 언어입니다.</li>
<li>Redux 같은 경우에는 모든 상태 업데이트를 변경할 수 없는 방식 채택해서 해결했지만, 보일러플레이트 코드가 많아지는 단점이 생기게 되었습니다.
<ul>
<li>단, 변경 변경 가능한 스타일 코드 작성을 도와주는 immer를 사용한다면 코드 개선이 가능하다.</li>
</ul>
</li>
<li>요즘에는 개발자가 변경 가능한 스타일을 사용할 수 있도록 valtio(js proxy) 같은 라이브러리도 등장</li>
</ul>
<p><img src="/blog-assets/2023/09/assets/10/Untitled2.png" alt="Untitled"></p>
<p><strong>렌더링을 최적화하는 메커니즘</strong></p>
<ul>
<li><strong>수동 최적화:</strong> 종종 특정 상태를 구독하는 셀렉터 함수의 생성을 의미합니다. 여기서 장점은 사용자가 구독 방법을 세밀하게 제어하고 해당 상태를 구독하는 컴포넌트가 재렌더링되는 방법을 최적화할 수 있다는 것입니다. 단점은 이것이 수동 프로세스이고 오류가 발생하기 쉬우며 API에 포함되어서는 안 되는 불필요한 오버헤드가 필요하다는 주장이 있을 수 있습니다.
<ul>
<li>redux: useSelector, recoil: useRecoilState, jotai: useAtom</li>
</ul>
</li>
<li><strong>자동 최적화:</strong> 라이브러리가 사용자가 필요한 것만 자동으로 재렌더링하는 프로세스를 최적화하는 곳입니다. 물론 여기의 장점은 사용이 간편하고 사용자가 수동 최적화에 대해 걱정할 필요 없이 기능 개발에 집중할 수 있다는 것입니다. 이것의 단점은 소비자로서 최적화 프로세스가 블랙박스이고 일부분을 수동으로 최적화하기 위한 방법이 없으면 너무 마술처럼 느껴질 수 있다는 것입니다.
<ul>
<li>Valtio는 업데이트되는 시기를 자동으로 추적하고 컴포넌트가 다시 렌더링되어야 하는 시기를 자동으로 관리하기 위해 내부적으로 <code>Proxy</code>를 사용하고 있습니다.</li>
</ul>
</li>
</ul>
<p><img src="/blog-assets/2023/09/assets/10/Untitled3.png" alt="Untitled"></p>
<p><strong>메모리 사용을 최적화하는 메커니즘을 제공</strong></p>
<ul>
<li>리액트 런타임 외부의 상태를 모듈 상태로 저장하는 상태 관리
<ul>
<li>특정 컴포넌트에 연결되지 않고 수동으로 관리해야 할 수도 있음을 의미(redux)</li>
</ul>
</li>
<li>리액트 런타임 내부의 상태로 저장하는 상태관리
<ul>
<li>리액트 라이프사이클에 연결하면 컴포넌트가 마운트 해제될 때 자동 가비지 컬렉션을 더 쉽게 활용
<ul>
<li>context api, recoil, jotai</li>
</ul>
</li>
</ul>
</li>
</ul>
<p><img src="/blog-assets/2023/09/assets/10/Untitled4.png" alt="Untitled"></p>
<p><strong>전역 상태 관리 라이브러리 및 패턴의 새로운 흐름(상향식 접근법 등장)</strong></p>
<ul>
<li>하향식(top down) 접근법: 리덕스를 포함한 이전까지 나온 상태관리 솔루션
<ul>
<li>필요한 상태를 모두 컴포넌트 트리 상단의 Store가 가지고 있으면서 하위 컴포넌트에서 필요한 상태를 가져다 쓰는 방식</li>
</ul>
</li>
<li>상향식(bottom up) 접근법
<ul>
<li>리액트 hook의 등장과 함께 작은 상태나 로직을 가진 hook들을 조합해가며 복잡한 상태까지 관리하는 방식이 유용할 수 있다고 알려짐에 따라서 상향식 접근법이 논의됨에 따라서 원자 단위의 스토어를 가지게 됨.</li>
<li>원자가 변경된 경우 원자를 구독한 컴포넌트가 리렌더링 되는 방식</li>
<li>recoil, jotai</li>
</ul>
</li>
</ul>

<h2 id="상태관리-라이브러리-요약">상태관리 라이브러리 요약<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#상태관리-라이브러리-요약"><span class="icon icon-link"></span></a></h2>
<p><img src="/blog-assets/2023/09/assets/10/Untitled7.png" alt="Untitled"></p>
<p><strong>상태관리 트렌드</strong></p>
<p><img src="/blog-assets/2023/09/assets/10/Untitled8.png" alt="Untitled"></p>
<p><a href="https://npmtrends.com/jotai-vs-mobx-vs-recoil-vs-redux-vs-valtio-vs-xstate-vs-zustand">https://npmtrends.com/jotai-vs-mobx-vs-recoil-vs-redux-vs-valtio-vs-xstate-vs-zustand</a></p>
<h3 id="contextapi">ContextAPI<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#contextapi"><span class="icon icon-link"></span></a></h3>
<p>정적인 데이터 위주로 처리하거나 업데이트가 자주 발생하지 않을 때 사용하기 적합</p>
<p>복잡한 업데이트를 처리 시 비효율적인데 그 이유는 <strong>Provider로 감싸진 부분의 업데이트가 되지 않은 state에도 리렌더링이 발생하기 때문이다.</strong></p>
<h3 id="flux-redux-zustand">Flux (Redux, Zustand)<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#flux-redux-zustand"><span class="icon icon-link"></span></a></h3>
<p><img src="/blog-assets/2023/09/assets/10/Untitled9.png" alt="Untitled"></p>
<p><strong>Store</strong> 라는 상태 저장소를 기반으로, <strong>Action 타입을 Reducer에 전달</strong>하면 해당 타입에 맞는 동작에 따라 상태값을 갱신 컴포넌트는 <strong>Selector</strong> 를 사용해 Store에서 <strong>필요한 상태값을 구독(subscribing)</strong> 하는 형태</p>
<p><strong>비즈니스 로직을 리액트 컴포넌트에서 분리할 목적으로 사용할 경우</strong></p>
<ul>
<li><a href="https://seungahhong.github.io/blog/2021/12/2021-12-30-redux/">Redux</a>, <a href="https://seungahhong.github.io/blog/2022/03/2022-03-26-redux-toolkit/">Redux-Toolkit</a>
<ul>
<li>Redux는 오직 하나의 store만 가지며, 하나의 객체 트리를 가지기 때문에 디버깅이 용이하다.</li>
<li>store 내부 상태는 action 객체에 의해서만 변경이 가능하다. 모든 state 변화들이 하나의 store에만 집중되어 있고 단방향으로 일어나기 때문에 예측 가능한 결과가 나타난다.</li>
<li>reducer는 순수함수이기 때문에 상태를 변경하는 것이 아닌 새로운 상태를 반환한다.</li>
<li>보일러플레이트 코드가 많다는 단점이 있지만, 해당 이슈를 보완하기 위해서 redux-toolkit이 나오게 되었다.</li>
</ul>
</li>
<li><a href="https://seungahhong.github.io/blog/2023/07/2023-07-22-zustand/">Zustand</a>
<ul>
<li>store 구현 방식 및 변경 방식이 간단함(redux에 비해 보일러플레이트 코드가 적다)</li>
<li>Provider로 래핑할 필요가 없다.</li>

<h3 id="xstate">XState<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#xstate"><span class="icon icon-link"></span></a></h3>
<ul>
<li>특정한 상태들에 따라 동작을 달리해야 하는 경우, 상태의 개수에 따라 복잡도가 매우 증가하게 되는데, 이런 상황을 해결하기 위해서 FSM(유한 상태 기계)에 제한된 구조와 몇 가지 제약으로 복잡하게 얽힌 코드를 정리하기 위한 기술 패턴이 사용된 라이브러리</li>
<li>특히, 복잡한 상태 변화/흐름을 flowchart로 도식화가 가능해서 개발 관련 담당자들과 협업시 효율적인 커뮤니케이션이 가능</li>
</ul>
<p><img src="/blog-assets/2023/09/assets/10/Untitled13.png" alt="Untitled"></p>
<ul>
<li>
<p>일반적으로 FSM은 다섯 부분으로 구성됩니다.(<a href="https://xstate.js.org/docs/about/concepts.html#finite-state-machines">문서</a>)</p>
<ul>
<li>
<p>하나의 초기 상태(An <strong>initial state)</strong></p>
</li>
<li>
<p>유한개의 상태(A finite number of <strong>states</strong>)</p>
</li>
<li>
<p>유한개의 이벤트(A finite number of <strong>events</strong>)</p>
</li>
<li>
<p>현재 상태와 이벤트로 다음 상태를 결정하는 전이 함수(A <strong>transition function</strong> that determines the next state given the current state and event)</p>
</li>
<li>
<p>유한 개의 최종 상태(A (possibly empty) set of <strong>final states</strong>)</p>
</li>
<li>

<h3 id="npm-상태관리-동향---redux--react-query-">npm 상태관리 동향 -> redux 👍, react-query 👍<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#npm-상태관리-동향---redux--react-query-"><span class="icon icon-link"></span></a></h3>
<ul>
<li>
<p>client state: redux > zustand > XState > mobx > jotai > recoil > valtio</p>

<li>
<p>server state: react-query > swr</p>
</li>
</ul>
<h3 id="정적인-데이터-위주-처리-업데이트-자주-발생하지-않을-경우--context-api-">정적인 데이터 위주 처리, 업데이트 자주 발생하지 않을 경우 → context API 👍<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#정적인-데이터-위주-처리-업데이트-자주-발생하지-않을-경우--context-api-"><span class="icon icon-link"></span></a></h3>
<h3 id="상향식-접근법-메모리-사용을-최적화-리액트-생태계만-사용할-경우--jotai-">상향식 접근법, 메모리 사용을 최적화, 리액트 생태계만 사용할 경우 → jotai 👍<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#상향식-접근법-메모리-사용을-최적화-리액트-생태계만-사용할-경우--jotai-"><span class="icon icon-link"></span></a></h3>
<ul>
<li>recoil: 리액트 "외부 요인" 으로써의 상태가 아니라 내부 state를 이용하기 때문에 스케줄러에 접근 가능(facebook 자체 라이브러리)</li>
<li>jotai: Typescript 기반, Recoil에 비해 용량이 매우 적음, unique 키 필요하지 않음</li>
</ul>
<h3 id="하향식-접근법-많은-모듈에서-데이터를-공유-해야할-경우--redux-">하향식 접근법, 많은 모듈에서 데이터를 공유 해야할 경우 → redux 👍<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#하향식-접근법-많은-모듈에서-데이터를-공유-해야할-경우--redux-"><span class="icon icon-link"></span></a></h3>
<ul>
<li>Redux: 다양한 middleware 라이브러리를 제공, 가장 널리 사용되는 라이브러리</li>
<li>zustand: provider 래핑 필요없음, 용량/코드 양이 리덕스보다 작다</li>
</ul>
<h3 id="자동-최적화proxy-사용하고-싶은-경우--valtio--mobx">자동 최적화(proxy) 사용하고 싶은 경우 → valtio 👍, mobx<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#자동-최적화proxy-사용하고-싶은-경우--valtio--mobx"><span class="icon icon-link"></span></a></h3>
<ul>
<li>valtio: react hook 지원</li>
<li>mobx는 객체지향 컴포넌트, hoc 방식의 함수를 사용, decorator 지원</li>
</ul>
<h3 id="flowchart-도식화를-통한-커뮤니케이션-중요할-경우--xstate-">flowchart 도식화를 통한 커뮤니케이션 중요할 경우 → XState 👍<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#flowchart-도식화를-통한-커뮤니케이션-중요할-경우--xstate-"><span class="icon icon-link"></span></a></h3>
<h3 id="서버-상태관리를-사용해야하는-경우--react-query--swr">서버 상태관리를 사용해야하는 경우 → react-query 👍, swr<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#서버-상태관리를-사용해야하는-경우--react-query--swr"><span class="icon icon-link"></span></a></h3>
<ul>
<li>react-query: React 어플리케이션에 서버 상태를 가져오고, 캐싱하고, 동기화하고, 업데이트하는 것을 쉽게 해 준다. graphql을 추가적으로 제공한다.</li>
<li>swr: 먼저 캐시에서 데이터를 반환한 다음, 서버에 데이터를 가져오는 요청을 보내고, 마지막으로 최신 데이터를 제공하는 전략이다. nextjs 환경 세팅이 용이하다.</li>
</ul>
