1c:T119b5,<h2 id="recoil이란">recoil이란?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#recoil이란"><span class="icon icon-link"></span></a></h2>
<p>참고코드(redux-toolkit vs recoil): <a href="https://github.com/seungahhong/states-todos">https://github.com/seungahhong/states-todos</a></p>
<p>리액트 상태 관리 로직의 한계점</p>
<ul>
<li>ContextAPI 부모와 자식간의 커플링에 의존성 발생
<ul>
<li>특히 리렌더링에 문제점 발생</li>
<li>상태관리는 아니다(최초세팅, read, write)</li>
</ul>
</li>
</ul>
<p>Recoil은 왜 필요한 걸까??</p>
<ul>
<li>최대한 React 스러운 API 유지</li>
<li>사용하기 위한 부속 라이브러리 최소화(특히, redux, mobx, redux-toolkit)
<ul>
<li>redux/react 사용을 위해서 react-redux 라이브러리를 사용해야했던 이슈들을 리코일에서는 내부적으로 처리</li>
</ul>
</li>
</ul>
<p><img src="/blog-assets/2022/03/assets/22/recoil.jpeg" alt="recoil"></p>
<ul>
<li>부모 자식간의 의존성을 끊어주며, 독립적인 스토리지에서 컴포넌트에 데이터를 전달한다.</li>
<li>특히, 기존로직을 건드리지 않고 atoms, selector를 사용 시 바로 적용이 가능하다.</li>
</ul>
<p>Recoil 철학</p>
<ul>
<li>보일러플레이트가 적은 API(React Hooks) 사용하여서 React에 로컬 상태를 관리(useState, useReducer)</li>
</ul>

<li>
<p>atom : 데이터를 보관하는 기본단위</p>
<ul>
<li>redux로 생각해본다면 store 저장 일부분?? 담당하고 있으면 기존에 reducer, action에 대한 처리를 내장 커스텀훅 사용가능</li>
</ul>
</li>
<li>
<p>selector</p>
<ul>
<li>atom, 다른 selector들을 조합할 수 있음</li>
<li>파생되는 상태(derived state)를 생성한다.</li>
<li>dependency에 해당되는 atom이 업데이트되면 같이 업데이트 되기 때문에 관리의 부담이 없음.</li>
</ul>
</li>
<li>
<p>hooks api(atom, selector 동일한 api 사용)</p>
<ul>
<li><code>[useRecoilState()](https://recoiljs.org/ko/docs/api-reference/core/useRecoilState)</code>: atom을 읽고 쓰려고 할 때 이 Hook을 사용한다. 이 Hook는 atom에 컴포넌트을 등록하도록 한다.</li>
<li><code>[useRecoilValue()](https://recoiljs.org/ko/docs/api-reference/core/useRecoilValue)</code>: atom을 읽기만 할 때 이 Hook를 사용한다. 이 Hook는 atom에 컴포넌트를 등록하도록 한다.</li>
<li><code>[useSetRecoilState()](https://recoiljs.org/ko/docs/api-reference/core/useSetRecoilState)</code>: atom에 쓰려고만 할 때 이 Hook를 사용한다.</li>
<li><code>[useResetRecoilState()](https://recoiljs.org/ko/docs/api-reference/core/useResetRecoilState)</code>: atom을 초깃값으로 초기화할 때 이 Hook을 사용한다.</li>
</ul>
</li>
<li>
<p>사용방안</p>
<ul>
<li>대규모 프로젝트와 단반향 개발일 경우 flux</li>
<li>작은프로젝트면서 여러 상태와 컴포넌트가 엮인경우 리코일</li>
</ul>
</li>
<li>
<p>단점</p>
<ul>
<li>디버깅이 어려울 수 있다(파생데이터 업데이트)</li>
<li>파생데이터 업데이트가 종속적으로 엮여서 무한루프가 발생할 수 있다( b=cselector cselector=b) 개발자의 역량이 필요하다 단 무한루프는 리코일에서 방지하도록 되어 있음</li>
</ul>
</li>
</ul>
<p>스토어 상세에서 리코일을 적용을 했다면 어떤 점이 좋았을까??</p>

</ul>
</li>
<li>리덕스의 보일러플레이트 코드에 대해서 최대한 줄일 수 있을 것이고 또한 리액트에서 밀고 있는 함수형 컴포넌트로 작성이 용이했을 것이다.</li>

<h2 id="리코일-프로젝트-회고">리코일 프로젝트 회고<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#리코일-프로젝트-회고"><span class="icon icon-link"></span></a></h2>
<p>좋은점</p>
<ul>
<li>기존에는 내가 일일이 action, store에서 업데이트를 시켜줘야해서 불편했지만, 리코일은 set만 할 경우에는 자동으로 get이 호출되서 편했다.</li>
<li>불변성에 대한 고민을 하지 않아서 좋았다.(redux: spread, immer)</li>
<li>캐싱이 되서 좋았다.</li>
<li>꼭 필요한 곳에만 렌더링이 이뤄짐으로 React.memo 같은 처리를 하지 않아서 좋았다.</li>
</ul>
<p>아쉬운점</p>
<ul>
<li>get에서만 async를 제공하기 때문에 다른상태에 세팅할 시 불편한 점이 많았다.(상태값을 저장할 atom을 생성해야해서 코드량이 많아짐)</li>
