10:T7844,<h3 id="introduction">Introduction<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#introduction"><span class="icon icon-link"></span></a></h3>
<p><code>product-spec-harness</code> is a domain-agnostic, interactive multi-agent harness with which a product manager (PM) drafts and validates a Product Requirements Document (PRD) and user stories step by step, starting from a need/problem or a draft plan. It specializes in the product-planning artifacts of the stage <em>before</em> development begins (problem definition → Definition of Ready check (DoR) → PRD → user stories → adversarial verification). It is a standalone plugin that does not depend on any other marketplace plugin (current version 0.3.0).</p>
<p>At the end of every Phase it shows the artifact to the user and moves to the next step only after approval. It asks one thing at a time as if interviewing, and adds a one-line plain-language definition for difficult terms.</p>
<p>It supports two input modes.</p>
<ul>
<li><strong>(A) Draft-input mode</strong> — If you provide a draft plan via argument/conversation, it extracts the problem definition from that content. Then, <em>before</em> generation, it first evaluates the original draft's Definition of Ready (DoR) (with the user's consent) to derive improvement points, and it then must generate the PRD and user stories reflecting those points, finally verifying the artifacts adversarially.</li>
<li><strong>(B) Conversational interview mode</strong> — If there is no draft plan, it defines the problem one question at a time and then produces the PRD and stories. Since there is no input draft to evaluate, it skips Phase 1 (Definition of Ready check).</li>
</ul>
<h3 id="background">Background<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#background"><span class="icon icon-link"></span></a></h3>
<h4 id="why-step-by-step-and-interactive">Why step-by-step and interactive<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#why-step-by-step-and-interactive"><span class="icon icon-link"></span></a></h4>
<p>Product planning does not yield the right answer in one shot, and any PRD and stories built on a wrong problem definition are entirely discarded. That is why this harness shows the key artifact at the end of every Phase and moves on only after the user approves. The approval gate is a mechanism to catch a wrong direction at the cheapest possible moment (when there is still only one Phase's artifact).</p>
<h4 id="why-the-definition-of-ready-check-dor-comes-before-generation">Why the Definition of Ready check (DoR) comes before generation<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#why-the-definition-of-ready-check-dor-comes-before-generation"><span class="icon icon-link"></span></a></h4>
<p>The rationale organized in the rubric (<code>references/dor-review-rubric.md</code>) is as follows.</p>
<ul>
<li><strong>Ambiguous requirements are downstream rework.</strong> Expressions like "fast," "easy," and "appropriately" leave implementers and QA with different interpretations, and that gap gets billed as rework near the end of QA or after release. Incomplete/hidden requirements are the most frequently cited problem in requirements engineering (NaPiRE survey: 109 of 228 respondents = 48%, Méndez Fernández et al. 2017), and avoidable rework accounts for a substantial share of project effort (Boehm &#x26; Basili 2001).</li>
<li><strong>Acceptance criteria must be testable, and the happy path alone is not enough.</strong> Every acceptance criterion must be expressible as condition-action-result (Given-When-Then), and must cover not only the happy flow but also boundary, error, empty-state, and permission flows.</li>
<li><strong>Automatic detection (LLM) assists human review; it does not pass the gate on its own.</strong> LLMs/NLP help detect defects and ambiguity in user stories (in-context examples improved ambiguous-requirement classification by an average of 20.2% over 0-shot — Bashir/Ferrari et al., ICSME 2025), but they can over-detect or hallucinate simply because something deviates from an ideal template (GPT-5; rule-based AQUSA precision 0.61 — Perkusich et al. 2025). Therefore evaluation results are presented as improvement candidates rather than as final verdicts, and a human makes the domain/context judgment.</li>
</ul>
<h4 id="why-it-internalizes-everything-as-a-standalone-plugin">Why it internalizes everything as a standalone plugin<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#why-it-internalizes-everything-as-a-standalone-plugin"><span class="icon icon-link"></span></a></h4>
<p>The Definition of Ready (DoR) methodology (readiness gate, a scorecard for the six criteria of a good story (INVEST), condition-action-result completeness, ambiguity check, dependency reference) is internalized inside this plugin (<code>references/dor-review-rubric.md</code>) without referencing an external plugin. It works standalone with only this plugin installed.</p>
<h4 id="out-of-scope-boundaries">Out of scope (boundaries)<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#out-of-scope-boundaries"><span class="icon icon-link"></span></a></h4>
<p>To avoid trigger conflicts, the following are explicitly out of scope, and this boundary is stated in the <code>plugin.json</code> description and in <code>evals/trigger-eval.json</code>.</p>
<ul>
<li>Frontend screen implementation, components, a PRD for technical design, implementation requirements, or writing code</li>
<li>Code review, commit messages, PR review, and work that creates/diagnoses/improves the harness itself</li>
<li>Merely inspecting an already-completed PRD/user stories/design/contract/acceptance criteria as an independent gate at handoff time (rather than authoring them)</li>
</ul>
<h3 id="design">Design<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#design"><span class="icon icon-link"></span></a></h3>
<h4 id="the-5-phase-structure">The 5-Phase structure<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#the-5-phase-structure"><span class="icon icon-link"></span></a></h4>

<p>Report format at the end of every Phase: <code>[Phase N] {key decision} — next: {next}. Shall we proceed?</code></p>
<h4 id="the-agent-team">The agent team<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#the-agent-team"><span class="icon icon-link"></span></a></h4>
<p>It is a harness in which 5 agents collaborate, and the orchestrator specifies <code>model: "opus"</code> on every Agent call (the convention being that reasoning quality determines the quality of the planning artifacts).</p>
<ul>
<li><strong>requirements-analyst</strong> (Phase 0) — Defines the need/problem/user. If a draft exists it extracts a fixed 5-field card, and it supplements only the fields that cannot be extracted or are ambiguous, one question at a time. It rejects undecidable goals and success metrics.</li>
<li><strong>dor-evaluator</strong> (Phase 1) — Evaluates the original draft from the Definition of Ready (DoR) perspective. If INVEST's Testable/Independent is 0, it blocks kickoff. It does not edit the draft directly but only presents improvement candidates, and it presents the result in chat only (does not save immediately).</li>
<li><strong>prd-writer</strong> (Phase 2) — Takes the problem-definition card and Phase 1 improvement points and writes a standard-structure PRD. Explicit scope-Out and observable success metrics are mandatory.</li>
<li><strong>story-writer</strong> (Phase 3) — Develops the PRD's core requirements into user stories + acceptance criteria, attaching an INVEST self-check and covered-requirement (R#) tagging to each story to enable requirement↔story traceability.</li>
<li><strong>spec-reviewer</strong> (Phase 4) — Verifies the PRD·stories adversarially. Praise-style comments are banned; it produces a report containing weaknesses, severity, and disposition. Supplementary recommendations follow additive-first.</li>
</ul>
<h4 id="input-mode-discrimination-and-the-difference-between-phase-1-and-4">Input-mode discrimination and the difference between Phase 1 and 4<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#input-mode-discrimination-and-the-difference-between-phase-1-and-4"><span class="icon icon-link"></span></a></h4>
<ul>
<li>At the start it discriminates the input mode once and declares it in one line in chat. User-provided text/files that describe two or more of problem/goal/feature/target/constraint are treated as a draft (mode A), and when the boundary is ambiguous it safely defaults to mode A (going straight to the PRD with the mode undetermined is forbidden). In mode A, presenting the Phase 1 entry question is mandatory, and only whether to <em>run</em> the evaluation is subject to user consent (yes/no).</li>
<li><strong>Phase 1 vs Phase 4</strong> — Their targets differ. Phase 1 evaluates the <em>input original draft</em> with the Definition of Ready (DoR) <em>before</em> generation and reflects improvement points into the PRD·stories (shown in chat). Phase 4 verifies the <em>generated artifacts</em> (PRD·stories) adversarially (shown in chat + saved on consent).</li>
</ul>
<h4 id="approval-gatesave-policy-principles-common-to-all-phases">Approval gate·save policy (principles common to all Phases)<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#approval-gatesave-policy-principles-common-to-all-phases"><span class="icon icon-link"></span></a></h4>
<ul>
<li><strong>Approval gate</strong> — At the end of every Phase it presents the key artifact + a one-line report and obtains approval. Before writing a file it shows the full content as a preview.</li>
<li><strong>Observable acceptance criteria</strong> — Acceptance criteria and success metrics are written as condition-action-result (Given/When/Then) that a third party can judge by observation, and undecidable sentences like "good/satisfying/intuitive" are banned.</li>
<li><strong>Completeness·traceability</strong> — A requirement↔story matrix tracks whether every core PRD requirement is covered by ≥1 story.</li>
<li><strong>additive-first</strong> — When supplementing an agreed PRD/stories, it proposes non-destructive additions·relaxations before overturning existing items.</li>
<li><strong>Save policy (opt-in)</strong> — Artifacts are gathered under <code>.claude/_docs/&#x3C;plan slug>/</code>. <code>PRD.md</code>·<code>user-stories.md</code> are saved upon preview approval, while <code>product-spec-review.md</code> (Phase 1 result) and <code>adversarial-review.md</code> (Phase 4 report) are recorded only when it asks whether to save and the user consents.</li>
</ul>

<h4 id="core-implementation-elements">Core implementation elements<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#core-implementation-elements"><span class="icon icon-link"></span></a></h4>
<ul>
<li><strong>Orchestrator (<code>skills/product-spec/SKILL.md</code>)</strong> — The entry-point skill. It defines input-mode discrimination → sequential progression through Phase 0~4 → wrap-up (opt-in save). In each Phase it invokes a dedicated agent as <code>Agent(subagent_type=..., model="opus", prompt=...)</code>, specifying each call's role·input·rules·output in the prompt.</li>
<li><strong>Three reference documents</strong> — <code>prd-template.md</code> (fixed 6 sections: background·problem / goals·success metrics / scope In·Out / core requirements / assumptions·risks / milestones), <code>user-story-guide.md</code> (story format + Gherkin acceptance criteria + INVEST), <code>dor-review-rubric.md</code> (DoR gate·INVEST scorecard·Given-When-Then completeness·ambiguity check·dependencies + the <code># Definition of Ready Review (DoR Review)</code> template + an 8-section checklist + Honesty Guardrail·rationale).</li>
<li><strong>Format of the points-to-improve checklist</strong> — Met items are marked <code>[O]</code>, unmet items are marked <code>[ ]</code> followed immediately below by <code>↳ Improve like this:</code> (a Before→After example).</li>
<li><strong>Honesty Guardrail</strong> — Quantitative figures are cited only with a verified grade·source, and promises of "N% improvement" are forbidden.</li>
<li><strong>Trigger check (<code>evals/trigger-eval.json</code>)</strong> — It defines cases that should trigger (should-trigger, e.g., "write a PRD," "derive user stories") and cases that should not (should-not-trigger, e.g., a frontend-development PRD·code·commit) to check trigger accuracy.</li>
</ul>
<h4 id="artifact-placement">Artifact placement<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#artifact-placement"><span class="icon icon-link"></span></a></h4>
