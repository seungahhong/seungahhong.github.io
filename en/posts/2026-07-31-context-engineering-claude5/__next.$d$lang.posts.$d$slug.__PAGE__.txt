11:T5c49,<h2 id="1-what-is-this-post-about">1. What Is This Post About?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#1-what-is-this-post-about"><span class="icon icon-link"></span></a></h2>
<p>Here it is in a single sentence.</p>
<blockquote>
<p><strong>The conventional wisdom that "the more rules you write for the AI, the better it performs" has been overturned.</strong> Anthropic deleted <strong>more than 80%</strong> of Claude Code's system prompt, and coding evaluation scores did not drop.</p>
</blockquote>
<p>In previous posts I covered how to <strong>build a harness well</strong> (<a href="/en/posts/2026-06-04-fe-harness/">Frontend Harness Engineering</a>) and how to <strong>make it fix itself</strong> (<a href="/en/posts/2026-07-05-meta-harness/">Self-Healing Harness</a>). This post runs in the opposite direction: <strong>what to take out of a harness.</strong></p>
<h3 id="what-weve-all-been-doing">What We've All Been Doing<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#what-weve-all-been-doing"><span class="icon icon-link"></span></a></h3>
<p>Anyone who has worked with a harness has walked this path.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">The AI makes a mistake</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">   → add one line to CLAUDE.md: "don't do this"</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">   → it makes the mistake again</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">   → add the same line to SKILL.md too</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">   → add it to the tool description as well, just in case</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">   → ...three months later, CLAUDE.md is 400 lines long</span></span></code></pre></figure>
<p>Adding rules feels immediately reassuring. "It's written down now, so it won't get it wrong." But as rules accumulate, so do <strong>sentences that contradict each other.</strong> Here is a case Anthropic actually found.</p>

















<table><thead><tr><th>Where it was written</th><th>What it said</th></tr></thead><tbody><tr><td>System prompt A</td><td>"leave documentation as appropriate"</td></tr><tr><td>System prompt B</td><td>"DO NOT add comments — one short line max"</td></tr></tbody></table>
<p>Each sentence is reasonable on its own. But <strong>read together</strong>, the model has to compute "which one applies right now?" every single time. That computation is the cost.</p>
<h3 id="what-changed">What Changed<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#what-changed"><span class="icon icon-link"></span></a></h3>
<p>The core reason is simple: <strong>the model got better.</strong> The Claude 5 generation (Opus 5, Fable 5) can look at the surrounding context and decide for itself. So spelling out every answer in advance now works against it.</p>
<p>Looking at the actual rewritten sentence makes it click.</p>
<p><strong>Before (nailed down as a rule):</strong></p>
<blockquote>
<p>"In code: default to writing no comments. Never write multi-paragraph docstrings or multi-line comment blocks — one short line max."</p>
</blockquote>
<p><strong>After (left to judgment):</strong></p>
<blockquote>
<p>"Write code that reads like the surrounding code: match its comment density, naming, and idiom."</p>
</blockquote>
<p>The second is shorter yet covers more situations. The first can't handle the exception "editing a legacy file that is densely commented"; the second handles it on its own.</p>
<hr>
<h2 id="2-six-rules-got-flipped">2. Six Rules Got Flipped<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#2-six-rules-got-flipped"><span class="icon icon-link"></span></a></h2>
<p>Anthropic laid out six shifts. Let's walk through them.</p>








































<table><thead><tr><th>#</th><th>Before (Claude 4 era)</th><th>Now (Claude 5 generation)</th></tr></thead><tbody><tr><td>1</td><td>Give explicit rules</td><td>Let it apply judgment</td></tr><tr><td>2</td><td>Attach usage examples</td><td>Design better tool interfaces</td></tr><tr><td>3</td><td>Load everything you might need upfront</td><td>Progressive disclosure</td></tr><tr><td>4</td><td>Repeat important things in several places</td><td>Write it in exactly one place</td></tr><tr><td>5</td><td>Save what to remember in CLAUDE.md</td><td>Rely on auto-memory</td></tr><tr><td>6</td><td>Leave markdown plans</td><td>Leave rich references (code, HTML)</td></tr></tbody></table>
<h3 id="rule-1--judgment-instead-of-instruction">Rule 1 — "Judgment" Instead of "Instruction"<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#rule-1--judgment-instead-of-instruction"><span class="icon icon-link"></span></a></h3>
<p>The test for whether to write a rule down is simple.</p>
<ul>
<li><strong>Things the model can infer from its surroundings</strong> → don't write them. (indent width, comment style)</li>
<li><strong>Things it cannot infer no matter how much it reads</strong> → write them. (e.g. "this repo is a static export, so server APIs are unavailable")</li>
</ul>
<p>Writing the former creates noise; omitting the latter creates incidents.</p>
<h3 id="rule-2--interfaces-instead-of-examples">Rule 2 — "Interfaces" Instead of "Examples"<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#rule-2--interfaces-instead-of-examples"><span class="icon icon-link"></span></a></h3>
<p>We used to bolt piles of usage examples onto tool descriptions. Now <strong>naming parameters and describing them well</strong> is more effective — and <strong>enumerating the choices</strong> (an enum) beats ten examples.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">[ Example-driven ]                 [ Interface-driven ]</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">"Use it like this:                 depth: 'shallow' | 'medium' | 'deep'</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">  search(q, 'deep')                      ↳ how deeply to explore</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">  search(q, 'shallow')</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">  ... (8 more examples)"           One line, and every valid value is visible</span></span></code></pre></figure>
<p>Examples leave you asking "but what about this case?" An enumeration doesn't.</p>
<h3 id="rule-3--dont-load-it-all-let-it-be-fetched">Rule 3 — Don't Load It All; Let It Be Fetched<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#rule-3--dont-load-it-all-let-it-be-fetched"><span class="icon icon-link"></span></a></h3>
<p><strong>Progressive disclosure</strong> is the central idea in this shift. Instead of pushing every piece of information into context from the start, information is <strong>loaded at the moment it becomes relevant.</strong></p>

























<table><thead><tr><th>Mechanism</th><th>When it loads</th><th>Cost</th></tr></thead><tbody><tr><td>CLAUDE.md body</td><td><strong>Always</strong>, at session start</td><td>Paid on every request</td></tr><tr><td>Skill</td><td>Only for related work</td><td>Paid only when used</td></tr><tr><td>Deferred tools</td><td>Only once searched for</td><td>Paid only when used</td></tr></tbody></table>
<p>One practical rule falls right out of this: <strong>keep only what's needed almost every time in CLAUDE.md, and move the occasional stuff into Skills.</strong></p>
<h3 id="rule-4--stop-repeating-yourself">Rule 4 — Stop Repeating Yourself<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#rule-4--stop-repeating-yourself"><span class="icon icon-link"></span></a></h3>
<p>We used to write important instructions in the system prompt, in the tool description, <em>and</em> in CLAUDE.md. It felt like a safety net. But repetition creates two problems.</p>
<ol>
<li><strong>You pay for the tokens three times</strong> — the same sentence is read in three places.</li>
<li><strong>You miss one when you update it</strong> → and that's the moment a <strong>contradiction</strong> is born.</li>
</ol>
<p>The current recommendation is <strong>"put it in the tool description only"</strong> — the one place guaranteed to be read when that tool is used.</p>
<h3 id="rule-5--claudemd-is-not-a-notepad">Rule 5 — CLAUDE.md Is Not a Notepad<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#rule-5--claudemd-is-not-a-notepad"><span class="icon icon-link"></span></a></h3>
<p>We used to hit <code>#</code> to say "remember this" and have it appended to CLAUDE.md. Now <strong>auto-memory</strong> saves contextually relevant things on its own, which narrows CLAUDE.md's job.</p>

























<table><thead><tr><th>Nature of the information</th><th>Where it belongs</th></tr></thead><tbody><tr><td>Gotchas in this repo (why the build breaks)</td><td>CLAUDE.md</td></tr><tr><td>The team's opinions and know-how, per task type</td><td>Skill</td></tr><tr><td>The individual user's preferences and history</td><td>Auto-memory</td></tr><tr><td>Deep supporting material</td><td>References (@mentions)</td></tr></tbody></table>
<h3 id="rule-6--something-executable-beats-a-plan-document">Rule 6 — Something Executable Beats a Plan Document<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#rule-6--something-executable-beats-a-plan-document"><span class="icon icon-link"></span></a></h3>
<p>Instead of describing "what to build" in markdown prose, leave it in a <strong>more precise form.</strong></p>
<ul>
<li>A test suite → pass/fail is unambiguous</li>
<li>A spec written as code (types, signatures) → little room for interpretation</li>
<li>A rubric → the quality bar is explicit</li>
<li>An HTML artifact → no need to describe a screen in words</li>
</ul>
<p>Prose is interpreted differently by every reader. Types and tests are not.</p>
<hr>
<h2 id="3-so-where-does-each-thing-go">3. So Where Does Each Thing Go?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#3-so-where-does-each-thing-go"><span class="icon icon-link"></span></a></h2>
<p>Let's put it together. Context is assembled from four places, each with a distinct job.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">┌─ System prompt ───── The product's own context. Users rarely touch it.</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">│                      (If you build a custom agent, this is the crux.)</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">│</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">├─ CLAUDE.md ───────── Only this repo's "gotchas." Keep it light.</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">│                      Split long verification procedures into Skills.</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">│</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">├─ Skill ───────────── Team opinions and know-how. Loads only when relevant.</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">│                      If long, apply progressive disclosure inside it too.</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">│</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">└─ References ──────── Link deep material via @mentions.</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">                       Prefer code-based specs over prose descriptions.</span></span></code></pre></figure>
<h3 id="a-claudemd-diet-checklist">A CLAUDE.md Diet Checklist<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#a-claudemd-diet-checklist"><span class="icon icon-link"></span></a></h3>
<p>Re-reading my own blog repo's <code>CLAUDE.md</code> against this standard, the deletion candidates jumped out immediately.</p>



































<table><thead><tr><th>Type of sentence</th><th>Verdict</th><th>Why</th></tr></thead><tbody><tr><td>"<code>src/components/</code> holds React components"</td><td>❌ Delete</td><td>The directory name already says it</td></tr><tr><td>"We use TypeScript strict mode"</td><td>❌ Delete</td><td>Open <code>tsconfig.json</code> and you know</td></tr><tr><td>"Static export means tag pages use query-based filtering"</td><td>✅ Keep</td><td><strong>Not knowing this causes bugs</strong></td></tr><tr><td>"Without <code>public/.nojekyll</code>, <code>_next</code> gets ignored"</td><td>✅ Keep</td><td>A textbook repo gotcha</td></tr><tr><td>"Commit messages should be written like this, and..." (20 lines)</td><td>➡️ Move to Skill</td><td>Only needed when committing</td></tr></tbody></table>
<p>The criterion collapses into one question: <strong>"If I don't write this, will the AI get it wrong?"</strong> If not, it can go.</p>
<h3 id="getting-diagnosed-automatically--doctor">Getting Diagnosed Automatically — <code>/doctor</code><a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#getting-diagnosed-automatically--doctor"><span class="icon icon-link"></span></a></h3>
<p>If judging this yourself feels like a burden, there's a tool for it. Claude Code's <strong><code>/doctor</code></strong> (<code>claude doctor</code> from the CLI) inspects the size of your Skills, CLAUDE.md, and system prompt and helps rightsize them. If the <a href="/en/posts/2026-07-05-meta-harness/">self-healing harness</a> from the previous post was "watch a mistake, then <strong>add</strong> a rule," <code>/doctor</code> is the automation of the opposite direction — <strong>taking things out.</strong></p>
<hr>
<h2 id="4-easy-things-to-get-wrong">4. Easy Things to Get Wrong<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#4-easy-things-to-get-wrong"><span class="icon icon-link"></span></a></h2>
<p>It would be unfortunate if this post read as <strong>"get rid of your harness."</strong> Let me be precise about a few things.</p>
<h3 id="misreading-1--so-i-can-delete-claudemd">Misreading 1 — "So I can delete CLAUDE.md?"<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#misreading-1--so-i-can-delete-claudemd"><span class="icon icon-link"></span></a></h3>
<p>No. <strong>Shrink it, don't scrap it.</strong> Repo-specific traps stay invisible to the model no matter how good it gets. Why <code>.nojekyll</code> is necessary won't emerge from reading every file in the project.</p>
<h3 id="misreading-2--should-things-that-must-be-enforced-also-be-left-to-judgment">Misreading 2 — "Should things that must be enforced also be left to judgment?"<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#misreading-2--should-things-that-must-be-enforced-also-be-left-to-judgment"><span class="icon icon-link"></span></a></h3>
<p>This is the same distinction I drew in the previous post. <strong>What you leave to judgment and what you block mechanically are different things.</strong></p>

























<table><thead><tr><th>Nature</th><th>Where it belongs</th><th>Effect of this shift</th></tr></thead><tbody><tr><td><strong>Must be blocked, always</strong> (dangerous commands)</td><td>hook · permission</td><td>None. Still blocked by machinery</td></tr><tr><td><strong>Requires judgment</strong> (style, trade-offs)</td><td>Guidance in docs</td><td><strong>Shrink it.</strong> The model can judge</td></tr><tr><td><strong>Repo-specific facts</strong> (build traps)</td><td>CLAUDE.md</td><td>Keep</td></tr></tbody></table>
<p>"Cut your rules" is <strong>not a statement about the third row.</strong> And enforcement never came from documents in the first place — it came from hooks.</p>
<h3 id="misreading-3--does-this-apply-to-every-model">Misreading 3 — "Does this apply to every model?"<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#misreading-3--does-this-apply-to-every-model"><span class="icon icon-link"></span></a></h3>
<p>No. What Anthropic removed was the system prompt <strong>for advanced models like Claude Opus 5 and Fable 5.</strong> If you're running a smaller model, explicit instructions still earn their keep. <strong>A harness is tuned to the model</strong> — it isn't written once and left forever.</p>
<hr>
<h2 id="5-applying-it-in-practice">5. Applying It in Practice<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#5-applying-it-in-practice"><span class="icon icon-link"></span></a></h2>
<p>Applied to my own repo, the order would be this.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">① Find contradictions   Look for sentence pairs that say different things</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">                        about the same topic → always merge into one (top priority)</span></span>
<span data-line=""> </span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">② Delete the obvious    Remove facts you'd learn by opening the file</span></span>
<span data-line=""> </span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">③ Split out the rare    Move procedures needed only at specific moments —</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">                        deploy, commit, release — into Skills</span></span>
<span data-line=""> </span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">④ Rules → principles    Replace several "don't do X" lines with one</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">                        "match the surroundings"</span></span>
<span data-line=""> </span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">⑤ Verify                Run a few ordinary tasks and check quality holds</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">                        → if it drops, revert just that item</span></span></code></pre></figure>
<p>Step ⑤ matters. <strong>Removal needs verification too.</strong> It's the same reason the self-healing harness from the previous post checked consistency, body cost, trigger accuracy, and generalization all at once before adopting a patch. If it got shorter <em>and</em> worse, that isn't an improvement.</p>
<h3 id="questions-to-confirm-you-actually-trimmed">Questions to Confirm You Actually Trimmed<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#questions-to-confirm-you-actually-trimmed"><span class="icon icon-link"></span></a></h3>

























<table><thead><tr><th>Question</th><th>Passing answer</th></tr></thead><tbody><tr><td>Is the same instruction in two files?</td><td>It shouldn't be</td></tr><tr><td>If I delete this sentence, does the AI get it wrong?</td><td>If "no," delete it</td></tr><tr><td>Is this procedure needed every session?</td><td>If "no," move it to a Skill</td></tr><tr><td>Can this explanation be replaced by code?</td><td>If yes, use code</td></tr></tbody></table>

<h2 id="6-wrapping-up--where-harnesses-are-headed">6. Wrapping Up — Where Harnesses Are Headed<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#6-wrapping-up--where-harnesses-are-headed"><span class="icon icon-link"></span></a></h2>
<p>Read alongside the previous two posts, the arc becomes visible.</p>



































<table><thead><tr><th>Stage</th><th>Question</th><th>Direction</th><th>Post</th></tr></thead><tbody><tr><td><strong>Stage 1</strong> Build</td><td>What should I write down?</td><td>Adding</td><td>2026-06 <a href="/en/posts/2026-06-04-fe-harness/">FE harness</a></td></tr><tr><td><strong>Stage 2</strong> Self-healing</td><td>How do I fold mistakes back in?</td><td>Adding (with approval)</td><td>2026-07 <a href="/en/posts/2026-07-05-meta-harness/">meta-harness</a></td></tr><tr><td><strong>Stage 3</strong> Pruning</td><td>What should I take out?</td><td><strong>Subtracting</strong></td><td>This post</td></tr><tr><td><strong>Stage 4</strong> Balance</td><td>How do I move both ways automatically?</td><td>Both</td><td>Ahead</td></tr></tbody></table>
<p>Stages 1 and 2 grew the harness; stage 3 is the first move in the <strong>opposite direction.</strong> And the two aren't contradictory — they're a pair. <strong>A system that only adds will inevitably bloat, and a bloated harness breeds contradictions.</strong> If self-healing adds rules, then periodic pruning of the <code>/doctor</code> variety has to take them back out for the thing to stay balanced.</p>
<p>The core message is one sentence.</p>
<blockquote>
<p><strong>A harness exists not to control the model, but to tell it only what it cannot know.</strong></p>
</blockquote>
<p>As models improve, the scope of "what the model cannot know" shrinks — and the harness should shrink with it. A harness that only ever grows may be holding not the model's limits, but <strong>our own anxiety.</strong></p>
