23:T30254,<h2 id="tanstack-start-10-is-stable-overview-usage-and-migration-guide">TanStack Start 1.0 Is Stable: Overview, Usage, and Migration Guide<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#tanstack-start-10-is-stable-overview-usage-and-migration-guide"><span class="icon icon-link"></span></a></h2>
<h3 id="️-tldr">✍️ TL;DR<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#️-tldr"><span class="icon icon-link"></span></a></h3>
<blockquote>
<p><strong>TanStack Start is a full-stack React framework that adds SSR, streaming, server functions, and middleware on top of TanStack Router, and it became stable as 1.0 (npm <code>1.169</code>) on October 13, 2026.</strong> Its default is "the familiar app that renders on the server and hydrates in the browser," and you hand work to the server only through explicit APIs like <code>createServerFn</code>. That is the biggest difference from the Next.js App Router, where Server Components are the default.</p>
</blockquote>
<h4 id="summary">Summary<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#summary"><span class="icon icon-link"></span></a></h4>
<ul>
<li><strong>Released</strong>: announced on the TanStack blog on October 13, 2026 ("TanStack Start 1.0 is Stable"). The first stable package is <code>@tanstack/react-start@1.169.0</code>, and the latest at the time of writing (2026-10-22) is <code>1.169.3</code>. "1.0" is the product version name, so you install <code>1.169</code> or later rather than <code>@tanstack/react-start@1.0</code> (the package was already on 1.1xx during the RC, so the number alone can't tell you RC from stable).</li>
<li><strong>What it is</strong>: routing is handled <strong>entirely by TanStack Router</strong>, and Start adds full-document SSR, streaming, server functions (type-safe RPC), server routes (APIs), middleware/context, client/server builds, and universal deployment on top. According to the official homepage, it supports React and Solid.</li>
<li><strong>Build tools</strong>: <strong>Vite 8 or later</strong> or <strong>Rsbuild 2</strong>. Node must be 22.12 or later.</li>
<li><strong>Execution model</strong>: all code is <strong>isomorphic</strong> by default (it runs on both server and client). Even a route <code>loader</code> runs on the server for the first request and in the browser for later navigations. Secrets and database access have to be fenced off with server functions or <code>.server.ts</code> files.</li>
<li><strong>Rendering options</strong>: pick per-route <code>ssr: true | 'data-only' | false</code> (Selective SSR), an app-wide SPA mode, static prerendering, or ISR driven by HTTP cache headers — all within one framework.</li>
<li><strong>RSC</strong>: <strong>experimental and opt-in</strong>. It is not the default component model as in Next.js; instead, a server function returns UI rendered on the server, and the client composes it. Next.js-style <code>'use server'</code> actions are <strong>intentionally unsupported</strong>; you use explicit server functions only.</li>
<li><strong>Migration</strong>: going from RC to 1.0 is mostly about requiring Vite 8, <code>.inputValidator()</code> → <code>.validator()</code>, the removal of <code>useSession</code>, swapping the Nitro plugin, and changed error/response behavior. For Next.js App Router → Start there is an official guide with a before/after example; the Remix 2 / React Router 7 guide is still "coming soon."</li>
<li><strong>Security history</strong>: <strong>CVE-2026-102989</strong>, disclosed September 30, 2026 (a reflected XSS in server-function response handling, CVSS 9.3). Confirm that the <code>@tanstack/start-server-core</code> you actually have installed is <strong>1.169.39 or later</strong>, then redeploy. On May 11 there was also an npm supply-chain attack (CVE-2026-45321) that pushed malicious versions of 42 <code>@tanstack/*</code> packages.</li>
</ul>

<h3 id="overview-what-is-tanstack-start">Overview: What Is TanStack Start?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#overview-what-is-tanstack-start"><span class="icon icon-link"></span></a></h3>
<p>TanStack Start is <strong>a full-stack React framework powered by TanStack Router</strong>. It provides full-document SSR, streaming, server functions, and client/server builds, and because it supports both Vite and Rsbuild, you can deploy it to whatever hosting provider or runtime you want.</p>
<p>It has only two building blocks.</p>
<ul>
<li><strong>TanStack Router</strong> — a router that handles nested routing, search params, and data loading in a type-safe way</li>
<li><strong>Vite or Rsbuild</strong> — the build tool responsible for HMR and production builds</li>
</ul>
<h4 id="router-alone-or-start">Router alone, or Start?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#router-alone-or-start"><span class="icon icon-link"></span></a></h4>
<p>The official docs say that "90% of a framework is the router." Start leaves routing <strong>entirely</strong> to TanStack Router and layers server features on top. So the question becomes: "Do you need server features?"</p>



































<table><thead><tr><th>What you need</th><th align="center">Router only</th><th align="center">Start</th></tr></thead><tbody><tr><td>Type-safe routing · search params · loaders</td><td align="center">✅</td><td align="center">✅</td></tr><tr><td>Full-document SSR · streaming</td><td align="center">△</td><td align="center">✅</td></tr><tr><td>Server functions (type-safe RPC) · server routes (API)</td><td align="center">—</td><td align="center">✅</td></tr><tr><td>Request/server-function middleware · context</td><td align="center">—</td><td align="center">✅</td></tr><tr><td>Full-stack client + server builds · universal deployment</td><td align="center">—</td><td align="center">✅</td></tr></tbody></table>
<p>△ means TanStack Router does have experimental SSR and streaming APIs, but you have to assemble them yourself; Start packages them as built-ins. The official position is to recommend Router alone (an SPA) <strong>only when you are certain you need none of the above</strong>.</p>
<h4 id="the-philosophy-behind-it">The philosophy behind it<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#the-philosophy-behind-it"><span class="icon icon-link"></span></a></h4>
<p>In the 1.0 announcement, Tanner Linsley is clear about the starting point. He felt the React ecosystem was narrowing its picture of what an application should look like — Next.js betting heavily on RSC and moving toward a server-centric model, React Router and Remix working through their own changes — and he wanted to keep <strong>the way he had built apps for the last ten years</strong> (state management, client-side navigation, data caching) while using new capabilities like server rendering, streaming, and server functions <strong>only where they belong</strong>.</p>
<p>So Start's defaults look like this.</p>
<ul>
<li>Components are just components, and routes are just routes. There are no <code>'use client'</code> boundaries to draw.</li>
<li>A route can be rendered on the server, can load only its data on the server while the component renders on the client, or can be handled entirely on the client.</li>
<li>When you need the server, you cross over through <strong>explicit APIs</strong> (<code>createServerFn</code>, middleware).</li>
<li>RSC also plugs in as an <strong>optional feature</strong> that does not change the app model.</li>
</ul>
<h3 id="the-road-to-10">The Road to 1.0<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#the-road-to-10"><span class="icon icon-link"></span></a></h3>













































<table><thead><tr><th>When</th><th>What happened</th></tr></thead><tbody><tr><td>December 2023</td><td>Server utilities that became the seed of Start appear in the repo</td></tr><tr><td>May 2024</td><td>The <code>react-router-server</code> package is renamed to <code>start</code></td></tr><tr><td>June 2025</td><td><code>1.121.0</code> — Vinxi is removed in favor of a Vite plugin ("devinxi")</td></tr><tr><td>September 2025</td><td><code>1.132.0</code> ships alongside the "v1 Release Candidate" announcement (9/23)</td></tr><tr><td>April 2026</td><td>React Server Components released as an experimental feature (4/13, "React Server Components Your Way")</td></tr><tr><td>May 2026</td><td>npm supply-chain attack (CVE-2026-45321) — malicious versions removed the same day (5/11)</td></tr><tr><td>June 2026</td><td>Rsbuild support made official · <code>.validator()</code> restored as the canonical name</td></tr><tr><td>September 2026</td><td>Security patch notice for CVE-2026-102989 (9/30)</td></tr><tr><td>October 2026</td><td><code>1.169.0</code> ships, <strong>1.0 stable announced</strong> (10/13, KST)</td></tr></tbody></table>
<p>Three things in the 1.0 announcement stand out.</p>
<ul>
<li><strong>"Finally dropping the RC caveat"</strong> — teams from small projects to Fortune 500 companies (none are named) were already running Start in production during beta and RC, and 1.0 is the formal commitment to those APIs. The team expected a short stretch of polish after RC, but in practice a lot of compiler, streaming, server-boundary, and hydration work landed.</li>
<li><strong>About 5.5x SSR throughput</strong> — maintainers profiled what the server was doing and stripped out work it didn't need to do, reaching roughly 5.5 times the throughput in their own benchmark. It's worth keeping in mind that this is <strong>relative to Start before the optimization work</strong>, not a comparison with other frameworks.</li>
<li><strong>Agents and types</strong> — the argument is that designing the router to be type-safe and strict pays off in the agent era as well. When an agent changes a route parameter or a server function's input, <strong>the types point to the places that no longer agree</strong>. In the same vein, TanStack Intent ships agent skills inside the npm packages themselves.</li>
</ul>
<p>There is also a candid look back at RSC. The team spent a lot of time integrating RSC without changing Start's app model, but on tanstack.com itself, tracking "what ships where" became so complicated that they <strong>took RSC back out</strong>. They point to the fact that removing it did not require rewriting the app as evidence for the opt-in design.</p>
<h3 id="core-concept-where-does-this-code-run">Core Concept: Where Does This Code Run?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#core-concept-where-does-this-code-run"><span class="icon icon-link"></span></a></h3>
<p>There is one rule to learn first when using Start: <strong>all code is isomorphic by default</strong>. Unless you constrain it, it goes into <strong>both</strong> the server bundle and the client bundle.</p>
<p>In particular, <strong>a route <code>loader</code> is not server-only.</strong> It runs on the server for the first request (SSR) and in the browser during subsequent client-side navigation. If you're used to Next.js async Server Components or React Router's server <code>loader</code>, this is the biggest trap.</p>

<p>The official rule is simple: server code can read unprefixed <code>process.env</code>, and client code can only read values carrying the build tool's public prefix (Vite <code>VITE_</code>, Rsbuild <code>PUBLIC_</code>). So the fix for "a secret read in a loader" isn't to add a prefix — it's to <strong>move it into a server function</strong>.</p>
<p>These are the APIs that control where code runs.</p>








































<table><thead><tr><th>API</th><th>Purpose</th><th>Behavior in the other environment</th></tr></thead><tbody><tr><td><code>createServerFn()</code></td><td>RPC, data mutations</td><td>On the client, a network request to the server</td></tr><tr><td><code>createServerOnlyFn(fn)</code></td><td>Server-only utilities</td><td>Throws if called on the client</td></tr><tr><td><code>createClientOnlyFn(fn)</code></td><td>Browser-only utilities</td><td>Throws if called on the server</td></tr><tr><td><code>createIsomorphicFn().server().client()</code></td><td>Different implementation per environment</td><td>The other side's implementation is removed from each bundle</td></tr><tr><td><code>&#x3C;ClientOnly fallback></code></td><td>Components that need browser APIs</td><td>Renders the fallback on the server</td></tr><tr><td><code>useHydrated()</code></td><td>Branch on hydration</td><td><code>false</code> during SSR and the first client render</td></tr></tbody></table>
<p>The <code>createIsomorphicFn</code> example from the 1.0 announcement captures this model well. Getting the current origin differs between the server (the request URL) and the browser (<code>window.location</code>); put the two implementations side by side and Start strips the other side's implementation from each bundle. Calling it in the browser does not send a request to the server.</p>

<p>One more thing: <strong>don't read <code>process.env</code> at module scope.</strong> Besides the risk of the value being inlined into the client bundle, edge runtimes such as Cloudflare Workers inject env <strong>per request</strong>, so at module load time it is <code>undefined</code> even on the server. Read it inside <code>.handler()</code>, middleware <code>.server()</code>, or server-route handlers.</p>

<p>Server functions are safe to import statically from anywhere, but the docs advise <strong>avoiding dynamic <code>import()</code>, which can cause bundler issues</strong>.</p>
<p>There are also defaults worth knowing.</p>
<ul>
<li><strong>CSRF protection</strong> — server functions are same-origin RPC. If there is no <code>src/start.ts</code>, Start installs <code>createCsrfMiddleware()</code> automatically, but <strong>once you create <code>src/start.ts</code> yourself, you have to add this middleware explicitly.</strong> The middleware checks the origin using the <code>Sec-Fetch-Site</code>, <code>Origin</code>, and <code>Referer</code> headers and rejects requests that carry none of them by default, so check ahead of time if you deploy behind a proxy that strips these headers.</li>
<li><strong>Serialization type checks</strong> — TypeScript checks that inputs and return values are serializable (<code>strict</code> by default). <code>FormData</code> (for POST) and <code>Response</code> are allowed.</li>
<li><strong>Cache headers</strong> — you can set <code>Cache-Control</code> with <code>setResponseHeaders</code>, but using <code>public</code> on a response that varies by session or cookie <strong>can replay one user's response to another</strong>, so use <code>private</code> (plus <code>Vary</code>) or <code>no-store</code>.</li>
</ul>

<p>There's a sentence the official docs repeat several times: <strong>a route guard (<code>beforeLoad</code>) is not a data authorization boundary.</strong> Server functions and server routes are <strong>API endpoints that can be called independently</strong> of the screen that uses them, so authorization belongs in the handler or middleware. A redirect in <code>beforeLoad</code> is just UX.</p>
<p>Global middleware that should apply to every request or every server function is registered in <code>createStart</code> in <code>src/start.ts</code>, via the <code>requestMiddleware</code> / <code>functionMiddleware</code> arrays. <code>sendContext</code>, which carries context from client to server, keeps the types in sync but <strong>does not validate at runtime</strong>, so validate it again in the server middleware. Never take trusted values such as the session from <code>sendContext</code>.</p>

<h4 id="7-using-it-with-tanstack-query">7. Using it with TanStack Query<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#7-using-it-with-tanstack-query"><span class="icon icon-link"></span></a></h4>

<h3 id="choosing-a-rendering-mode">Choosing a Rendering Mode<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#choosing-a-rendering-mode"><span class="icon icon-link"></span></a></h3>
<p>Start's most practical advantage is that you choose how to render <strong>per route</strong>.</p>

<p>The <strong>inheritance rule</strong> matters. A child route inherits its parent's setting and can only change it <strong>to something more restrictive</strong> (<code>true</code> → <code>'data-only'</code> → <code>false</code>). If the parent is <code>ssr: false</code>, writing <code>ssr: true</code> on the child has no effect. To change the default itself, use <code>createStart(() => ({ defaultSsr: false }))</code> in <code>src/start.ts</code>. And these settings apply only to <strong>the first request</strong>: on later client-side navigations, <code>beforeLoad</code> and <code>loader</code> run in the browser regardless of the mode.</p>
<h4 id="spa-mode">SPA mode<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#spa-mode"><span class="icon icon-link"></span></a></h4>
<p>No SSR doesn't mean giving up server features. After the build, the root route is prerendered into <code>/_shell.html</code> (the pending component fills the spot where matched routes would render), and server functions and server routes keep working. Other routes can be prerendered too, and the official docs recommend prerendering as much as you can. In exchange, your host needs rewrite rules (a Netlify <code>_redirects</code> example).</p>

<p>If you need slots, render a source created with <code>createCompositeComponent</code> through <code>&#x3C;CompositeComponent src={...}></code> and pass client components in as children. Because the client composes UI produced by the server, the owner of the component tree is still the client-side router — that's where it differs from Next.js.</p>
<p>There are constraints to know as well. RSC uses React's Flight protocol as is, so Start's own serialization isn't available inside Server Components yet (primitives, Dates, and React elements work), and caching Server Components with TanStack Query requires <code>structuralSharing: false</code>.</p>
<p>The post that introduced RSC ("React Server Components Your Way", 2026-04-13) states that Start <strong>intentionally does not support <code>'use server'</code> actions</strong>, citing existing attack vectors and the way they create implicit network boundaries. The same post explains that because Start doesn't parse Flight data coming from the client, recent CVEs that hit other RSC frameworks don't apply — keep in mind that this is TanStack's own assessment, not an independent audit.</p>
<p>The official comparison draws the line explicitly: this feature <strong>should not be presented as production feature parity with Next.js</strong>. If RSC is the center of your app, weigh that first.</p>

<p>On Netlify, <code>@netlify/vite-plugin-tanstack-start</code> handles both the build configuration and local platform emulation. When you build with Rsbuild, client assets go to <code>dist/client</code> and a fetch-style server entry goes to <code>dist/server/index.js</code>.</p>
<p>For environment variables, server code reads unprefixed values from <code>process.env</code>, and only values carrying the build tool's public prefix (Vite <code>VITE_</code>, Rsbuild <code>PUBLIC_</code>) are exposed to the client.</p>
<p>Before deploying, I recommend running through the official <strong>Production Checklist</strong> once. It includes items such as building with a harmless test secret and searching the client output for it, and calling private endpoints <strong>directly</strong> while signed out and as a different account.</p>

<p>There's a catch when replacing <code>useSession</code>: the new library <strong>cannot read existing Start session cookies</strong>. Either use a new cookie name and have users sign in again, or test a migration path that reads the old cookie first.</p>
<p><code>.validator()</code> has a backstory. It was originally called <code>.validator()</code>, was renamed to <code>.inputValidator()</code> in the RC (1.132), and in June 2026 (1.168.25, PR #7566) <code>.validator()</code> became the canonical name again, with <code>.inputValidator()</code> kept around with a deprecation warning until it was removed in 1.169.0. That's why <strong>RC-era tutorial code breaks on 1.0 as is.</strong> On the flip side, this history lets you split the upgrade into steps.</p>
<ol>
<li>On 1.168.25 or later (the last release supporting Vite 7 is 1.168.61), rename <code>.inputValidator()</code> to <code>.validator()</code> first</li>
<li>On the same version, apply changes that work on both versions, such as replacing <code>useSession</code> with a session library and switching <code>set-cookie</code> to <code>setCookie</code>/<code>appendResponseHeader</code></li>
<li>Upgrade to Vite 8 and 1.169.x, then swap the Nitro plugin and go through the behavior-change table below</li>
</ol>
<h4 id="behavior-changes">Behavior changes<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#behavior-changes"><span class="icon icon-link"></span></a></h4>





















































<table><thead><tr><th>Area</th><th>Change</th></tr></thead><tbody><tr><td>Server entry</td><td>A handler returned by <code>createStartHandler(...)</code> now <strong>rethrows</strong> the original error. In a custom entry, catch inside the <code>createServerEntry</code> callback and <code>return handleStartError(error)</code></td></tr><tr><td>Error responses</td><td>Uncaught errors produce a <strong>generic JSON body</strong> with a 400–599 status (500 by default), even if a success status was set earlier</td></tr><tr><td>Server function calls</td><td>Reject with whatever was thrown (including a <code>Response</code> and falsy values such as <code>undefined</code>). Return a <code>Response</code> to resolve with it</td></tr><tr><td>Middleware errors</td><td>Errors thrown by request middleware during a server-function call reach the client with their message, and the status is no longer always 500</td></tr><tr><td>Response helpers</td><td>Helpers <strong>override</strong> the response you return or throw. <code>setResponseStatus(401)</code> followed by a 200 response sends 401</td></tr><tr><td>Cookies</td><td><code>setResponseHeader('set-cookie', cookie)</code> <strong>replaces all</strong> outgoing cookies. <h4 id="coming-from-an-even-older-version-the-vinxi-era">Coming from an even older version (the Vinxi era)<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#coming-from-an-even-older-version-the-vinxi-era"><span class="icon icon-link"></span></a></h4>
<p>If you were on a beta from before the RC, there are two big transitions to get through first. Here is a summary of what the official tracking discussion (GitHub Discussion #2863) lays out.</p>
<p><strong>1.121.0 (June 2025) — Vinxi → Vite plugin</strong></p>

<p>On top of that, <code>registerGlobalMiddleware</code> was removed (today it's <code>createStart</code> in <code>src/start.ts</code>), Nitro was decoupled from the default setup (<code>nitroV2Plugin</code> in the RC, <code>nitro/vite</code> in 1.0), and you now add the React plugin (<code>viteReact()</code>) yourself. If you can't upgrade right away, the discussion suggests pinning versions with <code>npx create-start-app@latest pin-versions</code>.</p>
<p>In short, it's safest to climb one step at a time: <strong>Vinxi era → 1.121 structure → 1.132 names → 1.169 stable.</strong> And since blog posts and tutorials from the RC period are full of <code>.inputValidator()</code>, the Nitro v2 plugin, and Vite 7 examples, compare them against the latest docs before following them.</p>
<h3 id="migration--nextjs-app-router--start">Migration ② Next.js App Router → Start<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#migration--nextjs-app-router--start"><span class="icon icon-link"></span></a></h3>
<p>For teams moving from Next.js, the official guide provides <strong>a before/after example that implements the same article site in both frameworks</strong> (<code>examples/react/start-next-migration</code>), plus Playwright tests that run unchanged against both apps. They check public URLs, server-rendered metadata, query filtering, redirects, 404s, the sitemap, sign-in errors, session persistence, private response caching, mutations, and server-side rejection after sign-out. "Pin the behavior down as a contract and translate only the framework boundaries" is the heart of this guide.</p>
<p>There's one premise to know up front: <strong>Start has no <code>'use server'</code>.</strong> Every Server Action has to be rewritten with <code>createServerFn</code>, and the <code>'use client'</code> directive isn't needed either, so remove it. The <code>@tanstack/react-start</code> package also ships an agent skill for migrating from Next.js (<code>skills/lifecycle/migrate-from-nextjs/SKILL.md</code>), which is useful reference material when you hand the work to an agent. That skill, however, removes Next.js early in its steps, so running both apps side by side as in the official guide below is the safer approach.</p>
<h4 id="step-0-take-inventory-before-changing-anything">Step 0: Take inventory before changing anything<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#step-0-take-inventory-before-changing-anything"><span class="icon icon-link"></span></a></h4>
<ul>
<li><strong>Observable behavior</strong> — dynamic paths, query parameters, redirects, trailing slashes, locale prefixes, response status, title/description/canonical/robots, and sitemap membership</li>
<li><strong>Next.js-specific code</strong> — <code>next/*</code> imports, <code>'use server'</code>, server-only modules, metadata exports, <code>generateStaticParams</code>, <code>revalidatePath</code>/<code>revalidateTag</code>, cache directives, Proxy/middleware, and image/font configuration</li>
</ul>
<p>The guide warns that a route can render successfully and still have lost authentication, cache invalidation, or an important search URL.</p>
<h4 id="step-1-stand-start-up-next-to-the-existing-app">Step 1: Stand Start up next to the existing app<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#step-1-stand-start-up-next-to-the-existing-app"><span class="icon icon-link"></span></a></h4>
<p>Keep the Next.js app <strong>runnable</strong> until the migrated routes pass their checks. You can test Start without removing Next.js or its configuration.</p>

The guide itself says not to treat <code>createServerFn</code> as a drop-in replacement for the React form Action protocol.</p>
<h4 id="step-4-auth-metadata-and-caching">Step 4: Auth, metadata, and caching<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#step-4-auth-metadata-and-caching"><span class="icon icon-link"></span></a></h4>
<ul>
<li><strong>Auth</strong> — Start doesn't provide a session API. The official example keeps <code>iron-session</code> and replaces Next.js <code>cookies()</code> with a small <code>getCookie</code>/<code>setCookie</code> adapter. If sessions must survive cutover or rollback, verify cookie names, domains, paths, signing/encryption formats, expiration, key rotation, and logout in both deployments.</li>
<li><strong>Caching private pages</strong> — make sure personalized HTML never reaches another user by checking <code>Cache-Control: private, no-store</code>, and verify the final response through the CDN. Don't prerender or publicly cache pages that contain private data.</li>
<li><strong>Metadata</strong> — compare the HTML response before JS runs and the head after client navigation. Migrate the sitemap, robots.txt, icons, manifests, and social images explicitly, and return real 404s for missing content.</li>
<li><strong>Caching</strong> — list browser data, Router loaders, Query, server data, generated pages, and CDN responses <strong>separately</strong>, and define what populates and what invalidates each. Next.js cache directives and revalidation don't carry over automatically.</li>
</ul>
<h4 id="step-5-cut-over-with-a-rollback-path-in-hand">Step 5: Cut over with a rollback path in hand<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#step-5-cut-over-with-a-rollback-path-in-hand"><span class="icon icon-link"></span></a></h4>
<ol>
<li>Build both apps and run the contract tests against a staging deployment of Start, including real data, authenticated sessions, and the CDN.</li>
<li>During the transition, keep the database schema compatible with both versions and separate destructive schema changes from the framework cutover.</li>
<li>Preserve the public origin and paths as much as possible, and when paths must change, update redirects, internal links, canonicals, and sitemaps together.</li>
<li>Record the previous deployment and routing configuration, and know how to route traffic back — and what happens to sessions and writes when you do.</li>
<li>After cutover, monitor error rates, login and mutation failures, response status, indexing signals, and conversion events against the baseline.</li>
</ol>
<p>Remove Next.js and its leftover configuration only <strong>after</strong> all of this behavior and the rollback plan are verified. Compared with my earlier <a href="/en/posts/2024-11-23-nextjs-v15-migration/">Next.js 15 migration</a> post, the biggest difference is that, unlike a version bump within the same framework, this work is <strong>"translating an execution model," not "swapping APIs."</strong></p>
<h4 id="coming-from-remix--react-router-7">Coming from Remix / React Router 7<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#coming-from-remix--react-router-7"><span class="icon icon-link"></span></a></h4>
<p>A Start-specific guide is still "coming soon." In the meantime, the TanStack Router docs' <strong>"Migrate from React Router v7"</strong> covers the router-level mapping and recommends Start when you need full-stack features.</p>

<p>When moving to Start, the biggest conceptual difference is the <strong>loader's execution location</strong> mentioned earlier. A React Router Framework Mode <code>loader</code> runs on the server, but Start's <code>loader</code> is isomorphic, so server-only code has to move into server functions. On top of that, it's enough as a starting point to move <code>action</code> to a POST server function, resource routes to server routes, and <code>meta</code> to <code>head</code> (these three are my own mapping, not an official one).</p>
<h3 id="advantages">Advantages<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#advantages"><span class="icon icon-link"></span></a></h3>
<ol>
<li><strong>End-to-end type safety</strong> — links, path parameters, validated search params, loader data, route context, and server function inputs and outputs are connected in a single type graph. When you change something, your editor (and your agent) immediately finds what it affects.</li>
<li><strong>A familiar app model</strong> — the default is SSR + hydration, so you can write it like the React apps you've been building, without <code>'use client'</code> boundaries or a server/client component split. You get server functions and SSR without RSC.</li>
<li><strong>Explicit execution boundaries</strong> — <code>createServerFn</code>, <code>createServerOnlyFn</code>, <code>createIsomorphicFn</code>, and Import Protection make "where does this code run" visible in the code itself.</li>
<li><strong>Per-route rendering control</strong> — Full SSR, data-only, client-only, SPA mode, and prerendering can be mixed within one app.</li>
<li><strong>Middleware that spans client and server</strong> — server function middleware runs on both the client and the server around the RPC, and context flows through with its types.</li>
<li><strong>Freedom of build tool and hosting</strong> — both Vite and Rsbuild are supported, and Nitro plus partner plugins deploy to Cloudflare, Netlify, Railway, Vercel, Node, Bun, and more.</li>
<li><strong>Fits the TanStack ecosystem</strong> — it meshes with the TanStack libraries you may already use, such as Query (data caching), Form, and Table, under the same design philosophy.</li>
</ol>
<h3 id="drawbacks-and-caveats">Drawbacks and Caveats<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#drawbacks-and-caveats"><span class="icon icon-link"></span></a></h3>
<ol>
<li><strong>RSC is experimental.</strong> If your app is designed around Server Components, Next.js is more mature there.</li>
<li><strong>No built-in image or font optimization.</strong> You have to pick and configure equivalents of <code>next/image</code> and <code>next/font</code> yourself.</li>
<li><strong>The isomorphic-loader trap</strong> — putting secrets or database code in a loader can break on client navigation or drag server code into the client bundle. Teams used to thinking "loader = server" need a review rule for this.</li>
<li><strong>Server functions are public endpoints.</strong> A <code>beforeLoad</code> guard alone doesn't protect data; every server function that touches private data needs authorization. Once you create <code>src/start.ts</code>, you also have to register the CSRF middleware yourself.</li>
<li><strong>There's no session API.</strong> <code>useSession</code> was removed in 1.0, so you need a library such as iron-session or a managed service such as Clerk or WorkOS.</li>
<li><strong>A fast release cadence</strong> — according to npm, the 1.168 line alone shipped 61 patches between May 15 and October 10. Commit your lockfile and make a habit of reading the changelog when you upgrade.</li>
<li><strong>Gaps in the docs</strong> — the Remix 2 / React Router 7 migration guide is "coming soon," and the Nitro integration docs still carry an "under active development" warning.</li>
<li><strong>Security history</strong> — CVE-2026-102989 (GHSA-qx66-fv34-fjm8, CVSS 9.3) was a reflected XSS where an unauthenticated, crafted server-function URL could return attacker-controlled HTML from the application's origin. The affected range of <code>@tanstack/react-start</code> runs from 1.143.12 up to (but not including) 1.168.60, and updating a local install doesn't patch an app that is already deployed, so you need to <strong>rebuild and redeploy</strong>. It wasn't a framework design issue, but on May 11, 2026 a supply-chain attack exploiting a GitHub Actions misconfiguration (CVE-2026-45321) published 84 credential-stealing malicious versions across 42 packages — including <code>@tanstack/react-start</code> 1.167.68 and 1.167.71 — within a few minutes. All of them were deprecated and removed the same day, but if you installed dependencies that day, follow the official postmortem to check for those versions and rotate credentials.</li>
<li><strong>No explicit versioning policy yet.</strong> The 1.0 announcement doesn't spell out how future breaking changes will be handled (major cadence, support windows). That contrasts with <a href="/en/posts/2026-09-19-react-router-v8/">React Router v8</a>, which committed to "one major per year." Given the API's track record of moving — <code>.validator()</code> was renamed twice during the RC — budget time for reading the changelog on every upgrade for now.</li>
</ol>
<h3 id="real-world-adoption-and-counter-examples">Real-World Adoption and Counter-Examples<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#real-world-adoption-and-counter-examples"><span class="icon icon-link"></span></a></h3>
<p>Docs and announcements are, in the end, the maker's side of the story. For balance, I also looked up records from teams that actually made the move. Versions and timing vary, and none of these are independent benchmarks, so read them with that in mind.</p>



































<table><thead><tr><th>Case</th><th>When · version</th><th>What they did</th><th>Results · lessons</th></tr></thead><tbody><tr><td><strong>Inngest</strong></td><td>2026-01 · RC</td><td>Moved a Next.js dashboard to Start (also prototyped React Router v7 and Deno Fresh)</td><td>First local dev loads went from 10–12s to 2–3s, with one engineer and AI help over a couple of weeks. In exchange, mis-bundled server/client code was hard to trace, dev and the built app behaved differently, and an integration-flow issue once forced an instant rollback</td></tr><tr><td><strong>Tightknit</strong></td><td>2026-04</td><td>Moved a Next.js app to Start on Cloudflare Workers</td><td>Avoided vendor lock-in and fit their existing Cloudflare ecosystem. The cost: losing <code>vercel/og</code> meant building a separate worker on <code>workers-og</code> (which they themselves called a hack), and learning a new caching model</td></tr><tr><td><strong>LogRocket experiment</strong></td><td>2026-06 · Start 1.168.26 vs Next.js 16.2.9</td><td>Built the same dashboard twice with RSC</td><td>Start led on client JS, 116KB vs 193KB (gzip), and build time, 1.3s vs 5.1s, but setup took 8 min vs 3 min and the code was 345 vs 290 lines. <p>Three common threads stand out.</p>
<ul>
<li><strong>There were reports favoring Start on dev-server speed and bundle size</strong> (Inngest, LogRocket), and the price was setup cost and debugging the server/client boundary.</li>
<li><strong>What Next.js gives you by default</strong> (image optimization, OG image generation, metadata conventions) has to be filled in yourself — this repeats across cases. The LLM Gateway case shows less that "Start is slow" and more what happens when you leave that gap unfilled.</li>
<li><strong>If RSC is the center of your app, Next.js still; if your app is highly interactive, Start with RSC off</strong> — the LogRocket experiment and the official comparison land on the same conclusion.</li>
</ul>
<p>The 1.0 announcement also names adopters. Lovable chose Start as the foundation for newly generated apps, Netlify uses it as the default framework for its AI app builder that more than a million people have used, and Unkey adopted Start, Router, and Query in its open-source portal. Keep in mind that all of them are TanStack partners.</p>
<h3 id="compared-with-nextjs-and-react-router">Compared with Next.js and React Router<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#compared-with-nextjs-and-react-router"><span class="icon icon-link"></span></a></h3>
<p>Here is a summary of the official comparison (as of 2026-09-11, against the Next.js 16.3 App Router and React Router 8.3 Framework Mode). Keep in mind that TanStack wrote it, but it's a fairly restrained document: it doesn't crown a performance winner, and it spells out where Next.js has the advantage. By contrast, the overview page's line about offering "the same capability as Next.js, Remix, etc., with even more features and a more powerful developer experience" is a vendor claim with no evidence attached.</p>



























































<table><thead><tr><th>Aspect</th><th>TanStack Start</th><th>Next.js App Router</th><th>React Router Framework Mode</th></tr></thead><tbody><tr><td>Server rendering</td><td>SSR + hydration by default</td><td>Server and Client Components produce the initial HTML</td><td>Configurable SSR</td></tr><tr><td>Rendering control</td><td>Per-route full / data-only / off</td><td><code>use client</code> boundaries (initial SSR still happens)</td><td>Global SSR setting + route <code>clientLoader</code></td></tr><tr><td>RSC</td><td>Experimental, opt-in</td><td>The core component model</td><td>Unstable</td></tr><tr><td>Server calls · mutations</td><td>Typed server functions (GET/POST)</td><td>Server Actions</td><td>Route actions · fetchers</td></tr><tr><td>Middleware</td><td>Request + server function (client/server)</td><td>Proxy</td><td>Server and client route middleware</td></tr><tr><td>API endpoints</td><td>Server routes</td><td>Route Handlers</td><td>Resource routes</td></tr><tr><td>Build</td><td>Vite or Rsbuild</td><td>Turbopack</td><td>Framework tooling (Vite plugin)</td></tr><tr><td>Images · fonts</td><td>Your choice</td><td>Built-in <code>next/image</code> · <code>next/font</code></td><td>Your choice</td></tr></tbody></table>
<p>The official selection criteria go like this.</p>
<ul>
<li><strong>TanStack Start</strong> — when you want typed route context and URL state, explicit loaders and server functions, and per-route rendering control</li>
<li><strong>Next.js</strong> — when you need the Server Component model and the built-in image, font, metadata, and form facilities, or when your team's experience and existing integrations are already built around Next.js</li>
<li><strong>React Router Framework Mode</strong> — when loader/action/fetcher-centric, form-driven workflows and progressive enhancement matter</li>
</ul>
<p>And here's the line I personally agreed with most: <strong>you don't need to rewrite a healthy Next.js app just because the routing model is different.</strong> Instead, the official recommendation is to build <strong>one representative route</strong> in Start — including real data loading, search param validation, a mutation, handling unauthorized access, and deployment — and judge by whether it becomes easier to maintain.</p>
<h3 id="wrapping-up">Wrapping Up<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#wrapping-up"><span class="icon icon-link"></span></a></h3>
<p>In one sentence, TanStack Start 1.0 is <strong>"the release where building the router properly turned into a full-stack framework, and the team now commits to its APIs."</strong> It's less a feature launch than a milestone that puts a stability guarantee on a design already running in production.</p>
<p>If Next.js treats "the server as the default and the client as the exception," Start does the opposite: <strong>"the familiar app as the default, and the server made explicit."</strong> Which one is right depends on your app, but for teams already comfortable with type-safe routing and TanStack Query, it clearly looks like the full-stack option with the lowest barrier to entry.</p>
<p><strong>Adoption checklist:</strong></p>
<ul>
<li>✅ Prepare Vite 8+ (or Rsbuild 2) and Node 22.12+</li>
<li>✅ <code>@tanstack/react-start</code> 1.169.x, and confirm the installed <code>@tanstack/start-server-core</code> is 1.169.39 or later (CVE-2026-102989)</li>
<li>✅ No secrets or database code in loaders — move them into server functions if there are</li>
<li>✅ <code>authMiddleware</code> (or in-handler authorization) on every server function that touches private data</li>
<li>✅ If you created <code>src/start.ts</code>, register <code>createCsrfMiddleware()</code> explicitly</li>
<li>✅ Create the <code>QueryClient</code> inside <code>getRouter</code></li>
<li>✅ <code>Cache-Control: private</code> (or <code>no-store</code>) on personalized responses</li>
<li>✅ (RC users) <code>.inputValidator</code> → <code>.validator</code>, replace <code>useSession</code>, swap the Nitro plugin, review <code>set-cookie</code> handling</li>
<li>✅ (Moving from Next.js) <code>'use server'</code> → <code>createServerFn</code>, then behavior inventory → representative-route PoC → contract tests → cutover with a rollback path</li>
<li>✅ (Beware of old tutorials) if you see <code>.inputValidator()</code>, <code>nitroV2Plugin</code>, <code>createServerFileRoute</code>, or <code>app.config.ts</code>, it's pre-1.0 code — compare it against the latest docs</li>
<li>✅ If you installed dependencies on 2026-05-11, check for the supply-chain attack's malicious versions (GHSA-g7cv-rxg3-hmpx)</li>
</ul>
