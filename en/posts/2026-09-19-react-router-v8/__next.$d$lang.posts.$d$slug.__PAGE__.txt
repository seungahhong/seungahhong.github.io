1b:T1063e,<h2 id="react-router-v8-the-boring-major-and-the-v7--v8-upgrade-guide">React Router v8: The "Boring Major" and the v7 → v8 Upgrade Guide<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#react-router-v8-the-boring-major-and-the-v7--v8-upgrade-guide"><span class="icon icon-link"></span></a></h2>
<h3 id="️-tldr">✍️ TL;DR<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#️-tldr"><span class="icon icon-link"></span></a></h3>
<blockquote>
<p><strong>React Router v8 isn't a release that ships new features — it locks in, as defaults, the changes v7 already exposed behind future flags, and raises the minimum versions.</strong> If you turned every flag on while on v7, the upgrade is essentially one line: <code>pnpm i react-router@latest</code>.</p>
</blockquote>
<h4 id="summary">Summary<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#summary"><span class="icon icon-link"></span></a></h4>
<ul>
<li><strong>Released</strong>: June 17, 2026, announced on the Remix blog. The team itself calls it their most "boring" major yet.</li>
<li><strong>Minimum versions</strong>: Node <strong>22.22.0+</strong> · React <strong>19.2.7+</strong> · Vite <strong>7+</strong> (Framework mode). The package is now <strong>ESM-only</strong>, and tsconfig target/lib moved to ES2022.</li>
<li><strong>Five future flags became defaults</strong>: <code>v8_middleware</code> · <code>v8_splitRouteModules</code> (moved to top-level <code>splitRouteModules</code>) · <code>v8_viteEnvironmentApi</code> · <code>v8_passThroughRequests</code> · <code>v8_trailingSlashAwareDataRequests</code></li>
<li><strong>Four removals</strong>: the <code>react-router-dom</code> package · <code>data</code> in <code>meta</code>/<code>matches</code> (→ <code>loaderData</code>) · the Cloudflare dev proxy (→ <code>@cloudflare/vite-plugin</code>) · the <code>useRequestContextDomainName</code> option in <code>@react-router/architect</code></li>
<li><strong>Upgrade order</strong>: latest v7 → turn flags on one at a time and commit → clean up removed APIs → install v8. The key point is that <strong>every change can be made on v7 first.</strong></li>
<li><strong>What can break quietly</strong>: server/CDN/cache rules that handle <code>.data</code> URLs directly (<code>/_root.data</code> → <code>/_.data</code>), loaders comparing paths via <code>request.url</code>, and Vite configs relying on <code>isSsrBuild</code>.</li>
<li><strong>Going forward</strong>: a <strong>yearly major</strong> cadence. v6 and Remix v2 are <strong>EOL</strong> (no more security updates); v7 keeps getting security fixes. v9 (expected mid-2027) will require <strong>Node 24+</strong>, and RSC support is still unstable.</li>
</ul>

























<table><thead><tr><th>Item</th><th>Details</th></tr></thead><tbody><tr><td><strong>Runtime baseline</strong></td><td>Node 22.22.0+ · React 19.2.7+ · Vite 7+ · ESM-only</td></tr><tr><td><strong>New defaults</strong></td><td>Middleware · split route modules · Vite Environment API · pass-through requests · trailing-slash awareness</td></tr><tr><td><strong>Removed</strong></td><td><code>react-router-dom</code> · <code>data</code> param · Cloudflare dev proxy · architect option</td></tr><tr><td><strong>Support policy</strong></td><td>v6 &#x26; Remix v2 EOL · v7 security patches continue · one major per year</td></tr></tbody></table>
<p>The details follow below.</p>

<h3 id="why-a-boring-major">Why a "Boring Major"<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#why-a-boring-major"><span class="icon icon-link"></span></a></h3>
<p>React Router has changed shape many times over its 12 years, and long-time users remember "major = major surgery." Back in <a href="/en/posts/2022-03-12-react-router-v6/">v6</a>, <code>Switch</code> became <code>Routes</code> and <code>useHistory</code> became <code>useNavigate</code>.</p>
<p>Since v7, the team's strategy has been <strong>future flags</strong>. Behavior that will change in the next major ships behind a flag in the current one, and you turn each on whenever you're ready. On release day the flags simply become defaults, so <strong>there's almost nothing left to fix the day you upgrade.</strong></p>
<p>As the announcement's author (Brooks Lybrand) puts it, the only downside is that it's hard to hype up in a blog post. And the team is institutionalizing that boredom: <strong>from now on, there will be one major per year.</strong></p>
<h3 id="what-piled-up-since-v7">What Piled Up Since v7<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#what-piled-up-since-v7"><span class="icon icon-link"></span></a></h3>
<p>The headline of v7 was <strong>Framework mode</strong>: a single Vite plugin that adds a type-safe Route Module API, code splitting, SPA/SSR/static rendering, and data loading and mutations. At the same time it still supports a plain client-side router (Declarative mode) and Data mode for building your own framework. The commitment to <strong>keep all three modes</strong> carries over into v8.</p>
<p>Here's what landed across the 40+ releases since v7 (per the announcement; not exhaustive).</p>





























<table><thead><tr><th>Area</th><th>Additions</th></tr></thead><tbody><tr><td><strong>Data/server</strong></td><td>Middleware &#x26; better context · Pass-through Requests · Call-site revalidation · <code>fetcher.reset</code></td></tr><tr><td><strong>Bundling/build</strong></td><td>Split Route Modules · Vite Environment API support · object-based <code>route.lazy</code> · configurable Lazy Route Discovery</td></tr><tr><td><strong>Rendering</strong></td><td>SPA mode improvements · pre-rendering improvements · (unstable) RSC support</td></tr><tr><td><strong>APIs</strong></td><td>Type-safe <code>href</code> · <code>useRoute</code>/<code>useRouterState</code> (unstable) · <code>useTransitions</code> router prop · RouterProvider <code>onError</code> · Link masking</td></tr><tr><td><strong>Operations</strong></td><td>Instrumentation API · Subresource integrity · many performance improvements · Agent Skills</td></tr></tbody></table>
<p>That's why v8 looks light on "new" features. The features already shipped in v7 minors; v8 is where some of them get <strong>locked in as defaults</strong>.</p>
<h3 id="whats-changing">What's Changing<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#whats-changing"><span class="icon icon-link"></span></a></h3>
<h4 id="1-minimum-supported-versions">1. Minimum supported versions<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#1-minimum-supported-versions"><span class="icon icon-link"></span></a></h4>

























<table><thead><tr><th>Target</th><th>Minimum</th><th>Notes</th></tr></thead><tbody><tr><td><strong>Node</strong></td><td>22.22.0+</td><td>Only the latest minor line of Maintenance LTS is supported</td></tr><tr><td><strong>React</strong></td><td>19.2.7+</td><td>Both <code>react</code> and <code>react-dom</code></td></tr><tr><td><strong>Vite</strong></td><td>7+</td><td>Framework mode only. Check that custom Vite plugins are Vite 7 compatible</td></tr></tbody></table>
<p>Two more come with it:</p>
<ul>
<li><strong>ESM-only publishing</strong> — the CommonJS build is gone.</li>
<li><strong>tsconfig target/lib bumped to ES2022</strong> across the board.</li>
</ul>
<p>The Node support policy is now explicit too: <strong>all versions of Active LTS</strong>, and <strong>only the latest minor line of Maintenance LTS</strong>. As of the announcement:</p>
<ul>
<li>Node 24 is Active LTS → all 24.x supported</li>
<li>Node 22 is Maintenance LTS → <strong>only 22.22.x</strong> supported</li>
<li>If Node 22.23.x ships, React Router raises its minimum to 22.23.x in a <strong>minor release</strong></li>
<li>When Node 22 hits EOL, support is dropped in a <strong>major release</strong></li>
</ul>
<p>The goal is to quickly adopt Node versions that carry security patches as the baseline. Put differently, teams on Node 22 <strong>may need to bump Node even for a React Router minor update</strong>, so it's safer not to leave the Node version loose in CI and deploy images.</p>
<h4 id="2-future-flags-that-became-defaults">2. Future flags that became defaults<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#2-future-flags-that-became-defaults"><span class="icon icon-link"></span></a></h4>
<p>Five v8 future flags from v7 are removed, and their behavior is now the default.</p>



































<table><thead><tr><th>Flag</th><th>Status in v8</th><th>Modes</th></tr></thead><tbody><tr><td><code>future.v8_middleware</code></td><td>Default</td><td>Framework · Data</td></tr><tr><td><code>future.v8_splitRouteModules</code></td><td>Moved to top-level <code>splitRouteModules</code>, on by default</td><td>Framework</td></tr><tr><td><code>future.v8_viteEnvironmentApi</code></td><td>Default</td><td>Framework</td></tr><tr><td><code>future.v8_passThroughRequests</code></td><td>Default</td><td>Framework</td></tr><tr><td><code>future.v8_trailingSlashAwareDataRequests</code></td><td>Default</td><td>Framework</td></tr></tbody></table>
<h4 id="3-removed-apis">3. Removed APIs<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#3-removed-apis"><span class="icon icon-link"></span></a></h4>
<ul>
<li><strong>The <code>react-router-dom</code> package</strong> — a mirror of <code>react-router</code> kept around to smooth the v6 → v7 upgrade. Use <code>react-router</code> and <code>react-router/dom</code>.</li>
<li><strong>The <code>data</code> parameter in <code>meta</code> APIs</strong> — replaced by <code>loaderData</code>.</li>
<li><strong>The Cloudflare dev proxy</strong> (<code>@react-router/dev/vite/cloudflare</code>) — replaced by Cloudflare's official <code>@cloudflare/vite-plugin</code>.</li>
<li><strong>The <code>useRequestContextDomainName</code> option in <code>@react-router/architect</code></strong> — its behavior is now the default, so the option itself is gone.</li>
</ul>
<h3 id="the-v7--v8-upgrade-guide">The v7 → v8 Upgrade Guide<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#the-v7--v8-upgrade-guide"><span class="icon icon-link"></span></a></h3>
<p>The official guide's main advice: <strong>don't do it all at once — commit after each step.</strong> Most flags can be adopted in any order; exceptions are noted below.</p>
<h4 id="step-0-minimum-versions-first">Step 0: Minimum versions first<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#step-0-minimum-versions-first"><span class="icon icon-link"></span></a></h4>
<p>Align the runtime <strong>before</strong> touching React Router.</p>
<ul>
<li><code>node@22.22+</code></li>
<li><code>react@19.2.7+</code> / <code>react-dom@19.2.7+</code></li>
<li>In Framework mode, <code>vite@7+</code> — and make sure custom Vite plugins and config work with Vite 7</li>
</ul>
<h4 id="step-1-update-to-the-latest-v7">Step 1: Update to the latest v7<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#step-1-update-to-the-latest-v7"><span class="icon icon-link"></span></a></h4>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="bash" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="bash" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#702C00;--shiki-dark:#FFB757">npm</span><span style="--shiki-light:#032563;--shiki-dark:#ADDCFF"> install</span><span style="--shiki-light:#032563;--shiki-dark:#ADDCFF"> react-router@7</span><span style="--shiki-light:#032563;--shiki-dark:#ADDCFF"> @react-router/{dev,node,etc.}@7</span></span></code></pre></figure>
<h4 id="step-2-turn-on-future-flags-one-at-a-time">Step 2: Turn on future flags one at a time<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#step-2-turn-on-future-flags-one-at-a-time"><span class="icon icon-link"></span></a></h4>
<p>In Framework mode, flags go in <code>react-router.config.ts</code>; in Data mode, in the <code>createBrowserRouter</code> options.</p>

<ul>
<li><strong>Minimum version</strong>: <code>node@24+</code> — you can move to it while still on v8.</li>
<li><strong>Future flags</strong>: none yet</li>

<p>What it does have are three <strong>unstable flags</strong>, not recommended for production.</p>

<p>Some caveats: standalone APIs like <code>matchRoutes</code>, <code>matchPath</code>, and <code>useMatch</code> <strong>still use the legacy matcher</strong>, and case-sensitive routes aren't supported with this flag yet. If your app has overlapping route patterns, it's worth tidying them up before this flag stabilizes.</p>
<h3 id="react-router-going-forward-and-remix">React Router Going Forward, and Remix<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#react-router-going-forward-and-remix"><span class="icon icon-link"></span></a></h3>
<ul>
<li><strong>One major per year</strong> — making major versions regular, predictable, and therefore boring.</li>
<li><strong>End of life</strong> — with v8, <strong>React Router v6 and Remix v2 are EOL</strong> and no longer receive security updates. v7 continues to get security updates. If you're still on v6, now is the time to move to v7.</li>
<li><strong>Server Components / Server Actions</strong> — work is in progress but still unstable while the APIs settle. It's an opt-in architecture, and the team plans to <strong>stabilize it in a minor version.</strong></li>
<li><strong>Open Governance</strong> — development priorities continue to come from community Proposals.</li>
<li><strong>Design goals</strong> — Less is More · Routing and Data Focused · Simple Migration Paths · Lowest Common Mode</li>
</ul>
<p>The relationship with Remix is clearer now too. Remix v0–v2 was effectively a <strong>feature branch</strong> of React Router, and its matured ideas and APIs were merged back into React Router. That frees Remix to go its own way as a <strong>"truly full-stack, zero-dependency JavaScript web framework"</strong> (the Remix 3 beta).</p>
<p>The team's answer to "which should I use?" is simple: <strong>React Router if you need something battle-tested, Remix 3 if new approaches appeal to you.</strong></p>
<h3 id="wrapping-up">Wrapping Up<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#wrapping-up"><span class="icon icon-link"></span></a></h3>
<p>In one sentence, v8 is <strong>"a release that turns what you could already do on v7 into what you now must do."</strong> The feature list shipped across v7 minors; v8 just raised the defaults and the floor (the minimum versions).</p>
<p>So the upgrade's difficulty depends on <strong>how many flags you turned on in v7.</strong> All of them, and it's one line; none of them, and you walk steps 2–3 of this post on top of v7. Either way, installing v8 should be the last step.</p>
<p><strong>Upgrade checklist:</strong></p>
<ul>
<li>✅ Node 22.22+ · React/React DOM 19.2.7+ · (Framework) Vite 7+ — including <code>.nvmrc</code>, CI, and deploy images</li>
<li>✅ Update to the latest v7</li>
<li>✅ <code>v8_middleware</code> — <code>getLoadContext</code> for custom servers, <code>Future</code> type augmentation in Data mode</li>
<li>✅ <code>v8_splitRouteModules</code> — top-level <code>splitRouteModules</code> in v8</li>
<li>✅ <code>v8_viteEnvironmentApi</code> — move <code>isSsrBuild</code> branches to <code>environments.ssr</code></li>
<li>✅ <code>v8_passThroughRequests</code> — replace <code>new URL(request.url)</code> path checks with the <code>url</code> arg</li>
<li>✅ <code>v8_trailingSlashAwareDataRequests</code> — CDN/cache/rewrite rules: <code>/_root.data</code> → <code>/_.data</code></li>
<li>✅ <code>data</code> → <code>loaderData</code> in <code>meta</code>/<code>matches</code>/<code>useMatches()</code></li>
<li>✅ Remove <code>react-router-dom</code>; import from <code>react-router</code> / <code>react-router/dom</code></li>
<li>✅ Cloudflare dev proxy → <code>@cloudflare/vite-plugin</code>; clean up the architect option</li>
<li>✅ Finally, install <code>react-router@latest</code></li>
<li>✅ (Optional) Evaluate Node 24 ahead of v9</li>
</ul>
