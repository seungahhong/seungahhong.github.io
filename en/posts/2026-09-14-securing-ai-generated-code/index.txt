1e:T51e8,<h2 id="1-what-is-this-post-about">1. What Is This Post About?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#1-what-is-this-post-about"><span class="icon icon-link"></span></a></h2>
<p>Notes on <a href="https://www.youtube.com/watch?v=X0UI0O8YzJM">How Developers Secure AI-Generated Code: 5 Security Best Practices</a>, a talk by IBM security architect Jeff Crume on the IBM Technology channel. A Korean-subtitled version is <a href="https://www.youtube.com/watch?v=xdtHydnLmcU">here</a>.</p>
<p>It runs eleven minutes, and the argument collapses into one sentence.</p>
<blockquote>
<p>AI changed <strong>how fast code gets written.</strong> It did not change <strong>how fast code gets verified.</strong> The only way to close that gap is to move verification left.</p>
</blockquote>
<p>That sounds familiar — shift-left is a decade-old phrase. What this talk actually sharpens is <strong>why it stopped being optional now.</strong> After-the-fact security review was designed around an assumption: <strong>the volume of code a human can produce.</strong> Break the assumption and the practice breaks with it.</p>
<p>If the <a href="/en/posts/2026-09-13-writing-specs-for-agents/">previous post</a> was about <strong>what to tell an agent to do,</strong> this one is the other side of it — <strong>what to catch what the agent produced with.</strong></p>
<hr>
<h2 id="2-why-security-review-at-the-end-stopped-working">2. Why "Security Review at the End" Stopped Working<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#2-why-security-review-at-the-end-stopped-working"><span class="icon icon-link"></span></a></h2>
<p>In a traditional pipeline, security sat on the right edge.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">plan → design → build → test → [security review] → ship</span></span></code></pre></figure>
<p>That placement worked for a simple reason: <strong>development was slow.</strong> A sprint produced less code than the security team could absorb, so one pass at the end was enough.</p>
<p>AI-assisted development multiplies exactly one term in that equation.</p>

























<table><thead><tr><th></th><th>When humans wrote it</th><th>Now that AI writes it</th></tr></thead><tbody><tr><td><strong>Code produced</strong></td><td>hundreds to thousands of lines per sprint</td><td>thousands in a day</td></tr><tr><td><strong>Review capacity</strong></td><td>same</td><td><strong>same</strong></td></tr><tr><td><strong>Security checkpoints</strong></td><td>once, before release</td><td>once, before release</td></tr></tbody></table>
<p>If production goes up 10x and verification doesn't, the gate on the right becomes either <strong>a bottleneck or a formality.</strong> A bottleneck gets routed around; a formality catches nothing. Either way the outcome is identical.</p>
<p>Layered on top of that is the cost curve. The later a defect is found, the more expensive it is to fix — an old observation, and the original case for shift-left. Caught while coding, it ends inside the editor. Caught in production, it's an incident.</p>
<blockquote>
<p>The point is not that <strong>AI-generated code is uniquely dangerous.</strong> <strong>Unreviewed code is dangerous</strong>, and AI has simply made unreviewed code extremely easy to produce.</p>
</blockquote>
<hr>
<h2 id="3-principle-1--verify-outcomes-not-the-generation-process">3. Principle 1 — Verify Outcomes, Not the Generation Process<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#3-principle-1--verify-outcomes-not-the-generation-process"><span class="icon icon-link"></span></a></h2>
<p>The first principle is the least intuitive: <strong>stop trying to control "how the AI wrote it."</strong></p>
<p>Tuning prompts, swapping models, wedging "write it securely" into the system prompt — these are all bets placed on the <strong>generation process.</strong> They can shift the odds, but they <strong>cannot guarantee anything.</strong> The same prompt may emit different code tomorrow, and a model update can change it quietly.</p>
<p>So the thing to hold onto is the artifact.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">❌ "this model writes safe code" → trust</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">✅ "I confirmed this code is safe" → verification</span></span></code></pre></figure>
<p>One misconception deserves its own line:</p>
<blockquote>
<p><strong>Tests passing ≠ safe</strong></p>
</blockquote>
<p>Tests check <strong>intended behavior.</strong> Security defects are mostly <strong>unintended behavior.</strong> Code vulnerable to SQL injection runs perfectly on well-formed input. An endpoint missing an authorization check returns a clean 200 for a request that happens to be authorized. A green functional suite says nothing at all about either.</p>
<p>The axis the talk emphasizes is <strong>behavior and privileges in the real runtime environment.</strong> Working locally and running with real credentials, real network boundaries, and real data-access rights are different claims.</p>
<hr>
<h2 id="4-principle-2--pull-the-checks-into-the-editor">4. Principle 2 — Pull the Checks Into the Editor<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#4-principle-2--pull-the-checks-into-the-editor"><span class="icon icon-link"></span></a></h2>
<p>The second principle is the body of shift-left: make security checks <strong>feedback while editing</strong>, not a stage in a pipeline.</p>

























<table><thead><tr><th>Before</th><th>After</th></tr></thead><tbody><tr><td>SAST report just before release</td><td>static analysis on every save</td></tr><tr><td>quarterly vulnerability scan</td><td>dependency scan on every PR</td></tr><tr><td>secret rotation after an incident</td><td>secret detection in the commit hook</td></tr><tr><td>security team files a ticket</td><td>the author sees a red squiggle immediately</td></tr></tbody></table>
<p>What matters here isn't the tool list — it's <strong>who sees it, and when.</strong> The same SAST finding arriving as a ticket two weeks later carries a context-switch cost and usually slips to "later." Surfaced while coding, it just gets fixed. The tool didn't change; <strong>the cost did.</strong></p>
<p>In an agent-driven setup this goes one step further. Put the checks <strong>inside</strong> the agent's loop and the agent fixes its own defects within its own turn. Forcing lint, typecheck, and tests through hooks or a harness is something this blog has covered before (<a href="/en/posts/2026-08-25-agentic-code-quality/">Code Quality Lives in the Constraints</a>); the conclusion here is that security scanning belongs on that same list.</p>
<hr>
<h2 id="5-principle-3--distrust-the-dependencies-the-ai-dragged-in">5. Principle 3 — Distrust the Dependencies the AI Dragged In<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#5-principle-3--distrust-the-dependencies-the-ai-dragged-in"><span class="icon icon-link"></span></a></h2>
<p>The third is the one most often missed in practice: <strong>we read the generated code, but not the generated <code>package.json</code>.</strong></p>
<p>Ask an agent to "add image resizing" and you don't just get code. You get packages. And those packages usually arrive <strong>unreviewed</strong> — one line in the diff, the install succeeded, the tests passed.</p>
<p>Three axes to check:</p>





















<table><thead><tr><th>Axis</th><th>Question</th></tr></thead><tbody><tr><td><strong>Reputation / maintenance</strong></td><td>Is it actually used? When was the last commit? Is the name one character off a popular package (typosquatting)?</td></tr><tr><td><strong>License</strong></td><td>Is it usable given how we distribute?</td></tr><tr><td><strong>Supply-chain risk</strong></td><td>Known CVEs, including transitive deps? Any install scripts attached?</td></tr></tbody></table>
<p>The first row carries an AI-specific hazard. Models will <strong>invent plausible package names that don't exist</strong>, and attackers are known to claim those hallucinated names and publish real packages under them. Running <code>pnpm add</code> on whatever an agent suggested is risky for exactly that reason. <strong>A package name is not code — it's a trust decision.</strong></p>
<p>The remedy is unglamorous: put the lockfile diff in scope for review, and make adding a dependency a point where a human signs off. Writing "ask before adding a new dependency" into the agent spec at the ⚠️ tier catches most of it on its own.</p>
<hr>
<h2 id="6-principle-4--verify-intent-not-implementation">6. Principle 4 — Verify Intent, Not Implementation<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#6-principle-4--verify-intent-not-implementation"><span class="icon icon-link"></span></a></h2>
<p>The fourth is where human judgment is least replaceable.</p>
<p>Static analysis finds <strong>code that was written wrong.</strong> What it can't find is <strong>code that is doing the wrong thing.</strong> The latter isn't a syntax problem, it's a <strong>requirements-interpretation</strong> problem — and it looks perfectly normal to a scanner.</p>
<p>The typical shape:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Requirement: "a user must be able to view their own order history"</span></span>
<span data-line=""> </span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Agent implementation: GET /orders → returns all orders</span></span>
<span data-line=""><span style="--shiki-light:#702C00;--shiki-dark:#FFB757">  -</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6"> no injection        ✅</span></span>
<span data-line=""><span style="--shiki-light:#702C00;--shiki-dark:#FFB757">  -</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6"> authentication      ✅  (login is checked)</span></span>
<span data-line=""><span style="--shiki-light:#702C00;--shiki-dark:#FFB757">  -</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6"> authorization       ❌  (whose orders is not)</span></span>
<span data-line=""><span style="--shiki-light:#702C00;--shiki-dark:#FFB757">  -</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6"> tests pass          ✅  (only tested with the user's own orders)</span></span></code></pre></figure>
<p>What failed isn't the coding — it's the reading of the word <strong>"their own."</strong> The agent satisfied the requirement literally and passed every automated check. Catching this requires someone to ask: <strong>does this code stay inside the boundary the requirement intended?</strong></p>
<p>Questions worth having on hand:</p>
<ul>
<li>Can this code reach <strong>data outside the caller's permissions</strong>?</li>
<li>Are business rules (limits, state transitions, ownership) actually in the code, or only in the frontend?</li>
<li>Do the same rules hold on error paths, boundary values, and empty inputs?</li>
</ul>
<p>This section connects directly to the closing paragraph of the <a href="/en/posts/2026-09-13-writing-specs-for-agents/">spec post</a>. Self-verification is <strong>an agent checking its own work against its own spec</strong>, so <strong>if the spec itself is vague, everything passes.</strong> That's precisely why intent verification stays with people.</p>
<hr>
<h2 id="7-principle-5--make-it-a-habit-not-a-gate">7. Principle 5 — Make It a Habit, Not a Gate<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#7-principle-5--make-it-a-habit-not-a-gate"><span class="icon icon-link"></span></a></h2>
<p>The last principle is about time. Do all four of the above and, if you do them <strong>once</strong>, the result has a short shelf life.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">build → test → deploy → monitor → build again</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">   ↑_______________________________________|</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">       security has to ride the whole loop</span></span></code></pre></figure>
<p>Code that was clean at deploy time can become vulnerable through several paths.</p>





















<table><thead><tr><th>Path</th><th>What happens</th></tr></thead><tbody><tr><td><strong>A new CVE lands</strong></td><td>the code is unchanged, but a dependency is now vulnerable</td></tr><tr><td><strong>Configuration drift</strong></td><td>permissions, secrets, and network rules loosen in production</td></tr><tr><td><strong>A later agent change</strong></td><td>the next turn's agent deletes the earlier defense</td></tr></tbody></table>
<p>The third is the new entry for the AI era. An agent doesn't know <strong>why something was written that way before.</strong> A defensively added validation line that looks like dead code gets refactored away. That's why <strong>guardrails must live outside the code</strong> — as something that turns a test red, blocks at a hook, or gets rejected by policy when removed.</p>
<p>And here Principle 1 comes back around. Instead of trusting the agent's <strong>behavior</strong>, build <strong>boundaries it cannot cross.</strong> A prompt is a request; hooks, tests, and permissions are constraints.</p>
<hr>
<h2 id="8-applying-it-to-this-repository">8. Applying It to This Repository<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#8-applying-it-to-this-repository"><span class="icon icon-link"></span></a></h2>
<p>Here's an honest count of where this blog's repository stands on the five.</p>





























<table><thead><tr><th>Principle</th><th>Current state</th></tr></thead><tbody><tr><td><strong>1. Verify outcomes</strong></td><td>Partial — <code>pnpm test</code> and <code>pnpm e2e</code> exist, axe accessibility checks run, but all of it is a <strong>functional</strong> oracle</td></tr><tr><td><strong>2. Shift left</strong></td><td>Yes — a husky <code>pre-commit</code> forces lint → vitest → playwright before any commit</td></tr><tr><td><strong>3. Dependency validation</strong></td><td><strong>Missing</strong> — no automated audit. The recent major upgrade was judged by hand</td></tr><tr><td><strong>4. Intent validation</strong></td><td>Human — content-convention tests cover a slice (category vocabulary, 1:1 translations); the rest is review</td></tr><tr><td><strong>5. Continuous verification</strong></td><td>Partial — <code>deploy.yml</code> runs everything on push, but nothing runs when the code doesn't change</td></tr></tbody></table>
<p>Read honestly: <strong>#3 is empty, and #5 is event-driven, so it can't catch a new CVE.</strong> The attack surface of a static blog is small, but an empty box is still empty. Two cheap reinforcements:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="yaml" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="yaml" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#66707B;--shiki-dark:#BDC4CC"># ① one audit line in pre-commit or CI — Principle 3</span></span>
<span data-line=""><span style="--shiki-light:#032563;--shiki-dark:#ADDCFF">pnpm audit --audit-level=high</span></span>
<span data-line=""> </span>
<span data-line=""><span style="--shiki-light:#66707B;--shiki-dark:#BDC4CC"># ② a check that runs even when nothing changed — Principle 5</span></span>
<span data-line=""><span style="--shiki-light:#66707B;--shiki-dark:#BDC4CC">#    a schedule trigger, the same way refresh-popular.yml does it</span></span>
<span data-line=""><span style="--shiki-light:#023B95;--shiki-dark:#91CBFF">on</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span data-line=""><span style="--shiki-light:#024C1A;--shiki-dark:#72F088">  schedule</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">    - </span><span style="--shiki-light:#024C1A;--shiki-dark:#72F088">cron</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="--shiki-light:#032563;--shiki-dark:#ADDCFF">'0 0 * * 1'</span></span></code></pre></figure>
<p>A cron already refreshes the popular-posts snapshot daily (<code>refresh-popular.yml</code>), so <strong>the plumbing for scheduled runs is already in place.</strong> #5 is empty not because it's hard, but because nobody did it. That's usually the reason.</p>
<hr>
<h2 id="9-wrapping-up">9. Wrapping Up<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#9-wrapping-up"><span class="icon icon-link"></span></a></h2>



































<table><thead><tr><th></th><th>Principle</th><th>One line</th></tr></thead><tbody><tr><td><strong>1</strong></td><td>Verify outcomes, not the process</td><td>Running and safe are different claims. Tests passing ≠ safe</td></tr><tr><td><strong>2</strong></td><td>Pull checks into the editor</td><td>You're changing the <strong>cost of discovery</strong>, not the tooling</td></tr><tr><td><strong>3</strong></td><td>Distrust generated dependencies</td><td>We read the code but not <code>package.json</code>. Watch for hallucinated names</td></tr><tr><td><strong>4</strong></td><td>Verify intent, not implementation</td><td>What scanners miss is a defect in <strong>requirements interpretation</strong></td></tr><tr><td><strong>5</strong></td><td>A habit, not a gate</td><td>Clean at deploy time doesn't mean clean today</td></tr></tbody></table>
<p>Laid alongside the thread this blog has been pulling on, the placement is clear.</p>
<ul>
<li><a href="/en/posts/2026-08-25-agentic-code-quality/">Code Quality Lives in the Constraints</a> — holding quality with <strong>constraints</strong> at a scale review can't cover</li>
<li><a href="/en/posts/2026-08-23-ai-native-sdlc-playbook/">The AI-Native SDLC Playbook</a> — when code stops being the bottleneck, <strong>verification becomes one</strong></li>
<li><a href="/en/posts/2026-09-13-writing-specs-for-agents/">More Instructions, Less Compliance</a> — a vague spec makes self-verification pass everything</li>
<li>This post — what shape <strong>security</strong> takes on that verification list</li>
</ul>
<p>Look at the five again and none of them are new. Shift-left, dependency checks, intent review — all of it has been standard advice for years. What changed is that <strong>the slack that let you skip them is gone.</strong> Multiply production by ten and the gaps you used to cover with momentum simply show.</p>
