<h2 id="zustand-concepts">zustand Concepts<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#zustand-concepts"><span class="icon icon-link"></span></a></h2>
<ul>
<li>State management overview
These days, approaches to state management can roughly be divided into three categories.
<ul>
<li>Flux (Redux, Zustand)
<ul>
<li>The commonly used Flux approach, which updates state through a store, action functions, reducers, and so on.</li>
</ul>
</li>
<li>Proxy (Mobx, Valtio)
<ul>
<li>An approach that automatically detects and updates the specific pieces of state used by a component.</li>
</ul>
</li>
<li>Atomic (Jotai, Recoil)
<ul>
<li>An approach that stores and manages state within the React tree, similar to React's own state.</li>
</ul>
</li>
</ul>
</li>
<li>zustand concepts
<ul>
<li>The way stores are implemented and updated is simple (less boilerplate code compared to Redux).</li>
<li>There is no need to wrap the app with a Provider.</li>
<li>Unlike when using the Context API, unnecessary re-renders do not occur when state changes (only the changed state is updated).</li>
<li>It is not tightly coupled to any particular library (it provides APIs that work with React out of the box → hooks are provided).</li>
<li>While leveraging a single centralized store structure, defining and using state is simple.</li>
<li>It is more similar to the Flux structure than to Redux.</li>
<li>It provides a variety of middleware libraries (redux, immer, selector (automatically called when state changes), redux-devtools).</li>
</ul>
</li>
</ul>
<h2 id="zustand-features">zustand Features<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#zustand-features"><span class="icon icon-link"></span></a></h2>
<ul>
<li>
<p><strong>Fetching everything</strong>
You can retrieve all state values from the store, but since the component updates every time any state changes, you should select and retrieve only the state values you need.</p>

</li>
<li>
<p><strong>Selecting multiple state slices</strong>
By default, the component re-renders when a strict compare (old === new) detects a change.
This is the same as redux's useSelector, jotai's selectAtom, and recoil's selector.</p>

<li>
<p><strong>Memoizing selectors</strong>
If you use it together with useCallback in a React functional component, you can memoize the selector. This prevents unnecessary computations on every render.</p>

<h2 id="personal-opinion">Personal Opinion<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#personal-opinion"><span class="icon icon-link"></span></a></h2>
<ul>
<li>If you want to resolve the drawbacks of state management (redux, contextapi), this library seems well worth considering.
<ul>
<li>Minimizes boilerplate code (action, reducer, state, type, etc.)</li>
<li>No need to wrap with a provider</li>
<li>Child re-renders can be updated per state</li>
</ul>
</li>
<li>It is easier to learn than redux or mobx state management, and seems quick to adopt.</li>
<li>Since zustand itself supports many libraries, it seems easy to use. (However, check whether full library support is available.)</li>
<li>Because it is built on a React hooks-based structure, it seems good for extensibility and reusability.</li>
</ul>
