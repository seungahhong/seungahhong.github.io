1b:T11555,<h2 id="why-was-css-in-js-created">Why was CSS-in-JS created?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#why-was-css-in-js-created"><span class="icon icon-link"></span></a></h2>
<p>CSS-in-JS, as the name suggests, refers to the approach of writing CSS within JavaScript code. It was first introduced in 2014 by Christopher Chedeau (aka Vjeux), a developer at Facebook.</p>
<p><img src="/blog-assets/2022/05/images/31/Untitled.png" alt="Untitled"></p>
<p>Vjeux described the difficulties of writing CSS as follows, and emphasized that CSS-in-JS could solve all of these issues.</p>
<ul>
<li>
<p>Global namespace: A naming convention is required for names declared in the global space</p>
<ul>
<li>Issue
<ul>
<li>Because CSS was originally designed to style documents, it has no concept of modular scope (a global scope/namespace)</li>
<li>CSS methodologies (BEM) and Module/Scope formats were meant to keep CSS rules from affecting multiple elements, but they still do not support module-level scoping</li>
</ul>
</li>
<li>Solution
<ul>
<li>Because CSS-in-JS defines styles in JS, style variables are limited to lexical scope (component-level scope)</li>
<li>CSS-in-JS lets you export/import style variables freely, making reuse possible</li>
</ul>
</li>
</ul>

</li>
<li>
<p>Implicit Dependencies: Managing dependency relationships</p>
<ul>
<li>Issue
<ul>
<li>Because JS/CSS modules are separated, the relationship between className/attribute is not explicit, so developers have to remember and manage it themselves, which is difficult</li>
</ul>
</li>
<li>Solution
<ul>
<li>Because CSS-in-JS writes CSS inside JS, static analysis is possible, and with the help of the IDE it becomes easy to manage whether something is used or unused</li>
</ul>
</li>
</ul>
</li>
<li>
<p>Dead Code Elimination: Detecting unused code</p>
<ul>
<li>Issue
<ul>
<li>Because managing dependencies is difficult, it is hard to determine whether code is unused (dead code)</li>
<li>You can use Google Chrome's coverage tool, but it requires additional working time</li>
</ul>
</li>
<li>Solution
<ul>
<li>If you use CSS-in-JS, you can easily remove unused code with the help of eslint and the IDE</li>
</ul>
</li>
</ul>
</li>
<li>
<p>Non-deterministic Resolution</p>
<ul>
<li>Issue
<ul>
<li>CSS rules with higher specificity are applied. However, if they have the same specificity, the rule defined later is applied.</li>
<li>If you load CSS with the same specificity asynchronously, which CSS rule will be applied? The answer is you don't know.</li>
<li>This is called Non-deterministic Resolution.
<img src="/blog-assets/2022/05/images/31/Untitled1.png" alt="Untitled"></li>
</ul>
</li>
<li>Solution
<ul>
<li>By tightly coupling HTML/CSS/JS at the module (component) level, you can control and determine CSS priority.</li>
</ul>
</li>
</ul>
</li>
<li>
<p>Minification: Minimizing class names</p>

</li>

<li>
<p>Breaking Isolation: The problem of managing external modifications to CSS being difficult</p>
<ul>
<li>To easily achieve feature reusability and apply custom styles, it is more efficient to manage CSS/JS together</li>
<li>In the case of Vue/Svelte and others, this is handled by bundling style/script/html together in a single-file-component approach</li>
<li>In React, the goal is to bundle and manage them within the JS ecosystem using the CSS-in-JS approach</li>
</ul>
</li>
</ul>
