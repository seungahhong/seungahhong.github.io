21:T3169a,<h2 id="before-we-begin-vs-cypress">Before We Begin.. (vs. Cypress)<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#before-we-begin-vs-cypress"><span class="icon icon-link"></span></a></h2>
<h3 id="why-did-we-move-from-cypress-to-playwright">Why Did We Move from Cypress to Playwright??<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#why-did-we-move-from-cypress-to-playwright"><span class="icon icon-link"></span></a></h3>
<h4 id="pain-points-when-developing-with-cypress">Pain Points When Developing with Cypress<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#pain-points-when-developing-with-cypress"><span class="icon icon-link"></span></a></h4>
<ul>
<li>We felt that loading the test environment and running the tests took far too much time.</li>
<li>There were many cases where Cypress failed to find elements in the test environment, and we couldn't figure out the cause.</li>
<li>Cypress's own syntax was unfamiliar to FE developers.</li>
<li>Even when we wanted to run tests in parallel to improve test speed, there was the hurdle of having to pay an additional fee.</li>
</ul>
<p>→ To overcome these difficulties, we started looking for another testing library, and along the way we discovered one that could solve the problems above. That library is Playwright, built by Microsoft.</p>
<h4 id="cypress-vs-playwright">Cypress vs Playwright<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#cypress-vs-playwright"><span class="icon icon-link"></span></a></h4>
<ul>
<li>Test speed comparison
<ul>
<li>When running with link navigation first for e2e test isolation, based on a single spec it wasn't dramatically faster than Cypress.
<ul>
<li>However, when running in parallel with a large number of cases, we could feel that the test speed increased.</li>
<li><a href="https://emewjin.github.io/playwright-vs-cypress/#%ED%85%8C%EC%8A%A4%ED%8A%B8-%EC%86%8D%EB%8F%84%EA%B0%80-cypress%EB%B3%B4%EB%8B%A4-%EC%A7%84%EC%A7%9C-%EB%8D%94-%EB%B9%A0%EB%A5%BC%EA%B9%8C">https://emewjin.github.io/playwright-vs-cypress/#테스트-속도가-cypress보다-진짜-더-빠를까</a></li>
</ul>
</li>
<li>Playwright provides a beforeAll function, so in web apps built with a SPA structure, we could feel that the test speed increased when navigating to a link once at the beginning and then using page.goBack(), compared to beforeEach. (However, since you can't obtain the page in beforeAll, you have to create a new one, and in that case you can't run tests in parallel.)</li>
<li>After adding it to a company project, we found that it was roughly 5 times faster.</li>
</ul>
</li>
<li>Supported test environments
<ul>
<li>Playwright
<ul>
<li>Chromium-based browsers, Firefox, <strong>Safari support</strong></li>
<li><strong>Mobile browser support</strong></li>
<li><strong>Experimental mode: Android Chrome/WebView, Electron support planned</strong></li>
</ul>
</li>
<li>Cypress
<ul>
<li>Only supports two browsers: Chromium-based browsers and Firefox</li>
</ul>
</li>
</ul>
</li>
<li>Parallel test support
<ul>
<li>Playwright
<ul>
<li><strong>Runs all tests in parallel</strong></li>
<li><strong>Can set up to 4 worker threads</strong>
<ul>
<li>However, when specifying worker threads, isolating each test unit is mandatory!!</li>
</ul>
</li>
</ul>
</li>
<li>Cypress
<ul>
<li>Runs all tests serially</li>
<li>However, to run parallel tests, you must subscribe to a paid plan to run parallel tests in a CI/CD environment → you have to pay money ㅜㅜ)</li>
</ul>
</li>
</ul>
</li>
<li>Rich event support
<ul>
<li>Supports hover and drag (not supported by Cypress)</li>
</ul>
</li>
<li>Syntax
<ul>
<li>Supports the pure, native syntax of the language it targets. (Cypress provides its own custom syntax)
<img src="/blog-assets/2023/04/assets/02/Untitled.png" alt="Untitled"></li>
</ul>
</li>
</ul>
<h2 id="introducing-playwright">Introducing Playwright<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#introducing-playwright"><span class="icon icon-link"></span></a></h2>
<p><img src="/blog-assets/2023/04/assets/02/Untitled_1.png" alt="Untitled"></p>
<p>Playwright is an open-source web testing and automation library built by Microsoft. With a single API, it can test Chromium, Firefox, WebKit, and mobile web (Chromium, Safari, etc.). (In the <a href="https://playwright.dev/docs/next/api/class-android">Next version</a>, it appears to also support Android Chrome and Electron via ADB.)</p>
<p>In fact, Playwright itself is not an E2E testing framework; cross-browser testing becomes possible by using the @playwright/test framework. (However, it does not support legacy Edge or IE.)</p>
<h3 id="playwright-features">Playwright Features<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#playwright-features"><span class="icon icon-link"></span></a></h3>
<ul>
<li>Features
A single API for multi-browser/platform testing
<ul>
<li>Cross-browser: Supports the latest modern browsers Chromium, Webkit, and Firefox</li>
<li>Cross-platform: Windows, Linux, MacOS, locally or CI, headless or headed</li>
<li>Cross-language: Typescript, Javascript, Python, .NET, Java</li>
<li>Test Mobile Web: Tests mobile web on Android/Safari using native mobile emulation
Other features</li>
<li>Auto-waiting: Automatically waits until the element is ready before an action is executed (timeout option)</li>
<li>Retry: Assertions are automatically retried until the required condition is met (retry option)</li>
<li>Tracing: Enables error tracing through execution traces, video, and screenshot capture</li>
<li>Can hook into network activity to mock network requests</li>
<li>Supports basic mouse and keyboard input event testing
Powerful tools</li>
<li>Codegen: A tool that generates automation test code based on Playwright's capabilities
<ul>
<li>Because it generates code automatically, it saves time and effort in writing code</li>
</ul>
</li>
<li>inspector: Step-by-step debugging of test execution (a scaled-down version of Chrome DevTools)</li>
<li>trace viewer: Captures all information to investigate test failures</li>
</ul>
</li>
</ul>
<h2 id="setting-up-playwright">Setting Up Playwright<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#setting-up-playwright"><span class="icon icon-link"></span></a></h2>
<h3 id="test-files">Test Files<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#test-files"><span class="icon icon-link"></span></a></h3>
<p>The filename must include "test". It takes a form like hotfix.test.ts.</p>
<ul>
<li>You can change the extension via testMatch in playwright.config.ts.</li>
</ul>

<li>Playwright has separate timeouts for various tasks.</li>
<li>Timeouts can be configured globally or per command.

<p><strong>describe, test</strong>
Use describe to logically group tests, and write tests with test.
Within describe, when you need setup/teardown for the entire group of tests, try using beforeAll and afterEach,
<strong>→ Because creating context and page takes a lot of time, creating them in advance before all tests can reduce test time.</strong>
When you need setup/teardown work for each individual test, please use beforeEach and afterEach.</p>

<p><strong>Test Titles</strong>
Test titles should be as explicit as possible so that you can tell what the test does just by looking at the title, and they should be written as active sentences. (Avoid passive expressions like "~ is done" and instead write active expressions like "~ does".)</p>
<h3 id="handy-little-tips">Handy Little Tips<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#handy-little-tips"><span class="icon icon-link"></span></a></h3>
<h4 id="testonly">test.only<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#testonly"><span class="icon icon-link"></span></a></h4>
<p>When a test file has multiple test cases, even if you modify only one test, all test cases in the file will run. You can use <strong>test.only</strong> to run only the test case you are currently working on.</p>
<h4 id="testskip">test.skip<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#testskip"><span class="icon icon-link"></span></a></h4>
<p>When a test case can't be run but you still want it in the test list, you can use <strong>test.skip</strong>. It will be counted as pending in the final results.
<strong>Selector</strong>
Playwright's selectors are provided based on query priority, and when that feature doesn't work you can use locators to freely access elements.
Query priority</p>
<ul>
<li>Priority among queries for testing visual elements / user interactions
<ul>
<li>getByRole > getByLabelText > getByPlaceholderText > getByText > getByDisplayValue</li>
</ul>
</li>
<li>Priority among queries for testing HTML5 and ARIA attributes
<ul>
<li>getByAltText > getByTitle</li>
</ul>
</li>
<li>Test ID: Used only to find values that cannot be found with the queries above
<ul>
<li>getByTestId</li>
<li>It seems best to decide on the data attribute through team consensus.</li>
</ul>
</li>
<li>If you cannot access it even with these priorities, you can use locator.

<p>Because creating a browser instance is expensive, Playwright is designed to maximize what a single instance can do through multiple browser contexts.
A browser context is an isolated, session-like environment within a browser instance. It is fast and inexpensive to create. It's recommended to run each test in a new browser context to isolate browser state between tests.</p>

<h2 id="best-practices">Best Practices<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#best-practices"><span class="icon icon-link"></span></a></h2>
<h3 id="testing-philosophy">Testing philosophy<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#testing-philosophy"><span class="icon icon-link"></span></a></h3>
<ul>
<li>
<p>Test the areas/behaviors visible to the user</p>
<ul>
<li>Test pages where the end user can view the page or interact with it.</li>
</ul>
</li>
<li>
<p>Isolate tests as much as possible when writing them</p>
<ul>
<li>Isolate the work for each test individually (local/session storage, data, cookies, etc.)</li>
<li>When you need to avoid repeating something specific in tests, use before and after hooks</li>
<li>When navigating to a specific URL within a test file or logging into part of the app, use before hooks</li>
</ul>

<li>
<p>Write test code that follows the overall flow (long tests are fine.)</p>
<ul>
<li>When testing the entire app flow, handling assertions for multiple actions is fine.</li>
<li>Splitting a long test into individual tests unnecessarily should be avoided, because it slows down test execution.</li>
<li>When you want to display errors without terminating on a long test error, you can use soft assertions.</li>
</ul>

<h2 id="what-should-we-do-to-build-e2e-test-automation">What Should We Do to Build E2E Test Automation?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#what-should-we-do-to-build-e2e-test-automation"><span class="icon icon-link"></span></a></h2>
<h4 id="writing-scenarios-planningqatest-engineers">Writing scenarios (Planning/QA/Test Engineers)<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#writing-scenarios-planningqatest-engineers"><span class="icon icon-link"></span></a></h4>
<ul>
<li>Write testing scenarios that consider the user interface (UI)</li>
<li>Write test scenarios that can automate tests previously done manually (live-deployment sanity checks, basic verification)</li>
<li>Write scenarios not only for Happy cases but also for Bad cases</li>
<li>If you write test code during development, you can reduce the BAT test schedule</li>
<li>Migrate feature/component unit tests to automation, and focus testing on usability testing</li>
</ul>

<h4 id="whether-to-maintain-test-code-needs-discussion-with-the-planningqa-teams">Whether to maintain test code (needs discussion with the Planning/QA teams)<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#whether-to-maintain-test-code-needs-discussion-with-the-planningqa-teams"><span class="icon icon-link"></span></a></h4>
<ul>
<li>Whether it can be done without overlapping the E2E tests the QA team is also running</li>
<li>Need to list out the tests that are truly necessary from the user's perspective</li>
<li>Expanding service test automation
<ul>
<li>Test automation appropriate to the nature of the test is needed
<ul>
<li>Personal opinion on simplified tests
<ul>
<li>Test speed must be fast (within 5 minutes → must be faster than a human running the test) - Hotfix testing takes about 5 minutes</li>
<li>Whether it succeeds or fails, it must not affect the build.</li>
<li>Even if it fails, it should notify but must not block the deployment/development process.</li>
</ul>
</li>
<li>Other tests
<ul>
<li>When the number of test cases grows, configure Jenkins jobs/tests differently by domain and feature unit.</li>
</ul>

<h2 id="expected-results">Expected Results<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#expected-results"><span class="icon icon-link"></span></a></h2>
<ul>
<li>Through automated testing, we can quickly find issues (bugs) after deployment, which <strong>improves the user experience</strong>.</li>
<li>Through basic user end-to-end testing, we can pursue <strong>service stabilization</strong>.</li>
<li>We can raise <strong>the reliability of development code and the quality of the code</strong>.</li>
<li>By testing existing features together whenever a new feature is added, <strong>testing for potential issues becomes possible</strong>.</li>
<li>In the long run, we can <strong>save time and cost</strong>.</li>
</ul>
