<h3 id="consistent-errors-when-returning-undefined">Consistent errors when returning undefined<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#consistent-errors-when-returning-undefined"><span class="icon icon-link"></span></a></h3>
<p>In versions 16 and below, every component would always throw an error when it returned undefined.</p>
<p>However, due to a coding oversight, this error handling was missing for <code>forwardRef</code> and <code>memo</code> components, and it has now been added.</p>
<p>Starting from v17, <code>forwardRef</code> and <code>memo</code> components also throw an error when they return undefined.</p>

<h3 id="no-event-pooling"><strong>No Event Pooling</strong><a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#no-event-pooling"><span class="icon icon-link"></span></a></h3>
<ul>
<li>Event pooling
Because there was an issue where using event objects in older browsers caused performance degradation, React created and managed a Synthetic Event pool.
<ul>
<li>When a user triggers a particular event
<ul>
<li>It passes a reference to a Synthetic Event object from the Synthetic Event pool (→ reducing object creation time)</li>
<li>It populates the Synthetic Event object with the event information</li>
<li>It runs the event listener defined by the user</li>
<li>It resets the Synthetic Event object (→ by assigning null so that GC can reclaim the memory, a step for memory efficiency)
This feature can cause errors to occur in asynchronous operations.</li>
</ul>
</li>
</ul>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="tsx" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="tsx" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">onChange</span><span style="--shiki-light:#A0111F;--shiki-dark:#FF9492">=</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">{</span></span>

To resolve this issue, using React's persist to remove the event from the event pool and fall back to the traditional event approach works without any problems, but you give up the performance benefit.</li>
</ul>
<p>Starting from v17, React decided to no longer support the behavior that compensated for performance issues in legacy browsers.</p>
<p>However, the event.persist() method still exists, though calling it does nothing (kept for backward compatibility).</p>

<ul>
<li><strong>Starting from React 17, events are delegated to the React Tree Root instead of the document.</strong></li>
</ul>
<p><img src="/blog-assets/2022/02/images/13/Untitled.png" alt="Untitled"></p>
<p>Even when multiple React components run, because events are handled at the base Root Element, the structure and event handling can operate independently.</p>
<p>This makes it easier to use React alongside other technologies. If jQuery exists on the outside and React exists on the inside, you can now stop event propagation down to the jQuery layer as expected.</p>
<p>However, there may be code that manually attaches an event using <strong><code>document.addEventListener</code></strong> on the DOM to detect all React events. This kind of code was possible in React 16, but starting from React 17 the propagation is blocked, so you cannot tell whether events are firing at the <strong><code>document</code></strong> level. This means you need to switch to the capture approach.</p>
