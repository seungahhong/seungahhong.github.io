10:T13beb,<h2 id="why-should-we-use-typescript">Why should we use TypeScript?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#why-should-we-use-typescript"><span class="icon icon-link"></span></a></h2>
<p><strong>TypeScript makes code easier to read.</strong></p>
<ul>
<li>By explicitly annotating types for variables, return values, interfaces, and so on, the code becomes easier to understand.
<strong>TypeScript reduces developer mistakes.</strong></li>
<li>It's easy to catch errors while writing code or during the compile step.</li>
<li>You can respond to errors quickly and minimize side effects.
<strong>Make more active use of the IDE (autocompletion, type checking)</strong></li>
<li>With TypeScript, autocompletion works remarkably well.</li>
<li>When calling a function, you can tell what parameters it requires and what value it returns without having to open the code separately.</li>
<li>For React components, you can know the props/state values in advance.
<strong>Support for object-oriented programming</strong></li>
<li>Powerful object-oriented programming support such as interfaces, generics, and overloading/overriding makes it easy to structure the codebase of large, complex projects.</li>
</ul>

<ul>
<li>Let's decide when to use type versus interface!!
<ul>
<li>The latest version of tslint provides a guide for this.
<ul>
<li>Use an interface instead of a type literal.tslint(interface-over-type-literal)
<ul>
<li>A guide was added recommending that you use type only for literal types and use interfaces for Object-shaped types.</li>
</ul>
</li>
</ul>
</li>
<li><strong>Let's use interfaces for everything except literal types (i.e., primitive types, custom values).</strong></li>
<li>Reference page: <a href="https://luckyyowu.tistory.com/401">https://luckyyowu.tistory.com/401</a></li>
</ul>
</li>
</ul>
<p><strong>Similarities</strong></p>
<ul>
<li>Named types are used the same way for both Type and Interface</li>
<li>Index signatures can be used</li>
<li>Function types can be declared</li>
<li>Generics can be used</li>
<li>Both can be extended
<ul>
<li>interface extends with the extends keyword, while type extends with &#x26;</li>
</ul>
</li>
</ul>
<p><strong>Differences</strong></p>
<ul>
<li>
<p>Union types</p>
<ul>
<li>Possible with Type, but not with Interface
<ul>
<li>type yesOrNo = ‘yes’ | ‘no’</li>
</ul>
</li>
<li>You cannot extend a union type with an interface</li>
</ul>
</li>
<li>
<p>Tuple and array types</p>
<ul>
<li>type: easy to use and convenient to extend; interface: somewhat complicated and inconvenient</li>
</ul>

<h2 id="typescript-official-page-dos-and-donts-guide">TypeScript official page: Do's and Don'ts guide<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#typescript-official-page-dos-and-donts-guide"><span class="icon icon-link"></span></a></h2>
<p><strong>General Types</strong></p>
<ul>
<li>Don’t
<ul>
<li>Never use the Number, String, Boolean, or Object types. These types refer to non-primitive boxed objects that are almost never used appropriately in JavaScript code.</li>
</ul>
</li>
<li>Do
<ul>
<li>Use number, string, and boolean.</li>
</ul>
</li>
</ul>
<pre><code>/* WRONG */
function reverse(s: String): String;

/* OK */
function reverse(s: string): string;
</code></pre>
<p><strong>Callback Types</strong>
<strong>Return Types of Callbacks</strong></p>
<ul>
<li>Don’t
<ul>
<li>Don't use any as the return type of a callback whose value will be ignored.</li>
</ul>
</li>
<li>Do
<ul>
<li>Use void as the return type of a callback whose value will be ignored.</li>
</ul>
</li>
</ul>
<pre><code>/* WRONG */
function fn(x: () => any) {
  x();
}

/* OK */
function fn(x: () => void) {
  x();
}

// Why? Because using void is safer as it prevents the mistake of using x's return type in an unverified way.
function fn(x: () => void) {
  var k = x(); // oops! meant to do something else
  k.doSomething(); // error, but would be OK if the return type had been 'any'
}

</code></pre>
<p><strong>Function Overloads</strong></p>
<ul>
<li>Don’t
<ul>
<li>Don't put a general signature before a more specific one.</li>
</ul>
</li>
<li>Do
<ul>
<li>Order signatures so that the general signature comes after the more specific ones.</li>
</ul>
</li>
</ul>
<pre><code>/* WRONG */
declare function fn(x: unknown): unknown;
declare function fn(x: HTMLElement): number;
declare function fn(x: HTMLDivElement): string;
var myElem: HTMLDivElement;
var x = fn(myElem); // x: unknown, wat?

/* OK */
declare function fn(x: HTMLDivElement): string;
declare function fn(x: HTMLElement): number;
declare function fn(x: unknown): unknown;
var myElem: HTMLDivElement;
var x = fn(myElem); // x: string, :)
</code></pre>
<p><strong>Use Optional Parameters</strong></p>
<ul>
<li>Don’t
<ul>
<li>Don't write multiple signatures that differ only in trailing parameters.</li>
</ul>
</li>
<li>Do
<ul>
<li>Use optional parameters whenever possible.</li>
</ul>
</li>
</ul>
<pre><code>/* WRONG */
interface Example {
  diff(one: string): number;
  diff(one: string, two: string): number;
  diff(one: string, two: string, three: boolean): number;
}

/* OK */
interface Example {
  diff(one: string, two?: string, three?: boolean): number;
}
</code></pre>
<p>Note that this approach is only possible when all signatures have the same return type!!</p>
<h4 id="use-union-types">Use Union Types<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#use-union-types"><span class="icon icon-link"></span></a></h4>
<ul>
<li>Don’t
<ul>
<li>Don't use overloading when only one parameter type differs.</li>
</ul>
</li>
<li>Do
<ul>
<li>Use union types whenever possible.</li>
</ul>
</li>
</ul>

interface Moment {
  utcOffset(): number;
  utcOffset(b: number): Moment;
  utcOffset(b: string): Moment;
}

/* OK */
interface Moment {
  utcOffset(): number;
  utcOffset(b: number | string): Moment;
}

<p>A type alias doesn't create a brand-new type value; rather, it's like giving a name to a defined type so that developers can observe it more easily.
That's why when you define an interface and hover the cursor over it, it shows <code>interface xx</code>, whereas a type shows it in detail as <code>type xx = {xx: xx}</code>.

<h2 id="utility-type">utility type<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#utility-type"><span class="icon icon-link"></span></a></h2>
<h3 id="partial">Partial<t></t><a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#partial"><span class="icon icon-link"></span></a></h3>
<pre><code>Lets you define a type that satisfies a subset of a specific type.

```tsx
interface Address {
  email: string;
  address: string;
}

type MyEmail = Partial&#x3C;Address>;
const me: MyEmail = {}; // allowed
const you: MyEmail = { email: 'gmm117@naver.com' }; // allowed
const all: MyEmail = { email: 'gmm117@naver.com', address: 'seoul' }; // allowed
```
</code></pre>
<h3 id="excludet-u">Exclude&#x3C;T, U><a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#excludet-u"><span class="icon icon-link"></span></a></h3>
<pre><code>Constructs a type by excluding from T the intersecting properties that are assignable to U.
```tsx
type T0 = Exclude&#x3C;'a' | 'b' | 'c', 'a'>; // "b" | "c"
type T1 = Exclude&#x3C;'a' | 'b' | 'c', 'a' | 'b'>; // "c"
type T2 = Exclude&#x3C;string | number | (() => void), Function>; // string | number
```
</code></pre>
<h3 id="extractt-u">Extract&#x3C;T, U><a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#extractt-u"><span class="icon icon-link"></span></a></h3>
<pre><code>Constructs a type by extracting from T the intersecting properties that are assignable to U.
```tsx
type T0 = Extract&#x3C;'a' | 'b' | 'c', 'a' | 'f'>; // "a"
type T1 = Extract&#x3C;string | number | (() => void), Function>; // () => void
```
</code></pre>
<h3 id="nonnullable">NonNullable<t></t><a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#nonnullable"><span class="icon icon-link"></span></a></h3>
<pre><code>Constructs a type by excluding null and undefined from T.
```tsx
type T0 = NonNullable&#x3C;string | number | undefined>; // string | number
type T1 = NonNullable&#x3C;string[] | null | undefined>; // string[]
```
</code></pre>
<h3 id="readonly">Readonly<t></t><a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#readonly"><span class="icon icon-link"></span></a></h3>
<pre><code>Constructs a type with all properties of T set to readonly, meaning the properties of the resulting type cannot be reassigned.

```tsx
interface Todo {
  title: string;
}

const todo: Readonly&#x3C;Todo> = {
  title: 'Delete inactive users',
};

todo.title = 'Hello'; // error: cannot reassign a read-only property
```
</code></pre>
<h3 id="pick">Pick<t></t><a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#pick"><span class="icon icon-link"></span></a></h3>
<pre><code>Defines a type by selecting a few properties from a specific type

```tsx
interface Address {
  email: string;
  address: string;
}

type MyEmail = Pick&#x3C;Address, 'email'>;
// uses only part of it, the email property
```
</code></pre>
<h3 id="omit">Omit<t></t><a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#omit"><span class="icon icon-link"></span></a></h3>
<pre><code>Defines a type with certain properties removed (the opposite of pick)

```tsx
interface Address {
  email: string;
  address: string;
}

type MyEmail = Omit&#x3C;Address, 'address'>;
// removes the address property
```
</code></pre>
<h3 id="returntype">ReturnType<t></t><a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#returntype"><span class="icon icon-link"></span></a></h3>
<pre><code>Constructs a type consisting of the return type of function T.
```tsx
declare function f1(): { a: number; b: string };
type T0 = ReturnType&#x3C;() => string>; // string
type T1 = ReturnType&#x3C;(s: string) => void>; // void
type T2 = ReturnType&#x3C;&#x3C;T>() => T>; // {}
type T3 = ReturnType&#x3C;&#x3C;T extends U, U extends number[]>() => T>; // number[]
type T4 = ReturnType&#x3C;typeof f1>; // { a: number, b: string }
type T5 = ReturnType&#x3C;any>; // any
type T6 = ReturnType&#x3C;never>; // any
```
</code></pre>
