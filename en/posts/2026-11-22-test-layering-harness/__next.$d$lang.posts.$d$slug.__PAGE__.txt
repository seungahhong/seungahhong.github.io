24:Tb099,<h2 id="splitting-acceptance-criteria-into-layered-tests-one-approval-at-a-time">Splitting Acceptance Criteria into Layered Tests, One Approval at a Time<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#splitting-acceptance-criteria-into-layered-tests-one-approval-at-a-time"><span class="icon icon-link"></span></a></h2>
<p><a href="https://github.com/seungahhong/seungah-claude-plugins/tree/main/plugins/test-layering-harness">test-layering-harness</a> is a single-skill plugin I published to my Claude Code plugin marketplace (seungah-claude-plugins). It takes acceptance criteria (Given-When-Then), plans <strong>which tests to write, at which layer, and in which CI stage</strong>, and then adds the tests one by one through three approvals: plan → individual → final. The current version is 0.8.0.</p>
<p>If the <a href="/en/posts/2026-11-21-product-spec-harness/">product spec harness</a> takes you from a planning draft to acceptance criteria, this harness handles the next step: turning those criteria into a test suite that actually runs. It does not depend on any other plugin, so acceptance criteria are all it needs.</p>
<h3 id="️-tldr">✍️ TL;DR<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#️-tldr"><span class="icon icon-link"></span></a></h3>
<blockquote>
<p><strong>When AI writes the tests, the risk moves away from "how fast can we write them" to "what do we verify, at which layer, and what do we treat as the right answer."</strong> This harness plans tests along two axes — methodology × layer — has a human approve every step, and actually runs what it writes.</p>
</blockquote>
<h3 id="why-i-built-it">Why I built it<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#why-i-built-it"><span class="icon icon-link"></span></a></h3>
<h4 id="writing-many-tests-is-already-easy">Writing <em>many</em> tests is already easy<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#writing-many-tests-is-already-easy"><span class="icon icon-link"></span></a></h4>
<p>Ask an agent to "write tests" and you get tests quickly. The trouble comes after. The failures I kept seeing fell into three groups.</p>
<ul>
<li><strong>Every acceptance criterion becomes an E2E test.</strong> Acceptance criteria are written from the user's point of view, so a literal translation spins up a browser. You end up with the "ice-cream cone": a heavy top of slow, flaky tests whose failures are hard to trace.</li>
<li><strong>Suites exist only as names.</strong> The plan says "3 smoke, 10 regression," but nothing in the code marks them, so there is no way to run just the smoke tests. The harness calls this a phantom suite.</li>
<li><strong>Tests lock bugs in as the right answer.</strong> This is the most dangerous of the three.</li>
</ul>
<h4 id="the-biggest-risk-is-oracle-strength">The biggest risk is oracle strength<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#the-biggest-risk-is-oracle-strength"><span class="icon icon-link"></span></a></h4>
<p>The rule a test uses to decide what counts as success is called its oracle. Research from 2025 onward keeps pointing to weak or wrong oracles as the biggest risk in LLM-generated tests.</p>
<p>LLMs tend to write assertions from <strong>what the current implementation actually returns</strong>, not from the spec. If the code has a bug, you get a test that enshrines the bug as correct, and that test hides it behind a green check. On top of that, LLMs are worse at judging whether their own oracles are right than they are at producing them.</p>
<p>So the harness does three things. It <strong>decomposes</strong> tests along a layer taxonomy, has a <strong>human approve</strong> every application, and <strong>re-checks oracles against the acceptance criteria and actually runs</strong> the result.</p>
<h3 id="two-axes-methodology--layer">Two axes: methodology × layer<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#two-axes-methodology--layer"><span class="icon icon-link"></span></a></h3>
<h4 id="four-methodologies">Four methodologies<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#four-methodologies"><span class="icon icon-link"></span></a></h4>
<ul>
<li><strong>Smoke</strong> — broad and shallow. The checkpoint right after a deploy that asks, "Is this build worth testing further?"</li>
<li><strong>Sanity</strong> — narrow and deep. This harness uses it to run the pages and components related to a change before the PR.</li>
<li><strong>Regression</strong> — broad and deep. Confirms existing behavior has not broken.</li>
<li><strong>Nightly</strong> — a full run on a schedule. The safety net for what selective runs miss.</li>
</ul>
<p>The harness goes out of its way to state two things.</p>
<p>First, the ISTQB glossary treats <strong>smoke and sanity as synonyms</strong>. "Smoke is broad and shallow, sanity is narrow and deep" is an industry convention, not a standard.</p>
<p>Second, <strong>nightly is not a test type but an axis of <em>when</em> to run</strong>. Neither ISTQB nor ISO defines a nightly test type.</p>
<p>The harness uses the conventional names but always writes these facts into the plan.</p>
<h4 id="three-layers">Three layers<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#three-layers"><span class="icon icon-link"></span></a></h4>
<ul>
<li><strong>Unit</strong> — "Is this function or decision logic right?" Fast, cheap, and precise about the cause, but it gives little confidence that parts work together.</li>
<li><strong>Integration</strong> — "Do modules, components, and APIs work together?" The balance point between speed and confidence.</li>
<li><strong>E2E</strong> — "Does the whole user journey work?" The highest confidence, but slow, expensive, flaky, and hard to diagnose. So it is kept to a few critical journeys.</li>
</ul>
<h4 id="seven-cards-instead-of-a-12-cell-grid">Seven cards instead of a 12-cell grid<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#seven-cards-instead-of-a-12-cell-grid"><span class="icon icon-link"></span></a></h4>
<p>Four methodologies times three layers gives twelve cells. In an early version (0.2.0) I actually wrote a criteria document for each of the twelve.</p>
<p>But the two axes are independent (orthogonal). ISO/IEC/IEEE 29119-1:2022 defines regression as "a design and execution choice, not a test level." A layer is a fixed property of a single test, while a methodology is a selection on top of it — "which bundle do we pick it into" — so one test can belong to several methodologies at once. The twelve cells are not mutually exclusive buckets, just the points where the two axes cross.</p>
<p>So from 0.3.0 on I replaced them with <strong>seven axis cards: four methodology cards and three layer cards</strong>. Instead of pre-filling twelve cells, the harness combines the two cards it needs at the moment it routes an acceptance criterion. Each card spells out which criteria it includes and excludes, how strong the oracle must be, and how it is separated in real code.</p>
<p>Not every combination is useful, so the harness grades them honestly.</p>

































<table><thead><tr><th>Layer \ Methodology</th><th>Smoke</th><th>Sanity</th><th>Regression</th><th>Nightly</th></tr></thead><tbody><tr><td>Unit</td><td>Weak</td><td>Degenerate</td><td><strong>Strong</strong> (highest oracle risk)</td><td>Empty</td></tr><tr><td>Integration</td><td><strong>Strong</strong></td><td>Degenerate</td><td><strong>Strong</strong></td><td>Fairly strong</td></tr><tr><td>E2E</td><td>Conditionally strong (real API only)</td><td>Not created</td><td><strong>Strong</strong></td><td>Strongest by the evidence, but not created</td></tr></tbody></table>
<p>Weak or degenerate combinations are left empty rather than forced. Unit tests, for example, already run in full at the PR stage, so a nightly-only unit test means nothing. Regression × Unit is the strongest combination and also the one most at risk of "locking a bug in as correct," so its oracle checks are especially strict. E2E nightly fits best by the evidence, but I chose not to create it as an operating decision — more on that below.</p>
<h4 id="three-presets-matched-to-the-repository">Three presets matched to the repository<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#three-presets-matched-to-the-repository"><span class="icon icon-link"></span></a></h4>
<p>The harness reads the repository and recommends one of three presets, with its reasons.</p>
<ul>
<li><strong>Trophy-lean</strong> — frontend and component-heavy. Thick integration, unit only for decision logic, E2E only for essential journeys. Recommended when it sees React, Vue, or Svelte with Testing Library.</li>
<li><strong>Google-pipeline</strong> — large codebases and monorepos. Fast, unit-heavy checks before the PR; broader runs after merge. Recommended when it sees workspaces or affected-test selection.</li>
<li><strong>Contract-honeycomb</strong> — distributed services. Contract tests between services and integration at the center, E2E close to zero. Recommended when it sees OpenAPI, proto, or contract-testing tools.</li>
</ul>
<p>None of the presets sets a ratio like "70% unit, 20% integration, 10% E2E." Even Fowler, who popularized the test pyramid, said the numbers themselves don't matter, and the Testing Trophy and Honeycomb are expert rules of thumb rather than experimentally proven optima. A preset only suggests where the weight should sit.</p>
<h3 id="the-flow-five-phases-and-three-approval-gates">The flow: five phases and three approval gates<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#the-flow-five-phases-and-three-approval-gates"><span class="icon icon-link"></span></a></h3>



































<table><thead><tr><th>Phase</th><th>What happens</th><th>Gate</th></tr></thead><tbody><tr><td>Phase 0 Initial inquiry</td><td>Ask where the acceptance criteria come from; detect test runners, mock tools, test id conventions, etc.</td><td>—</td></tr><tr><td>Phase 1 Composition</td><td>Recommend a preset and let the user pick methodologies and layers with checkboxes</td><td>Scope fixed</td></tr><tr><td>Phase 2 Plan</td><td>Route each criterion through card combinations into a layered plan and a CI placement table</td><td><strong>A: plan approval</strong></td></tr><tr><td>Phase 3 Individual application</td><td>One test at a time: draft → check → approve → write file → run</td><td><strong>B: individual approval</strong></td></tr><tr><td>Phase 4 Re-check</td><td>Overall summary and full run, then final confirmation</td><td><strong>C: final commit</strong></td></tr></tbody></table>
<p>None of the three gates can be skipped. No individual application without plan approval, no file writes without individual approval, no confirmation without final approval. The skill's default tool permissions are read and search only, so file writes and runner executions go through the usual permission prompts every time.</p>
<h4 id="phase-0-always-ask-where-the-criteria-come-from">Phase 0: always ask where the criteria come from<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#phase-0-always-ask-where-the-criteria-come-from"><span class="icon icon-link"></span></a></h4>
<p>The first live run was on this very blog repository. The most common mistake it exposed was the agent digging through the repository and inventing candidate criteria without asking — even though the user might already have an authoritative criteria document.</p>
<p>So Phase 0 always presents three options and waits: (a) paste them into the chat, (b) give a file or link path, or (c) none. Only on (c) does it look for candidates in the repository's PRDs, stories, and existing test titles, propose them, and confirm again. If the first request already includes the criteria, it does not ask again.</p>
<p>At the same point it reads the repository: which runners exist and which are missing, whether there is a tool that intercepts network requests, whether existing tests call real external APIs, what test id attribute the team uses, and whether there are candidate environments for E2E. For environment variables it reports key names only and never prints their values.</p>
<h4 id="phase-1-only-build-inside-what-was-chosen-scope-guard">Phase 1: only build inside what was chosen (scope guard)<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#phase-1-only-build-inside-what-was-chosen-scope-guard"><span class="icon icon-link"></span></a></h4>
<p>The user picks methodologies and layers with checkboxes, pre-checked according to the recommended preset. Layers without a runner are marked "runner needs to be added."</p>
<p>The chosen (methodology × layer) set becomes the fence for every later step. The harness calls this the <strong>scope guard</strong> and treats it as seriously as the three gates. If a criterion would naturally be an E2E test but the user did not choose E2E, the harness either pushes it down to integration or marks it "out of scope — not added" and asks whether to widen the scope. It never adds tests on its own.</p>
<h4 id="phase-2-one-criterion--several-layers">Phase 2: one criterion = several layers<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#phase-2-one-criterion--several-layers"><span class="icon icon-link"></span></a></h4>
<p>An acceptance criterion is not equated with a single test. The harness slices it, sends calculation and decision logic to unit, collaboration between modules and APIs to integration, and only critical user journeys to E2E. The principle: "every E2E test can be an acceptance test, but not every acceptance test needs to be E2E." Given-When-Then maps directly to Arrange-Act-Assert at any layer, so the layer is decided by "what do we isolate and what do we use for real."</p>
<p>Next, each slice gets methodology memberships. Most are regression; deterministic, critical happy paths are smoke; anything slow, expensive, or flaky is deferred to nightly.</p>
<p>Each row of the plan holds the criterion ID, the layer, the methodology and the command that selects that bundle, combination strength, the API boundary (mock or real, and where the fake responses come from), how screen elements are located, the oracle, the planned test file path, a Given-When-Then summary, and the supporting card. A CI placement table and the list of run scripts to be added are attached, and everything is approved <strong>in one go</strong>. No file is created before approval.</p>
<h4 id="phase-3-one-test-at-a-time">Phase 3: one test at a time<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#phase-3-one-test-at-a-time"><span class="icon icon-link"></span></a></h4>
<p>The approved plan is worked through row by row, not in parallel. Each test follows this order.</p>
<ol>
<li><strong>Oracle pre-check</strong> — Is the assertion a copy of what the current implementation returns, or does it verify what the acceptance criterion requires? If it copies the implementation, the expectation is re-derived from the criterion; if it is unclear, the harness asks, "Is this expectation correct?" Before the first test, it also looks at existing flaky tests in that area, because feeding flaky tests in as context spreads the flakiness to new ones.</li>
<li><strong>Draft and self-check</strong> — It checks the file location, traces of real API calls, the order used to find screen elements, and whether tags and criterion IDs follow the rules. It does not include assertions that cannot fail, such as reading back a value it just set.</li>
<li><strong>Gate B</strong> — The user chooses "apply / apply after edits / skip this test only / stop here." The file is written only on approval.</li>
<li><strong>Run</strong> — The harness actually runs the applied test and shows the runner output rather than its own claim. If it fails, it separates "the test is wrong" from "the code violates the criterion" and asks what to do next. It also checks that the test passes on correct code (not a false alarm), and runs the selection to confirm the new tags pull this test into its bundle and not into others.</li>
</ol>
<p>If the user stops midway, only what has been applied so far is kept and the flow moves to the final phase.</p>
<h4 id="phase-4-re-check-and-confirm">Phase 4: re-check and confirm<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#phase-4-re-check-and-confirm"><span class="icon icon-link"></span></a></h4>
<p>The harness summarizes applied, skipped, and failed tests, the distribution across layers and bundles, suspected code defects, and anything still unverified, then asks one last time whether to confirm. If the user asks to roll back a particular test, only that file change is reverted.</p>
<h3 id="the-rules-it-keeps">The rules it keeps<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#the-rules-it-keeps"><span class="icon icon-link"></span></a></h3>
<h4 id="unit-and-integration-never-call-real-apis">Unit and integration never call real APIs<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#unit-and-integration-never-call-real-apis"><span class="icon icon-link"></span></a></h4>
<p>Unit and integration tests are always mocked, no exceptions. The moment a test goes out to the real network it is no longer a unit or integration test. The harness prefers tools that intercept requests at the network boundary (MSW, nock, and the like); when none exist it falls back to replacing the module itself, and writes down in the plan what that leaves unverified, such as request assembly or error mapping.</p>
<p>Fake responses (fixtures) are sourced in three steps: reuse what the repository already has; otherwise ask the user for a real response sample; otherwise derive one from the schema or types and label it "not captured from a real response." The harness never calls a real API to create a fixture. Copying fixture values straight into the expected values is also forbidden — a fixture is a precondition (Given), not the answer.</p>
<p>After writing, it statically checks for leftover external URLs or un-mocked HTTP calls, while also stating the limit: passing that check does not prove the test never touches the network.</p>
<blockquote>
<p><strong>A passing mock is not a working integration.</strong> A fixture is a snapshot of the moment it was captured, so the test stays green even after the real API changes. The output always notes that the only thing that confirms integration is an E2E run against the real API.</p>
</blockquote>
<h4 id="e2e-is-smoke-and-regression-only-and-smoke-sits-inside-regression">E2E is smoke and regression only, and smoke sits inside regression<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#e2e-is-smoke-and-regression-only-and-smoke-sits-inside-regression"><span class="icon icon-link"></span></a></h4>
<p>E2E tests are created only as smoke and regression. No nightly or sanity-only E2E. The cost is written down too: with nowhere to defer cross-browser or large E2E runs, regression E2E itself must be narrowed to critical journeys.</p>
<p>Smoke is a subset of regression. A smoke test carries both the smoke and the regression tag. The same scenario is never duplicated into a mock file and a real-API file; the run mode is expressed only as a tag on the existing test. By default E2E tests carry the mock-mode tag and run deterministically in CI; only scenarios the user points to get the real-API tag as well and are run by hand.</p>
<h4 id="e2e-smoke-runs-against-the-real-api-only--and-what-that-costs">E2E smoke runs against the real API only — and what that costs<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#e2e-smoke-runs-against-the-real-api-only--and-what-that-costs"><span class="icon icon-link"></span></a></h4>
<p>This is where the harness is most opinionated. <strong>E2E smoke runs against the real API only, even if nobody asks.</strong> Passing smoke on mock data cannot answer smoke's actual question: "Is what we deployed really alive?" In exchange, it is not placed in any fixed CI stage (PR, post-deploy, nightly) and lives only as a manual run recipe.</p>
<p>This is an operating decision that directly conflicts with the usual advice that "a gate that blocks deploys must be deterministic and free of external dependencies" (MinimumCD, Fowler). So the harness does not dress it up as evidence-based; it writes it into the output as is. <strong>E2E smoke is not an automated deploy gate but a manual checkpoint a person runs before promotion.</strong> A pass against the real API is also only an observation of "it passed at this time, in this environment," not a permanent guarantee of integration.</p>
<p>In 0.5.0 the rule was the exact opposite: "E2E smoke never gets a real-API mode." When I reversed it in 0.6.0, I changed the rule without hiding the fact that it conflicts with the evidence.</p>
<h4 id="the-only-exception-for-calling-a-real-api-and-its-conditions">The only exception for calling a real API, and its conditions<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#the-only-exception-for-calling-a-real-api-and-its-conditions"><span class="icon icon-link"></span></a></h4>
<p>The only time the harness itself calls a real API is when running E2E smoke, and even then three things must all be in place: the target environment URL, test accounts and seed data (or confirmation that none are needed), and <strong>approval to run, given on the spot</strong>. Approving the plan is not treated as approving the run.</p>
<ul>
<li>If the target is production, it asks once more.</li>
<li>Journeys with side effects — payments, sending messages, deletions, billing — are asked about one by one.</li>
<li>Secret values are never accepted in the chat; only environment variable or secret key names are handled.</li>
<li>Data created by the tests is not deleted by the harness on its own; it is reported as left behind.</li>
<li>Failures are split three ways: test defect, code defect, and <strong>environment or external cause</strong> (not deployed, expired auth, rate limits, upstream outage), so that environment problems are not blamed on the code.</li>
<li>If the conditions are not met and it cannot run, the recipe stays <strong>UNVERIFIED</strong>. "I created a run recipe" is never reported as "I verified it."</li>
</ul>
<h4 id="sanity-is-a-selection-lane-not-an-axis-for-new-tests">Sanity is a selection lane, not an axis for new tests<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#sanity-is-a-selection-lane-not-an-axis-for-new-tests"><span class="icon icon-link"></span></a></h4>
<p>In the combination table above, sanity is "degenerate" everywhere. That means "no new sanity-only tests," not "no sanity." In this harness, sanity is <strong>a selection lane that picks existing tests by change scope and runs them before the PR</strong>.</p>
<p>The targets widen in three steps: the changed files, the parent pages and components that import them, and — if E2E was chosen — the mock E2E tests for the related pages. If the mapping is uncertain, the scope widens to everything rather than narrowing. In the PR job, unit and integration failures block, while mock E2E only reports.</p>
<p>No sanity tag is planted in the code. New tests are created only when a changed target has no tests at all, and the CI config file is never edited directly — the harness only proposes what to add. This placement and blocking policy, too, is labeled as an operating decision rather than a standard.</p>
<h4 id="find-screen-elements-the-way-users-do">Find screen elements the way users do<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#find-screen-elements-the-way-users-do"><span class="icon icon-link"></span></a></h4>
<p>Tests that query the screen try a fixed ladder from the top.</p>
<ol>
<li><strong>Visible elements and interaction</strong> — role (button, link, …) with name → label → placeholder → visible text → current value</li>
<li><strong>HTML and ARIA attributes</strong> — image alt text → title attribute</li>
<li><strong>Test ID</strong> — only when the above cannot find it</li>
<li><strong>Last resort</strong> — an arbitrary CSS selector</li>
</ol>
<p>Every step down requires a reason why the step above cannot work. "It's easier to write" is not a reason. A few more details:</p>
<ul>
<li><strong>Runners name things differently.</strong> Testing Library and Playwright use different names for the same concepts, and Playwright has no query that finds by current value at all. The harness never calls an API that doesn't exist; when it needs to pin down a value, it finds the element with a higher-ranked query and checks the value with an assertion.</li>
<li><strong>The test id attribute name is the team's call.</strong> The harness does not invent one; it detects it in the repository and asks if there is none or several are mixed. Adding a new test id to product code is a change outside the test files, so it gets separate approval.</li>
<li><strong>The last resort is allowed, but its coupling cost is written down.</strong> Locating by an analytics attribute ties the test to a contract made for another purpose; locating by part of a CSS module class name ties it to a build hash, an implementation detail. When their owners change them, the test breaks. The harness flags the risk, and the user decides.</li>
</ul>
<p>This ladder reflects the design intent of the official Testing Library guide, not experimentally proven superiority. So the harness does not score compliance or claim numbers like "finding by role cuts flakiness by X%." And picking a good selector does not make the oracle stronger; the two are separate checks.</p>
<h4 id="always-in-a-__test__-folder-next-to-the-target">Always in a __test__ folder next to the target<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#always-in-a-__test__-folder-next-to-the-target"><span class="icon icon-link"></span></a></h4>
<p>Unit and integration tests go into a __test__ folder created right in the folder of the file under test. Even if the repository has another convention (a plural folder name, a separate test folder, files right next to the source), this rule applies without exception.</p>
<p>At first there was an exception: "follow the existing convention if there is one." In practice that exception became a loophole, and tests occasionally appeared next to the source with no folder. In 0.4.1 I removed the exception and made the harness check the path three times — before, during, and after writing. E2E has its own runner and folder conventions, so its path is asked for separately when the layer is chosen.</p>
<h4 id="criterion-ids-in-test-titles">Criterion IDs in test titles<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#criterion-ids-in-test-titles"><span class="icon icon-link"></span></a></h4>
<p>Every smoke and regression test starts its title with the acceptance criterion ID, so the code itself shows which criterion a test verifies.</p>
<p>Smoke and regression contain only tests grounded in acceptance criteria. Tests needed outside the criteria, such as performance or fuzzing, can live without an ID only in nightly or sanity, and even then the plan records a reason and they are approved separately. If the input criteria have no IDs, the harness first gets approval for a numbered mapping table, and never invents IDs that are not in the input. If there is a test you want in smoke but no matching criterion, the harness does not invent the test; it asks whether to add the criterion (a planning decision).</p>
<h4 id="suites-must-exist-in-code">Suites must exist in code<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#suites-must-exist-in-code"><span class="icon icon-link"></span></a></h4>
<p>Writing "smoke" in a plan does nothing on its own. The harness attaches tags in the code using what the runner provides natively (Playwright and Vitest tags; for Jest, which lacks native tags, title conventions or project separation), adds per-bundle run scripts, and then runs those commands to confirm this test is selected and others are not. A test that the plan places in a bundle but that carries no tag in code is rejected. If the runner cannot do tags, the harness does not pretend; it downgrades the bundle to "a label only, not real run separation."</p>
<p>When E2E is in scope, it confirms six isolation conditions from actual run output. In short: "the smoke and regression lists that run in CI contain no real-API tests," "smoke E2E has no mock tag and does have the regression tag," "nightly has no E2E," and "the same scenario is not duplicated in files that differ only by mode."</p>
<h3 id="honesty-principles">Honesty principles<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#honesty-principles"><span class="icon icon-link"></span></a></h3>
<p>The part of this harness that took the most work was not a feature but the list of things <em>not</em> to say.</p>
<ul>
<li>It does not set layer ratios like 70/20/10.</li>
<li>It does not hide that smoke and sanity are synonyms in the standard.</li>
<li>It does not cite unsupported effect numbers like "smoke catches 80% of critical bugs early" or "switching to mocks cuts flakiness by N%."</li>
<li>It does not claim that prioritizing test order reduces CI cost. Only the order changes; the total amount of execution stays the same. What reduces cost is selection, batching, and parallelism.</li>
<li>It never reports a mock pass as verified integration, or an unexecuted test as passing.</li>
<li>Things that are operating decisions or design intent rather than evidence — sanity's PR placement, the real-API-only rule for E2E smoke, the selector ladder — are labeled as such.</li>
<li>Every conclusion carries a confidence level (high, medium, low) and a source.</li>
</ul>

<p>Looking back, most changes came from "in real use, it slipped out this way": inventing criteria instead of asking, folder rules collapsing through an exception clause, suites that existed in the plan but not in the code. Each time I added a rule, I tried to also write down what it makes us give up.</p>
<h3 id="wrapping-up">Wrapping up<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#wrapping-up"><span class="icon icon-link"></span></a></h3>
<p>Generating tests is already something agents do well. What is left for people is judging "what does this test treat as the right answer" and "at which layer and at what point should this test run," and this harness is designed to put those judgments in front of a person every time. Three approvals can feel tedious, but I think they are cheap compared with finding a test that enshrined a bug months later.</p>
