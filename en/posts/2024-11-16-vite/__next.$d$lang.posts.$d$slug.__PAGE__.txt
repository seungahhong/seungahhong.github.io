10:T2e661,<h2 id="why-you-should-use-vite">Why You Should Use Vite<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#why-you-should-use-vite"><span class="icon icon-link"></span></a></h2>
<h4 id="problems-with-traditional-module-bundlers">Problems with Traditional Module Bundlers<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#problems-with-traditional-module-bundlers"><span class="icon icon-link"></span></a></h4>
<ul>
<li>
<p>Before browsers natively supported ES Modules (Native ESM), JavaScript modularization could not be handled at the browser level. To support such source modules in the browser, we had to merge multiple files or group them into meaningful units using modularization syntax such as require/IIFE/import/export. This is called bundling, and today <a href="https://webpack.js.org/"><strong>Webpack</strong></a>, <a href="https://rollupjs.org/"><strong>Rollup</strong></a>, and <a href="https://parceljs.org/"><strong>Parcel</strong></a> are the tools that provide it.</p>
</li>
<li>
<p>However, as applications grew increasingly sophisticated, JS tools began to hit performance bottlenecks. Even with HMR, applying changed files could take several seconds, which hurt developer productivity.</p>
</li>
<li>
<p>ESM (ECMAScript Modules)</p>
<ul>
<li>ESM refers to a module approach in which the modularization syntax <code>import</code> and <code>export</code> can be handled by the browser itself, without any separate tooling. If you run code like the following in a browser without a bundler such as Webpack, an error occurs.</li>
</ul>

<h4 id="vites-characteristics">Vite's Characteristics<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#vites-characteristics"><span class="icon icon-link"></span></a></h4>
<ul>
<li>
<p>Performance improvements for cold-start dev server startup
<img src="/blog-assets/2024/11/assets/16/Untitled1.png" alt="Untitled"></p>
<ul>
<li>
<p>Dependencies: Provides a pre-bundling feature using esbuild for source code whose contents do not change, such as node_modules</p>
<ul>
<li>
<p>esbuild delivers speeds 10-100x faster than traditional bundlers like webpack and parcel</p>
</li>
<li>
<p>esbuild pre-bundles all packages in node_modules and serves and caches them as shown below</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="tsx" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="tsx" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#66707B;--shiki-dark:#BDC4CC">// Dependencies package import 할 경우</span></span>

<span data-line=""> </span>
<span data-line=""><span style="--shiki-light:#66707B;--shiki-dark:#BDC4CC">// vite esm 지원을 위한 변환/캐싱</span></span>
<span data-line=""><span style="--shiki-light:#032563;--shiki-dark:#ADDCFF">/node_modules/</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">.vite</span><span style="--shiki-light:#A0111F;--shiki-dark:#FF9492">/</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">deps</span><span style="--shiki-light:#A0111F;--shiki-dark:#FF9492">/</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">dayjs.js</span><span style="--shiki-light:#A0111F;--shiki-dark:#FF9492">?</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">v</span><span style="--shiki-light:#A0111F;--shiki-dark:#FF9492">=</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">b09621d8</span></span></code></pre></figure>
</li>
</ul>
</li>
<li>
<p>Source code: Applies the Native ESM approach so the browser imports, transforms, and serves modules directly
<img src="/blog-assets/2024/11/assets/16/Untitled2.png" alt="Untitled"></p>
</li>
</ul>
</li>
<li>
<p>HMR performance improvements
With traditional bundlers, changing source code required re-running the entire bundling process, which caused slow performance. By using the Native ESM approach and swapping only the changed module, performance is improved.
It also leverages HTTP headers to improve page load speed (minimizing the number of requests).</p>
<ul>
<li>304 Not Modified: Uses the client cache</li>
<li>Cache-Control: Uses caching via max-age=31536000, immutable</li>
</ul>
</li>
<li>
<p>Uses Rollup in production</p>
<ul>
<li>Although esbuild boasts the fastest performance, its ecosystem is still lacking and its stability for browser bundling is considered weaker, so Vite uses the Rollup bundler in production (providing performance benefits such as tree shaking, lazy loading, and file splitting).</li>
<li>Rollup switched its parser to SWC in v4, and work is underway to build Rolldown, a Rust port. Once development is complete, it will be able to fully replace esbuild (with the goal of eliminating the mismatch between development and build).</li>
<li><a href="https://www.youtube.com/watch?v=EKvvptbTx6k">https://www.youtube.com/watch?v=EKvvptbTx6k</a></li>
</ul>
</li>
</ul>

<p><strong>Setting the Stage with Vite Installation</strong>
<strong>vite: A modern web project build tool</strong></p>
<ul>

<li>vite-tsconfig-paths: Enables the path aliases configured in the tsconfig.json file to also be applied in Vite. With vite-tsconfig-paths, the path aliases defined in the TypeScript configuration are recognized by Vite as well and can be used when resolving module paths</li>
<li>vite-plugin-svgr
<ul>
<li>A Vite plugin that converts SVGs into React components</li>
<li>However, installing a version later than 3.3.0 causes build and type errors (with 3.3.0 you can convert an SVG to a React component as shown below)</li>

<p><strong>Update tsconfig.json</strong>
Reasons to use isolatedModules</p>
<ul>
<li><strong>Isolating dependencies between modules</strong>: Ensures each module does not depend on the types of others, so modules are processed individually at compile time. This can reduce TypeScript's compilation time.</li>
<li><strong>Performance improvement</strong>: Compiling modules independently means only the modules that changed are recompiled, improving overall compilation speed.</li>
<li><strong>ESM compatibility</strong>: Increases compatibility with ES modules, providing better results when integrating with various build tools.</li>
<li><strong>Preventing check errors</strong>: Since every module is checked individually, a type error in one module is prevented from affecting other modules.
Configure the vite.config.js path in <code>include</code>.</li>
</ul>

<p><strong>Summary of error cases by step</strong>
The "@forward rules must be written before any other rules" error</p>
<ul>
<li>Fix it so that the @forward statement is placed above all other rules (@import, @use, style declarations)
@forward</li>
<li>Part of the Sass module system introduced in Dart Sass, it plays an important role in structuring and managing modularized stylesheets.</li>
<li>Unlike the @import approach, @forward makes it easier to manage the modularization and reusability of Sass code.
@use: imports a module while using a namespace to prevent conflicts, and lets you explicitly import only the parts you need.
@import simply includes a file, which can be included multiple times and carries the risk of variable or mixin conflicts.</li>
</ul>

<p><strong>external file link settings(alias)</strong>
In CRA, when accessing a path inside an external file (tsconfig.json), the path is resolved relative to the current project environment, but in VITE the path is accessed relative to the external file. This causes issues with alias handling, so you need to reassign it as an absolute path instead of a tsconfig path.
e.g.)</p>
<ul>
<li>CRA(root)
<ul>
<li>Based on the location of the outside/index.tsx component</li>
</ul>
</li>
<li>VITE
<ul>
<li>Based on the root location</li>
</ul>
</li>

<p><strong>setting baseurl for Vite</strong>
In CRA, resource paths are set internally based on the BaseURL (PUBLIC_URL), but in VITE you need to change that path to the <code>base</code> property value. (Specify the base url path in an env variable.)
However, in the DEV environment you should use the internal resource path, so do not specify a path.</p>

<p><strong>Installation</strong>
Remove the previous version of Storybook.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="bash" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="bash" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#702C00;--shiki-dark:#FFB757">yarn</span><span style="--shiki-light:#032563;--shiki-dark:#ADDCFF"> remove</span><span style="--shiki-light:#032563;--shiki-dark:#ADDCFF"> @storybook/addon-</span><span style="--shiki-light:#023B95;--shiki-dark:#91CBFF">*</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">(</span><span style="--shiki-light:#702C00;--shiki-dark:#FFB757">knobs,</span><span style="--shiki-light:#032563;--shiki-dark:#ADDCFF"> controls,</span><span style="--shiki-light:#032563;--shiki-dark:#ADDCFF"> etc.</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">)</span></span></code></pre></figure>
<p>Add the Storybook packages for Vite integration.
In the existing CRA environment, using the @storybook/react package command worked fine, but with VITE you use the @storybook/react-vite package and need to install the storybook package additionally.
Also, if you use version 6 of the Storybook integration packages, you will encounter an error like 'storybook-channel-mock.js:7 Uncaught TypeError: import_channels.default is not a constructor'.
Be sure to install the latest packages, version 8 or higher.</p>

<h2 id="jest-to-vitest-migration">Jest to Vitest Migration<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#jest-to-vitest-migration"><span class="icon icon-link"></span></a></h2>
<ul>
<li>
<p><strong>Why Vitest is better than Jest</strong></p>
<ol>
<li><strong>Fast performance</strong>: esbuild-based, so tests run faster than Jest. (jest: Babel)</li>
<li><strong>ESM support</strong>: Natively supports modern ES modules. (Jest can support the ES approach, but compatibility issues arise)</li>
<li><strong>TypeScript integration</strong>: Integrates naturally with TypeScript without additional configuration.</li>
<li><strong>Simple mocking API</strong>: Provides intuitive and easy-to-use mocking features.</li>
<li><strong>Compatibility with Vite</strong>: Reuses your Vite configuration and plugins as-is.</li>
<li><strong>Modern features</strong>: Supports HMR and a fast watch mode.</li>
<li><strong>Small learning curve</strong>: Configuration familiar to Vite users.</li>
<li><strong>Excellent developer experience</strong>: Modern and detailed error reporting and test feedback.</li>
</ol>
</li>
