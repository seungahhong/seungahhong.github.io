<h2 id="concurrent-features">Concurrent Features<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#concurrent-features"><span class="icon icon-link"></span></a></h2>
<h3 id="starttransition">startTransition<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#starttransition"><span class="icon icon-link"></span></a></h3>
<p>Before introducing transition updates, let's take a look at React's state updates.</p>
<ul>
<li><strong>Urgent updates</strong>: reflecting direct interactions (typing, hovering, scrolling, etc.)
<ul>
<li>This is the area where users feel something is wrong if it isn't updated immediately in response to their input (frozen screen, lag, etc.).</li>
</ul>
</li>
<li><strong>Transition updates</strong>: UI transitions from one view to another
<ul>
<li>This is the area where users don't expect it to appear on screen instantly.</li>
</ul>
</li>
</ul>
<p>Up until React 17, there was no way to specify urgent vs. transition updates, so all state was updated as urgent updates.</p>
<p>The problem was that even when a transition update became slow because the user's device was low-performance or the network was slow, it should not interfere with urgent updates, but versions before 17 had the issue of it interfering.</p>
<p>To work around this issue, techniques like setTimeout, throttle, and debounce were the best available options.</p>
<p>From React 18 onwards, the startTransition API is provided, giving you a way to explicitly designate urgent updates vs. transition updates.</p>

<h3 id="usetransition-vs-usedeferredvalue">useTransition vs useDeferredValue<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#usetransition-vs-usedeferredvalue"><span class="icon icon-link"></span></a></h3>
<ul>
<li>Use useTransition when you have control over the state, and use useDeferredValue when you only have access to a value via props.</li>
</ul>
<h2 id="suspense-support-for-server-side-rendering">Suspense Support for Server-Side Rendering<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#suspense-support-for-server-side-rendering"><span class="icon icon-link"></span></a></h2>
<p>The existing React SSR went through the following 4 steps.</p>
<ul>
<li>The server fetches the data for the entire app. (Data Fetching)</li>
<li>Then, the server renders the entire app to HTML and sends it as the Response.</li>
<li>Then, the client loads the JavaScript code for the entire app.</li>
<li>Then, the client connects the entire app's HTML generated on the server with the JavaScript logic. (Hydration)</li>
</ul>
<p>The important point is that each step had to be completed for the entire app before it could move on to the next step, so if a delay occurred at any step, the user would see a blank screen, resulting in a poor UX experience.</p>
<p>Deriving the problems</p>
<ul>
<li>When data fetching required to render a specific component takes a long time</li>
<li>When a specific component has a large amount of code and takes a long time to load</li>
<li>When a specific component's logic is complex and takes a long time</li>
</ul>
<p>From React 18 onwards, you can wrap expensive-to-render sub-components in Suspense so they proceed without blocking the Hydration of the entire app. (The sub-components later hydrate independently.)</p>
<p>To use Suspense, you must use the renderToPipeableStream function.</p>
<ul>
<li>renderToString(React.Node): string: Be able to run ( Limited support Suspense)</li>

<h2 id="usesyncexternalstore">useSyncExternalStore<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#usesyncexternalstore"><span class="icon icon-link"></span></a></h2>
<p>As React 18 comes to support Concurrent reads, this is a new hook that forcibly synchronizes and updates an external store.</p>
<ul>
<li>External Store: An external store refers to state that is managed and subscribed to outside of React rather than inside it. Examples include redux, mobx, global variables, and DOM state.</li>
<li>Internal Store: Refers to state used inside React. Examples include props, context, useState, and useReducer.</li>
<li>tearing: When a single piece of state affects multiple UIs, tearing refers to the UI looking different because the update speed differs from component to component.</li>
</ul>
<p>Before React 18, since it was impossible to pause/defer rendering, there was no problem because whenever state was updated the screen would always change unconditionally.</p>
<p>From React 18 onwards, with the arrival of Concurrent rendering, when a pause/defer occurs, updates can differ from component to component, causing the problem of showing different values.</p>
<p>To solve this issue, React 18 provides the useSyncExternalStore hook, making it possible to always keep the UI consistent.</p>
<p><img src="/blog-assets/2022/06/images/08/Untitled2.png" alt="Untitled"></p>
<p>Tearing: the mismatch between external store data and the screen</p>
<p><img src="/blog-assets/2022/06/images/08/210630_fin_03_tearing.gif" alt="210630_fin_03_tearing.gif"></p>
<p>A test for tearing</p>
<p><code>useSyncExternalStore</code> takes two functions as arguments.</p>
<ul>
<li><code>subscribe</code>: the callback function to register</li>
<li><code>getSnapshot</code>: used to check whether the subscribed value has changed since it was last rendered, whether it is an immutable value like a string or number, or whether it is a cached or memoized object. Afterward, an immutable value is returned by the hook.</li>
</ul>
