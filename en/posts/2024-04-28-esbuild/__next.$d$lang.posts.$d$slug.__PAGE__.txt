1b:Tbe4e,<h2 id="characteristics-of-esbuild">Characteristics of esbuild<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#characteristics-of-esbuild"><span class="icon icon-link"></span></a></h2>
<ul>
<li><strong>Written in Go and compiled using static (native) code</strong>
There are three ways to describe how code written in a programming language is converted into machine language that a machine can understand.
<ul>
<li>Static compilation
<ul>
<li>Because the entire program is converted into machine language during compilation, the total execution time is shorter.</li>
<li>However, compilation takes a long time, and the code must be compiled differently for each platform (Mac, Windows).</li>
</ul>
</li>
<li>Interpreter
<ul>
<li>This approach reads the programming language one statement at a time and converts it into machine language. Because it converts and runs incrementally, the initial startup is fast (adopted by JavaScript).</li>
<li>However, the total execution time is slower than static compilation, and it is inefficient because it has to translate the same code the same way every time it encounters it.</li>
</ul>
</li>
<li>JIT (Just in Time)
<ul>
<li>This approach translates a statement, stores the translated result in a cache, and if it encounters the same statement again, it uses the machine code stored in the cache to execute it.</li>
<li>It uses a mix of static compilation and interpretation (V8 engine).
Because esbuild is written in Go and compiles using the static compilation approach, it can reduce the total execution time.</li>
</ul>
</li>
</ul>
</li>
<li><strong>Heavily uses parallel processing</strong>
Parallel processing is another factor that contributes to the performance improvement.
Because the JavaScript engine runs on a single thread, it can only operate on one thread, which limits processing speed.
esbuild, written in Go, uses the operating system's parallel processing and maximizes CPU usage to perform bundling, which is why it is said to be highly performant.</li>
<li><strong>Uses memory efficiently</strong>
It maximizes CPU cache usage, minimizes AST data conversion as much as possible, and reuses data.</li>
</ul>
<p>Thanks to the three characteristics above, esbuild is said to be able to compile builds about 10-100 times faster overall^^</p>

<h2 id="reasons-for-using-esbuild-loader">Reasons for Using esbuild-loader<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#reasons-for-using-esbuild-loader"><span class="icon icon-link"></span></a></h2>
<p>To improve the build speed of the service, I decided to measure the current build time to identify where most of the time is being spent, using speed-measure-webpack-plugin.</p>
<p>This plugin measures and reports the time each Loader and Plugin takes as well as the total time during a build, and you can install and use it as shown below.</p>
<ul>
<li>Loader
<ul>
<li>Performs a preprocessing step that transforms a module's source code when each file is imported or loaded during the build process</li>
<li>webpack basically understands only JS / JSON files → it performs the work of converting other web resources (HTML, CSS, Images, fonts, etc.)</li>
</ul>
</li>
<li>Plugin
<ul>
<li>While a loader is involved in the process of interpreting and transforming files, a plugin is responsible for changing the form of the resulting output</li>
<li>A feature that provides additional functionality on top of the basic behavior</li>
</ul>
</li>
</ul>

<h4 id="lets-measure-the-speed">Let's measure the speed.<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#lets-measure-the-speed"><span class="icon icon-link"></span></a></h4>
<p>After measuring, I was able to confirm that, in order of slowest build time, babel-loader, the Terser Plugin, and OptimizeCssAssetsWebpackPlugin took the longest.</p>
<ul>
<li>Summary of the Loaders and Plugins involved in the performance measurement
<ul>
<li><strong>babel-loader</strong>
<ul>
<li>Converting syntax of ES6 or higher into ES5 or lower code is called <strong>transpiling</strong>, and this is done by babel; babel-loader is what integrates this babel with webpack.</li>
</ul>
</li>
<li><strong>optimize-css-assets-webpack-plugin</strong>
<ul>
<li>If HtmlWebpackPlugin is a plugin that compresses HTML, optimize-css-assets-webpack-plugin is a plugin that compresses CSS.</li>
</ul>
</li>
<li><strong>terser-webpack-plugin</strong>
<ul>
<li>The series of operations that converts the code we write into a lighter version that provides the same functionality—such as mangling or compressing the code—is called minify or minification (code minification), and the tool that performs code minification is called a minifier. terser-webpack-plugin is a plugin that helps deliver the JavaScript code we write in a more minified state in production.</li>
</ul>
</li>
<li><strong>css-loader, postcss-loader, sass-loader</strong>
<ul>
<li><strong>postcss-loader</strong>: A tool that transforms styles through JS plugins.</li>
<li><strong>sass-loader</strong>: sass-loader is a third-party package rather than a feature managed and maintained by webpack; because browsers cannot recognize sass, it <strong>transpiles</strong> it into css.</li>
<li><strong>css-loader</strong>: Converts css files into js code.</li>
</ul>
</li>
<li><strong>IgnorePlugin</strong>
<ul>
<li>Configures the files to ignore during bundling using regular expressions or filter functions.</li>
</ul>
</li>
<li><strong>file-loader</strong>: Handles making files usable as modules. It moves the actually used files to the output directory.</li>
<li><strong>url-loader</strong>: Handles converting files into base64 urls. Rather than moving files, it converts them and stores them in the output directory.</li>
</ul>
</li>
</ul>
<h2 id="introducing-esbuild-loader-to-leverage-the-strengths-of-both-webpack-and-esbuild">Introducing esbuild-loader to Leverage the Strengths of Both webpack and esbuild<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#introducing-esbuild-loader-to-leverage-the-strengths-of-both-webpack-and-esbuild"><span class="icon icon-link"></span></a></h2>
<p>As mentioned above, it would be nice to adopt esbuild as the bundler, but esbuild does not support all of the loaders and plugins used in the existing webpack, and it is also difficult to abandon webpack, which has a wealth of reference material for when issues arise. For these reasons, I ended up adopting esbuild-loader to benefit only from esbuild's speed while keeping webpack.</p>
<p>Rather than using webpack + babel/plugin, using webpack-[esbuild-loader/minifycss] provides an alternative that can make the transpilation and Minification steps faster.</p>
