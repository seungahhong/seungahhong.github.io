1b:Ta506,<h2 id="overview">Overview<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#overview"><span class="icon icon-link"></span></a></h2>
<ul>
<li>A Data Synchronization Library for React</li>
<li>It makes fetching, caching, synchronizing, and updating <strong>server state</strong> in a React application easy.</li>
</ul>
<h2 id="server-state">Server State<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#server-state"><span class="icon icon-link"></span></a></h2>
<ul>
<li>It is stored in a remote location and is neither owned nor controlled by your app.</li>
<li>An asynchronous API is required to fetch and update the data.</li>
<li>It is shared with other people and can be updated without your knowledge.</li>
<li>The data your app uses can potentially become "out of date."</li>
</ul>
<h2 id="advantages-of-react-query">Advantages of React Query<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#advantages-of-react-query"><span class="icon icon-link"></span></a></h2>
<ul>
<li>Caching</li>
<li>Deduplication of redundant server data requests (preventing double-clicks)</li>
<li>Removing stale data in the background</li>
<li>Knowing when data becomes stale</li>
<li>Updating stale data as soon as possible</li>
<li>Performance optimization for paginated and lazy-loaded data</li>
<li>Memory management and garbage collection for server state</li>
<li>Memoization through structural sharing of query results</li>
</ul>
<h2 id="disadvantages-of-react-query">Disadvantages of React Query<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#disadvantages-of-react-query"><span class="icon icon-link"></span></a></h2>
<ul>
<li>Adds a library dependency</li>
<li>Learning curve</li>
<li>Requires understanding the query lifecycle</li>
</ul>
<h2 id="query-states">Query States<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#query-states"><span class="icon icon-link"></span></a></h2>
<p>Query data managed through React Query goes through fetching, fresh, stale, inactive, and delete states according to its lifecycle.</p>
<ul>
<li>fetching - a query that is currently being requested</li>
<li>fresh - a query that has not expired. Even when a component mounts or updates, the data is not requested again. (within staleTime)</li>
<li>stale - an expired query. When a component mounts or updates, the data is requested again. (after staleTime ends)</li>
<li>inactive - a query that is no longer in use. After a certain period of time, the garbage collector removes it from the cache. (within cacheTime)
<ul>
<li>If the site regains focus while cacheTime is still active, a stale query is triggered, but the cached data is displayed on the screen.</li>
</ul>
</li>
<li>delete - a query removed from the cache by the garbage collector (after cacheTime ends)</li>
</ul>
<h2 id="key-concepts">Key Concepts<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#key-concepts"><span class="icon icon-link"></span></a></h2>
<p>The following are the default settings that form the basis of the API provided by React Query.</p>
<ul>
<li>Data fetched with <code>useQuery</code> (and <code>useInfiniteQuery</code>) becomes stale by default.
<ul>
<li>You can extend the time it takes for data to become stale using the <code>staleTime</code> option.</li>
</ul>
</li>
<li>A stale query is refetched in the background in the following cases:
<ul>
<li>When a new query instance mounts</li>
<li>When the browser window is refocused</li>
<li>When the network reconnects</li>
<li>When the <code>refetchInterval</code> option is set</li>
</ul>
</li>
<li>Query results with no active <code>useQuery</code> or <code>useInfiniteQuery</code> instances are labeled "inactive" and remain until they are used again.
<ul>
<li>Inactive queries are released from memory after 300 seconds (5 minutes).</li>
</ul>
</li>
<li>A query that fails 3 or more times in the background is treated as an error.
<ul>
<li>Use the <code>retry</code> option to set the number of retries when the query function throws an error, and the <code>retryDelay</code> option to set the wait time between retries.</li>
</ul>
</li>
<li>Query results use structural sharing for memoization, and the data reference does not change.
<ul>
<li>This is a technique used in immutable.js. (<a href="https://medium.com/@dtinth/immutable-js-persistent-data-structures-and-structural-sharing-6d163fbd73d2">a helpful article</a>)</li>
<li>In 99.9% of cases, there is no need to turn this option off.</li>
<li>Structural sharing applies only to JSON-compatible data, and query results of other types are always considered changed.</li>
</ul>
</li>
</ul>

<h2 id="staletime-vs-cachetime">staleTime vs cacheTime<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#staletime-vs-cachetime"><span class="icon icon-link"></span></a></h2>
<p>The instance created when component A mounted had its <code>staleTime (default 0)</code> elapse, so its cache entered the <code>inactive</code> state at unmount time, and a new instance was created when component B mounted.</p>
<p>In this situation, I had misunderstood the point at which <code>cacheTime</code> and <code>staleTime</code> begin.</p>
<p><code>staleTime</code> begins the moment a query instance mounts. <code>cacheTime</code> begins after a query instance has completely unmounted and entered the <code>inactive</code> state.</p>
<p>During the staleTime that begins at mount time, the query is in an active, fresh state.</p>
<p>Then, once staleTime ends, the query is in a stale state, but cacheTime has not yet started. (Because valid data still exists on the screen, the cache timer does not run.)</p>
<p>Only once the query unmounts, the things on the screen disappear, and it enters the inactive state does cacheTime finally begin. During this cacheTime, the data truly exists as a cache, so if you call it again, you can reuse this cached data.</p>
<p>So then, what exactly is the difference between staleTime and cacheTime?</p>
<p>If we just want to use the cache, isn't cacheTime alone enough? (Can't we just use the default options of staleTime=0, cacheTime=5 minutes?)</p>
<p><code>staleTime</code> is the time it takes to change from <code>fresh -> stale</code>. <code>cacheTime</code> is the time an <code>inactive</code> query is kept in the cache.</p>
<p>This is why the defaults are <code>staleTime=0, cacheTime=5 minutes</code>.</p>
<p>By setting <code>staleTime=0</code>, every query becomes <code>stale</code> as soon as it finishes, and by default it is fetched from the server again when called again.</p>
<p>At this point, to provide a slightly faster response with cached data, React Query defaults to <code>cacheTime=5 minutes</code>, and a query that has become <code>stale</code> can be used until fresh data is fetched again from the server.</p>
<h2 id="isfetching-vs-isloading">isFetching vs isLoading<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#isfetching-vs-isloading"><span class="icon icon-link"></span></a></h2>
<p>isFetching returns true every time data is fetched, regardless of whether cached data exists.</p>
<p>isLoading returns true only when there is no cached data. (If you set the initialData option, it always returns false.)</p>
<p>Knowing the difference between the two lets you use a more appropriate loading indicator.</p>

<li><code>enabled</code> can be set to prevent a query from running automatically. Passing <code>false</code> prevents it from running automatically. Also, among the data returned by useQuery, status starts in the idle state.</li>
<li><code>refetch</code> is the feature that requests a query again <code>manually</code>. If a query error occurs, only the error is logged. To make it throw the error, you must pass the <code>throwOnError</code> property as <code>true</code>.</li>
<li>It is typically used together in cases where you do not request the query automatically, but instead trigger the request via a button click or a specific event.</li>
