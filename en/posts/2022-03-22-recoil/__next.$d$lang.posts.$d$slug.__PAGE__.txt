f:T117ea,<h2 id="what-is-recoil">What is Recoil?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#what-is-recoil"><span class="icon icon-link"></span></a></h2>
<p>Reference code (redux-toolkit vs recoil): <a href="https://github.com/seungahhong/states-todos">https://github.com/seungahhong/states-todos</a></p>
<p>Limitations of React's state management logic</p>
<ul>
<li>ContextAPI creates dependencies through coupling between parent and child
<ul>
<li>In particular, it causes re-rendering issues</li>
<li>It is not really state management (initial setup, read, write)</li>
</ul>
</li>
</ul>
<p>Why do we need Recoil?</p>
<ul>
<li>It keeps the API as React-like as possible</li>
<li>It minimizes the auxiliary libraries required for use (especially redux, mobx, redux-toolkit)
<ul>
<li>Issues that forced you to use the react-redux library in order to use redux/react are handled internally by Recoil</li>
</ul>
</li>
</ul>
<p><img src="/blog-assets/2022/03/assets/22/recoil.jpeg" alt="recoil"></p>
<ul>
<li>It breaks the dependency between parent and child, delivering data to components from an independent store.</li>
<li>In particular, you can apply atoms and selectors immediately without touching the existing logic.</li>
</ul>
<p>Recoil philosophy</p>
<ul>
<li>It manages local state in React (useState, useReducer) using a low-boilerplate API (React Hooks)</li>
</ul>

<li>Derived data is updated automatically. (selector)
<ul>
<li>If A, B ⇒ C changes, previously you had to fetch A and B data and update C manually, but with Recoil, if you specify it in a selector, it updates automatically. (components that have a dependency are updated automatically)</li>
<li>It is said to be equivalent to compute in mobx</li>
</ul>
</li>
</ul>

<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">}</span></span></code></pre></figure>
<ul>
<li>
<p>atom : the basic unit that holds data</p>
<ul>
<li>If you think of it in redux terms, it is responsible for part of the store. When you have it, you can use built-in custom hooks for the processing previously handled by reducers and actions</li>
</ul>
</li>
<li>
<p>selector</p>
<ul>
<li>It can compose atoms and other selectors</li>
<li>It creates derived state</li>
<li>When an atom it depends on is updated, it updates along with it, so there is no management burden.</li>
</ul>
</li>
<li>
<p>hooks api (atom and selector use the same api)</p>
<ul>
<li><code>[useRecoilState()](https://recoiljs.org/ko/docs/api-reference/core/useRecoilState)</code>: Use this Hook when you want to read from and write to an atom. This Hook subscribes a component to the atom.</li>
<li><code>[useRecoilValue()](https://recoiljs.org/ko/docs/api-reference/core/useRecoilValue)</code>: Use this Hook when you only want to read an atom. This Hook subscribes a component to the atom.</li>
<li><code>[useSetRecoilState()](https://recoiljs.org/ko/docs/api-reference/core/useSetRecoilState)</code>: Use this Hook when you only want to write to an atom.</li>
<li><code>[useResetRecoilState()](https://recoiljs.org/ko/docs/api-reference/core/useResetRecoilState)</code>: Use this Hook when you want to reset an atom to its default value.</li>
</ul>
</li>
<li>
<p>Usage recommendations</p>
<ul>
<li>For large-scale projects and unidirectional development, use flux</li>
<li>For small projects where multiple states and components are intertwined, use Recoil</li>
</ul>
</li>
<li>
<p>Drawbacks</p>
<ul>
<li>Debugging can be difficult (derived data updates)</li>
<li>Derived data updates can become intertwined dependently and cause an infinite loop (b=cselector cselector=b), so developer skill is required. That said, Recoil is designed to prevent infinite loops</li>
</ul>
</li>
</ul>
<p>What would have been better if I had applied Recoil to the store detail page?</p>
<ul>
<li>Because of Redux's global store, the code became somewhat complex as I applied React.memo for rendering optimization
<ul>
<li>In particular, if I had connected the screen components to atoms that matched the data they needed, the rendering optimization code probably would not have been necessary</li>
</ul>
</li>
<li>I could have reduced the Redux boilerplate code as much as possible, and it would have been easier to write with the functional components that React is promoting.</li>
</ul>

<h2 id="recoil-project-retrospective">Recoil project retrospective<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#recoil-project-retrospective"><span class="icon icon-link"></span></a></h2>
<p>Good points</p>
<ul>
<li>Previously it was inconvenient because I had to update everything manually through actions and the store, but with Recoil, when I only did a set, get was called automatically, which was convenient.</li>
<li>I liked that I didn't have to worry about immutability. (redux: spread, immer)</li>
<li>I liked that caching was provided.</li>
<li>I liked that rendering happened only where it was truly needed, so I didn't have to do things like React.memo.</li>
</ul>
<p>Disappointing points</p>
<ul>
<li>Because async is provided only in get, there were many inconveniences when setting other state. (You have to create an atom to store the state value, which increases the amount of code)</li>
<li>I used useRecoilCallback to handle snapshots, but even when I updated the state within that function, the reference was tied to the existing snapshot, so I couldn't fetch the updated data.</li>
