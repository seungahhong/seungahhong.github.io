f:T2155b,<h2 id="why-you-should-adopt-a-mocking-library">Why You Should Adopt a Mocking Library<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#why-you-should-adopt-a-mocking-library"><span class="icon icon-link"></span></a></h2>
<h3 id="current-frontend-issues">Current Frontend Issues<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#current-frontend-issues"><span class="icon icon-link"></span></a></h3>
<ul>
<li>When developing a new feature
<ul>
<li>When frontend development proceeds in parallel with backend API work</li>
<li>Frontend work items
<ul>
<li>Define the spec after discussing the API interface with the backend developer</li>
<li>Until the mocking data is ready, create sample data to build the screen components
<ul>
<li>To test against the planning/design mockups, generate sample data that matches the required conditions</li>
</ul>
</li>
</ul>
</li>
</ul>
</li>
<li>When modifying an existing feature
<ul>
<li>Frontend work items
<ul>
<li>No API integration is possible until the backend developer provides the real API</li>
<li>It is hard to analyze based only on the screens shown in the design mockups and planning documents (the screen changes depending on state values/data)
<ul>
<li>To test against the planning/design mockups, generate sample data that matches the required conditions</li>
</ul>
</li>
</ul>
</li>
</ul>
</li>
<li>Conclusion
<ul>
<li>Whether developing a new or existing feature, until the backend mock/real API is available, sample data is created within the implemented code to run tests
<ul>
<li>If the sample data/integration code is accidentally not removed, it leads to code errors and degraded service quality.</li>
<li>When the mock/real API is integrated near the end of development, testing across various situations is not carried out comprehensively, overloading the frontend workload</li>
</ul>
</li>
<li>This results in poor development scheduling and poor code quality.</li>
</ul>
</li>
</ul>
<h3 id="why-does-this-happen">Why does this happen?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#why-does-this-happen"><span class="icon icon-link"></span></a></h3>
<h4 id="when-frontend-development-proceeds-in-parallel-with-backend-api-work">When frontend development proceeds in parallel with backend API work<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#when-frontend-development-proceeds-in-parallel-with-backend-api-work"><span class="icon icon-link"></span></a></h4>
<ul>
<li>Since planning, design/BE/FE development usually proceed simultaneously, the frontend—which handles the endpoint at the completion stage of the project—faces time pressure and difficulties in progress as it has to handle API integration, sample data creation, testing, and so on</li>
</ul>
<h4 id="when-you-have-to-understand-a-feature-in-order-to-modify-an-already-developed-screen">When you have to understand a feature in order to modify an already developed screen<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#when-you-have-to-understand-a-feature-in-order-to-modify-an-already-developed-screen"><span class="icon icon-link"></span></a></h4>
<ul>
<li>When planning/design/development specifications are insufficient or the responsible person is absent
<ul>
<li>There are many obstacles to development, such as creating sample data to understand the feature and inquiring with the backend about the API</li>
</ul>
</li>
</ul>
<h3 id="what-are-we-trying-to-solve-on-the-frontend">What are we trying to solve on the frontend?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#what-are-we-trying-to-solve-on-the-frontend"><span class="icon icon-link"></span></a></h3>
<h4 id="when-frontend-development-proceeds-in-parallel-with-backend-api-work-1">When frontend development proceeds in parallel with backend API work<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#when-frontend-development-proceeds-in-parallel-with-backend-api-work-1"><span class="icon icon-link"></span></a></h4>
<ul>
<li>It would be great to develop in parallel by conforming to the API interface, without adding/modifying sample data in the actual implementation code.
<ul>
<li>In particular, it would be great if the real API could be integrated with as few problems as possible.</li>
</ul>
</li>
<li>It would be great to finish the actual frontend development before the API development is complete.</li>
</ul>
<h4 id="when-you-have-to-understand-a-feature-in-order-to-modify-an-already-developed-screen-when-developingtesting-a-screen-dependent-on-a-backend-api">When you have to understand a feature in order to modify an already developed screen (when developing/testing a screen dependent on a backend API)<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#when-you-have-to-understand-a-feature-in-order-to-modify-an-already-developed-screen-when-developingtesting-a-screen-dependent-on-a-backend-api"><span class="icon icon-link"></span></a></h4>
<ul>
<li>It would be great to be able to test the screen without changing/adding to the already implemented code.</li>
<li>It would be great to build a Mocking Server to reduce the pending time of requests to the backend for API testing.</li>
</ul>
<h2 id="lets-build-a-mock-server-on-the-frontend">Let's Build a Mock Server on the Frontend<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#lets-build-a-mock-server-on-the-frontend"><span class="icon icon-link"></span></a></h2>
<p>Let's adopt the MSW (Mock Service Worker) library to improve the currently problematic process.</p>
<p>Let's build a Mock Server based on the API spec agreed upon with the backend developer.</p>
<h3 id="other-mock-libraries-compared">Other Mock Libraries Compared<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#other-mock-libraries-compared"><span class="icon icon-link"></span></a></h3>
<p>I also reviewed other mocking libraries, but I chose the MSW library because of its low entry barrier, quick adoption, and GraphQL support.</p>
<ul>
<li>sinon
<ul>
<li>A library that helps with JavaScript testing</li>
<li>Provides various features such as Spies, Stubs, Mocks, and more</li>
<li><a href="https://sinonjs.org/#get-started">Sinon.JS - Standalone test fakes, spies, stubs and mocks for JavaScript. Works with any unit testing framework.</a></li>
</ul>
</li>
<li>nock
<ul>
<li>Used to define Mock data for HTTP requests on NodeJS</li>
<li><a href="https://www.npmjs.com/package/nock#node-version-support">npm: nock</a></li>
</ul>
</li>
</ul>
<h2 id="what-is-msw">What is MSW?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#what-is-msw"><span class="icon icon-link"></span></a></h2>
<ul>
<li>MSW (short for Mock Service Worker, <a href="https://mswjs.io/">https://mswjs.io</a>) is an API mocking library that intercepts server-bound network requests and returns a mocked response.
<ul>
<li>Service Worker: runs on a separate background thread isolated from the main thread</li>
</ul>
</li>
<li>With the MSW (Mock Service Worker) library, you can mock APIs at the network level without building a Mock server.</li>
<li>Because MSW creates mock APIs based on Service Workers, it is not dependent on the many libraries or frameworks used on the frontend and works without compatibility issues.</li>
<li>Mock API support: REST API, GraphQL API</li>
<li>Supported environments: Browser, Node</li>
</ul>

<h2 id="a-development-workflow-using-msw">A Development Workflow Using MSW<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#a-development-workflow-using-msw"><span class="icon icon-link"></span></a></h2>
<ol>
<li>Requirements handed over by the planner/designer (kick-off sharing)</li>
<li>Discuss the API spec (interface) with the backend developer (hand over the FE API requirements)</li>
<li>API spec document provided</li>
<li>Build a mock server using the MSW library</li>
<li>Proceed with FE development (including API integration)</li>
<li>Replace the existing mock server when the backend developer provides the real API</li>
</ol>
<h2 id="advantages-of-msw">Advantages of MSW<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#advantages-of-msw"><span class="icon icon-link"></span></a></h2>
<ul>
<li>Quick adoption thanks to a low entry barrier</li>
<li>Ability to mock network requests without a separate environment</li>
<li>Ability to develop ahead of time at a high level of completeness, with no dependency on the API</li>
<li>Can be used for debugging based on network state</li>
</ul>
