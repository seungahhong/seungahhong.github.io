f:Tad8a,<h2 id="background">Background<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#background"><span class="icon icon-link"></span></a></h2>
<h3 id="problems-with-the-npm-and-yarn-classic-10-package-managers">Problems with the NPM and Yarn Classic (1.0) Package Managers<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#problems-with-the-npm-and-yarn-classic-10-package-managers"><span class="icon icon-link"></span></a></h3>
<h4 id="phantom-dependencies">Phantom Dependencies<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#phantom-dependencies"><span class="icon icon-link"></span></a></h4>
<p><img src="/blog-assets/2024/03/assets/18/Untitled.png" alt="Untitled"></p>
<p><img src="/blog-assets/2024/03/assets/18/Untitled1.png" alt="Untitled"></p>
<ul>
<li>Both yarn classic (1.0) and npm (v3+) use hoisting and merging to flatten the dependency tree in order to efficiently manage the storage taken up by duplicate packages (surprisingly, up through npm v2 every dependency was installed redundantly).</li>
<li>To minimize duplicate packages internally, the packages that each package depends on are lifted to the top level.</li>
<li>The upshot is that a package you never installed gets lifted to the top level, which leads to the issue of being able to use a library you never explicitly added.</li>
</ul>
<h4 id="storage-issues">Storage Issues<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#storage-issues"><span class="icon icon-link"></span></a></h4>
<ul>
<li>With yarn 1.0 and npm, every library is installed into node_modules, so duplicate packages keep getting installed per package.</li>
</ul>
<h3 id="what-can-pnpm-solve">What Can PNPM Solve?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#what-can-pnpm-solve"><span class="icon icon-link"></span></a></h3>

<ul>
<li>
<p>Instead of hoisting packages, pnpm stores them globally in a global store (~/.pnpm-store).</p>

<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Library</span><span style="--shiki-light:#A0111F;--shiki-dark:#FF9492">/</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">pnpm</span><span style="--shiki-light:#A0111F;--shiki-dark:#FF9492">/</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">store</span><span style="--shiki-light:#A0111F;--shiki-dark:#FF9492">/</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">v3 </span><span style="--shiki-light:#66707B;--shiki-dark:#BDC4CC">// 글로벌 저장소 패스</span></span></code></pre></figure>
</li>
<li>
<p>The package paths installed in the global store (~/.pnpm-store) are connected to the virtual store (.pnpm) via hard links.</p>
<ul>
<li>node_modules/.pnpm/~~</li>
<li>A folder named with the package version (bar@1.0.0) is created, and links are set up under node_modules.</li>
<li>Because both the package folders and the symbolic link files are added, the storage taken up by node_modules can increase.</li>
</ul>

<p><img src="/blog-assets/2024/03/assets/18/Untitled4.png" alt="Untitled"></p>
</li>
<li>
<p>Because only the packages installed from package.json exist at the first depth of node_modules, phantom dependencies are eliminated.
Since packages are not hoisted, they are not installed at the first depth, so if you try to use a package you did not install while running the project, an error occurs.</p>
</li>
</ul>
<p>→ Because every package is bundled only with its related packages, access to unrelated packages can be blocked, and there is no need to perform complex operations like hoisting, which makes management easier.</p>
<h4 id="resolving-storage-issues">Resolving Storage Issues<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#resolving-storage-issues"><span class="icon icon-link"></span></a></h4>
<ul>
<li>By managing packages in one place in the global store (~/.pnpm-store) and composing node_modules through hard links / soft links, storage usage is reduced, and performance and build speed can also be improved.</li>
</ul>

<h4 id="msw-error">msw error<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#msw-error"><span class="icon icon-link"></span></a></h4>
<ul>
<li>An error occurs because the Module System differs (msw-storybook-addon, msw).
Cause: msw-storybook-addon, the package needed to integrate msw with storybook, is built in the CommonJS style, while headers-polyfill, which is a dependency pulled in when installing the msw package, is built in the ESM style, causing a Module Parsing error.</li>
<li>In particular, the msw package installs headers-polyfill (^3.~) using the caret (^) style, so the current latest version 3.2.5 gets installed, which means an ESM-style module is used and the error occurs.
Fix: Resolved by installing version 0.36.8, the most recent version that does not use headers-polyfill.
