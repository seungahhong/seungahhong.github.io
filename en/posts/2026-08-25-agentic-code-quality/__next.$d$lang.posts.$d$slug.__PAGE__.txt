17:T5c28,<h2 id="1-what-is-this-post-about">1. What Is This Post About?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#1-what-is-this-post-about"><span class="icon icon-link"></span></a></h2>
<p>Notes on Addy Osmani's <a href="https://addyosmani.com/blog/agentic-code-quality">Agentic Code Quality</a>. In one sentence:</p>
<blockquote>
<p><strong>Judging quality by reading code breaks down at agent scale.</strong> So the checks have to move out of the diff and into the <strong>harness, environment, and system surrounding the agent</strong>. In the author's words — <strong>"Software quality now depends on the constraints you set around your agents."</strong></p>
</blockquote>
<p>If the <a href="/en/posts/2026-08-23-ai-native-sdlc-playbook/">last post</a> asked "once code stops being the bottleneck, how do we rebuild the process?", this one zooms into a single cell of that answer: quality. Both share a premise — generation now outruns human capacity to consume it.</p>
<h3 id="the-premise-nobody-can-read-it-all">The Premise: Nobody Can Read It All<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#the-premise-nobody-can-read-it-all"><span class="icon icon-link"></span></a></h3>
<p>Until now, code quality was judged one way. <strong>Someone reads it.</strong> Is it clean, thoughtful, fast, understandable, well tested?</p>
<p>That works only when <strong>writing speed and reading speed are comparable</strong>. But agents can produce hundreds of thousands — even millions — of changes a day. There is no one left to read them.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">When humans wrote it:  1 written : 1 reviewed    → review acts as a gate</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">With agents:           1000 written : 1 reviewed → review becomes a queue</span></span></code></pre></figure>
<p>This is where a common misreading splits off. The conclusion isn't "give up on review." It's <strong>change who does the reading — from people to the system.</strong> The article puts it precisely:</p>
<blockquote>
<p><strong>"An agent can propose anything. Your constraints decide whether a proposal is safe enough."</strong></p>
</blockquote>
<hr>
<h2 id="2-there-are-cases-where-skipping-review-is-fine">2. There Are Cases Where Skipping Review Is Fine<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#2-there-are-cases-where-skipping-review-is-fine"><span class="icon icon-link"></span></a></h2>
<p>The article cites Guillermo Rauch's checklist for when you can afford not to read the code, and pulls out one observation: every "yes" on that list is really <strong>a statement about how low the stakes are</strong> — no users, throwaway code, a prototype.</p>
<p>In other words, "ship it unreviewed" is <strong>a judgment about risk, not about code</strong>. Which leads to the conclusion: once the stakes go up, something has to read the code — and if it isn't you on every diff, then <strong>the constraints have to read it</strong>.</p>
<p>That's the axis of the whole piece. The choice isn't "read / don't read" but <strong>"a human reads / the system reads."</strong> The nobody-reads option exists only while the stakes are low.</p>
<hr>
<h2 id="3-what-a-quality-gate-actually-is">3. What a Quality Gate Actually Is<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#3-what-a-quality-gate-actually-is"><span class="icon icon-link"></span></a></h2>
<p>It sounds abstract, but every example given is something you already use.</p>








































<table><thead><tr><th>Constraint</th><th>What it catches</th><th>Character</th></tr></thead><tbody><tr><td><strong>Unit, property, acceptance tests</strong></td><td>Does behavior match the spec</td><td>The familiar layer</td></tr><tr><td><strong>Mutation testing</strong></td><td>If mutating the code doesn't break a test → <strong>the test is weak</strong></td><td>Tests the tests</td></tr><tr><td><strong>Code metrics</strong></td><td>Cyclomatic complexity, line length, readability</td><td>The maintainability axis</td></tr><tr><td><strong>Types / compiler</strong></td><td>Makes the wrong state unrepresentable</td><td>The cheapest layer</td></tr><tr><td><strong>Security, perf, a11y scans</strong></td><td>What surfaces late</td><td>Distinct responsibilities</td></tr><tr><td><strong>Architecture rules (ESLint etc.)</strong></td><td>"This layer may not import that one"</td><td><strong>The layer you define yourself</strong></td></tr></tbody></table>
<p>Two things stand out.</p>
<p><strong>① Mutation testing gets named explicitly.</strong> There's a reason it matters again in the agent era. Tell an agent "make the tests pass" and it will make them pass. The question is <strong>what those tests were catching in the first place</strong> — and you can't know that without testing the tests. Coverage says "was this line executed"; mutation testing says <strong>"could this test have failed."</strong></p>
<p><strong>② Each check should carry a distinct responsibility.</strong> The advice is to keep a broad but <strong>deliberately chosen</strong> set of checks rather than leaning on unit tests alone. The emphasis is on <em>deliberately</em>, not on <em>broad</em>. Three tools that check the same thing three times are one constraint, not three.</p>
<hr>
<h2 id="4-two-missing-pieces--environment-and-trust">4. Two Missing Pieces — Environment, and Trust<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#4-two-missing-pieces--environment-and-trust"><span class="icon icon-link"></span></a></h2>
<p>Setting constraints isn't the whole job. The article flags two things the model leaves out.</p>
<h3 id="4-1-autonomy--agents-fail-for-the-same-reasons-people-do">4-1. Autonomy — Agents Fail for the Same Reasons People Do<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#4-1-autonomy--agents-fail-for-the-same-reasons-people-do"><span class="icon icon-link"></span></a></h3>
<p>Agents execute intent well but stumble when <strong>information is missing or the task is ambiguous</strong>. What's interesting is the list of causes: <strong>brittle environments</strong> that don't hold up under script-driven stress, <strong>nondeterministic builds</strong>, <strong>missing permissions</strong>, <strong>weak tests</strong>.</p>
<p>Those are all <strong>the same reasons humans fail to ship good code.</strong> Not new problems — old ones that were merely tolerable at human speed. An agent hitting them dozens of times a minute makes them intolerable.</p>
<p>Hence the environment being aimed for:</p>
<blockquote>
<p><strong>"An agent can do real work, get feedback it can trust, and fail without doing much damage."</strong></p>
</blockquote>
<p>Worth reading each condition separately.</p>





















<table><thead><tr><th>Condition</th><th>What happens without it</th></tr></thead><tbody><tr><td><strong>Can do real work</strong></td><td>Blocked permissions or tools → the agent routes around them or fakes the work</td></tr><tr><td><strong>Feedback it can trust</strong></td><td>Flaky tests and nondeterministic builds are noise. The agent edits code to match the noise</td></tr><tr><td><strong>Failure without damage</strong></td><td>If failure is expensive you must limit attempts — and then you can't grant autonomy</td></tr></tbody></table>
<p>The second is the most practical. <strong>A flaky test in an agent environment isn't an annoyance; it's a poisoned oracle.</strong> A human shrugs and says "oh, that one's always flaky." An agent believes the signal and rewrites working code.</p>
<h3 id="4-2-trust--extended-but-earned">4-2. Trust — Extended, but Earned<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#4-2-trust--extended-but-earned"><span class="icon icon-link"></span></a></h3>
<blockquote>
<p><strong>"We start with trust, but it has to be hard-earned."</strong></p>
</blockquote>
<p>Instead of the all-or-nothing permission binary, autonomy grows with <strong>track record and the quality of the evidence</strong>. It's the same idea as the 1σ/2σ/3σ authority split from <a href="/en/posts/2026-08-23-ai-native-sdlc-playbook/">the last post</a>. The question shifts from "should the agent have permission" to <strong>"when, and how much."</strong></p>
<hr>
<h2 id="5-constraints-play-different-roles-at-different-moments">5. Constraints Play Different Roles at Different Moments<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#5-constraints-play-different-roles-at-different-moments"><span class="icon icon-link"></span></a></h2>
<p>The article splits constraints into three moments: some shape the work <strong>before it begins</strong>, some give feedback <strong>while the agent works</strong>, and some decide whether the output <strong>can cross the production boundary at all</strong>.</p>
<p>Even "a test" changes character entirely depending on where you put it.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Before   types, schemas, architecture rules, CLAUDE.md  → prevent it up front</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">During   tests, lint, build, hooks                      → say "wrong way" early</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Boundary CI, security scans, approval gates             → stop it from leaving</span></span></code></pre></figure>
<p>And this <strong>back-pressure</strong> should live throughout the loop rather than existing as a single review after all the work is done — a point the article keeps returning to.</p>
<p>Block only at the end, and here's what happens: the agent is rejected after building the whole thing. What's wasted isn't just tokens — it's <strong>all the context stacked on top of a wrong premise</strong>.</p>
<hr>
<h2 id="6-when-verification-runs-out-of-room--only-three-options">6. When Verification Runs Out of Room — Only Three Options<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#6-when-verification-runs-out-of-room--only-three-options"><span class="icon icon-link"></span></a></h2>
<p>The most operationally useful part. What if changes are generated faster than the tooling can consume them?</p>
<p><strong>You build a queue.</strong> And that queue moves at human speed. Every gain from automation evaporates right there.</p>
<p>The three options offered:</p>

























<table><thead><tr><th>Option</th><th>What it does</th><th>The cost</th></tr></thead><tbody><tr><td><strong>① Scale verification</strong></td><td>More checking capacity and parallelism</td><td>Infrastructure</td></tr><tr><td><strong>② Slow generation</strong></td><td>Reduce the rate agents produce changes</td><td>Give up speed</td></tr><tr><td><strong>③ Lower the bar</strong></td><td>Let constraints push back less</td><td>Accept risk</td></tr></tbody></table>
<p>And then: <strong>from a scaling perspective, be ready to do all three.</strong> It isn't a pick-one problem.</p>
<p>It goes one step further — in some directions, <strong>un-constraining gets more done.</strong> Rather than tightening everything uniformly, <strong>clamp down hardest where you care most and loosen elsewhere</strong>, and you maximize throughput without sacrificing quality.</p>
<p>Which ultimately means deciding where you want to sit on the spectrum from <strong>innovation-focused to quality-focused</strong>.</p>
<p>Treat constraints as strictly-more-is-better and that dial becomes unusable. You have to admit constraints have a cost before you can decide which to relax.</p>
<hr>
<h2 id="7-where-to-spend-human-attention">7. Where to Spend Human Attention<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#7-where-to-spend-human-attention"><span class="icon icon-link"></span></a></h2>
<blockquote>
<p><strong>"If you put a human check into a system that otherwise moves at machine speed, don't be surprised if that impacts productivity."</strong></p>
</blockquote>
<p>Painfully accurate. Human attention is <strong>scarce and expensive</strong>, so it can't be dropped anywhere — it has to be <strong>directed deliberately</strong>.</p>
<p>Two placement principles:</p>
<ul>
<li>Humans attach to <strong>the nuanced problems that need judgment</strong> — taste, intent, architecture</li>
<li>Downstream humans are pulled in <strong>only when the automated guardrails break</strong></li>
</ul>
<p>Which leads to:</p>
<blockquote>
<p><strong>"Human 'code review' in the future is going to look very different."</strong></p>
</blockquote>
<p>Same direction as the last post. Review doesn't disappear — <strong>its altitude rises.</strong></p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Better asked of a machine: Is there a bug in this diff? Does it violate a security rule? Is the style right?</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Only a human can answer:   Should this have been built at all? Will this abstraction still hold in six months?</span></span></code></pre></figure>
<hr>
<h2 id="8-quality-isnt-a-single-metric">8. Quality Isn't a Single Metric<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#8-quality-isnt-a-single-metric"><span class="icon icon-link"></span></a></h2>
<p>The last axis. Correctness is <strong>one dimension</strong> of quality, not the whole of it.</p>
<blockquote>
<p>Software quality isn't a single metric. Think of it as a collection of signals of varying importance to you and your team.</p>
</blockquote>

































<table><thead><tr><th>Dimension</th><th>Example constraints</th></tr></thead><tbody><tr><td><strong>Correctness</strong></td><td>Unit / property / acceptance tests, mutation testing</td></tr><tr><td><strong>Maintainability</strong></td><td>Complexity metrics, architecture rules, review</td></tr><tr><td><strong>Performance</strong></td><td>Benchmarks, bundle budgets, Lighthouse</td></tr><tr><td><strong>Security</strong></td><td>Scanners, policies, dependency audits</td></tr><tr><td><strong>Efficiency</strong></td><td>Resource and cost measurement</td></tr><tr><td><strong>Comprehensibility</strong></td><td>Docs, naming, structure — <strong>the weakest cell for automation</strong></td></tr></tbody></table>
<p>And something matters more than the count: not <strong>how many</strong> constraints you have, but whether they're <strong>demanding enough to meet your bar</strong>.</p>
<p>If twelve green check badges all pass and production still burns, you don't lack constraints — <strong>your constraints are soft</strong>.</p>
<hr>
<h2 id="9-applying-it-to-this-repo">9. Applying It to This Repo<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#9-applying-it-to-this-repo"><span class="icon icon-link"></span></a></h2>
<p>Reading without applying leaves nothing behind, so here are this blog repo's constraints sorted into the dimensions from section 8.</p>








































<table><thead><tr><th>Dimension</th><th>Constraints in place</th><th>Gaps</th></tr></thead><tbody><tr><td><strong>Correctness</strong></td><td>Vitest unit tests, Playwright E2E, 3-stage pre-commit</td><td>No mutation testing — <strong>no idea how demanding the tests are</strong></td></tr><tr><td><strong>Maintainability</strong></td><td>ESLint, TypeScript strict</td><td>No architecture rules (import boundaries)</td></tr><tr><td><strong>Performance</strong></td><td>—</td><td>No bundle budget or Lighthouse gate</td></tr><tr><td><strong>Security</strong></td><td>—</td><td>Personal static blog, small surface</td></tr><tr><td><strong>Accessibility</strong></td><td>axe checks, 0 violations across 5 pages</td><td>Dark mode unverified (<a href="/en/posts/2026-08-23-ai-native-sdlc-playbook/">carried-over TODO</a>)</td></tr><tr><td><strong>Comprehensibility</strong></td><td><code>CLAUDE.md</code>, content conventions</td><td>—</td></tr></tbody></table>
<p>And there's a real case here of <strong>a constraint catching a human</strong>. Adding a post breaks three tests with hardcoded post counts. It looked like busywork at first, but through section 6's lens it's <strong>feedback during the work</strong>. Add the Korean original and forget the <code>.en.md</code>, and <code>content-conventions.test.ts</code> fails immediately. That isn't the kind of mistake review catches.</p>
<p>The bigger gap, though, sits upstream of mutation testing. Same conclusion as the last post: nothing verifies whether editing <code>CLAUDE.md</code> or a harness skill made agent behavior <em>worse</em>. The table in section 8 is effectively <strong>missing a row for "agent configuration."</strong> Application code is checked along six dimensions; the configuration that produces that code is checked along none.</p>
<hr>
<h2 id="10-easy-things-to-get-wrong">10. Easy Things to Get Wrong<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#10-easy-things-to-get-wrong"><span class="icon icon-link"></span></a></h2>
<h3 id="misreading-1--more-constraints-means-more-quality">Misreading 1 — "More constraints means more quality"<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#misreading-1--more-constraints-means-more-quality"><span class="icon icon-link"></span></a></h3>
<p>The article explicitly disagrees. Apply strong constraints where they serve <strong>both quality and throughput</strong>, and <strong>remove or relax the ones serving neither</strong>.</p>
<p>A usable test:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Has this check caught a real problem lately?        ← if not, it isn't serving quality</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Would a human have to do this work without it?      ← if not, it isn't serving throughput</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">→ Both no? Delete it.</span></span></code></pre></figure>
<p>A check that only ever passes isn't a safety net — it's <strong>overhead</strong>.</p>
<h3 id="misreading-2--constraints-belong-in-ci">Misreading 2 — "Constraints belong in CI"<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#misreading-2--constraints-belong-in-ci"><span class="icon icon-link"></span></a></h3>
<p>CI is <strong>the constraint at the boundary</strong>. The argument runs the other way: use the signal <strong>as early as possible, through every available path</strong>. CI telling you at the end that you may not deploy is already late feedback.</p>
<p>Why that matters more for agents: <strong>an agent can restart from the point where it got the feedback.</strong> A mistake caught inside a five-minute loop and one caught by CI after the PR is opened have very different recovery costs.</p>
<h3 id="misreading-3--you-dont-have-to-read-code-anymore">Misreading 3 — "You don't have to read code anymore"<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#misreading-3--you-dont-have-to-read-code-anymore"><span class="icon icon-link"></span></a></h3>
<p>The author draws that line himself in the first paragraph: he still reads and reviews code, and is very intentional about <strong>where he's comfortable letting constraints be the check</strong>.</p>
<p>You don't stop reading — <strong>you choose where to read.</strong> That choice is exactly the risk judgment from section 2.</p>
<hr>
<h2 id="11-wrapping-up">11. Wrapping Up<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#11-wrapping-up"><span class="icon icon-link"></span></a></h2>






























<table><thead><tr><th></th><th>The point</th><th>Why</th></tr></thead><tbody><tr><td><strong>1. The reader changes</strong></td><td>Constraints read every diff instead of you</td><td>Nobody reading is only safe when stakes are low</td></tr><tr><td><strong>2. The environment is the quality</strong></td><td>Trustworthy feedback + damage-free failure</td><td>A flaky test is a poisoned oracle for an agent</td></tr><tr><td><strong>3. Constraints cost something</strong></td><td>Serve neither goal? Delete it</td><td>Not <em>many</em> constraints — <strong>demanding, chosen</strong> ones</td></tr><tr><td><strong>4. Humans move up</strong></td><td>Taste, intent, architecture</td><td>A human check inside a machine-speed loop is the new bottleneck</td></tr></tbody></table>
<p>And this is another axis of the same story the earlier posts have been telling.</p>
<ul>
<li><a href="/en/posts/2026-07-05-meta-harness/">Self-healing harness</a> — verify when you <strong>add</strong> a rule</li>
<li><a href="/en/posts/2026-07-31-context-engineering-claude5/">Context engineering by subtraction</a> — verify when you <strong>remove</strong> one</li>
<li><a href="/en/posts/2026-08-22-delete-and-verify/">Delete, make it earn access, make it verify</a> — verify when you <strong>hand an agent work</strong></li>
<li><a href="/en/posts/2026-08-23-ai-native-sdlc-playbook/">The AI-native SDLC</a> — verify when you <strong>change the process</strong></li>
<li>This post — <strong>what you build those verifications out of.</strong> That's constraints</li>
</ul>
<p>The article closes by handing the reader homework: quality lives in the constraints you set around your agents, so take the problem statement and build your own constraint-driven plan.</p>
<p>At a scale where nobody can read it all, the only way to keep the bar is to <strong>build the system that makes reading unnecessary first</strong>.</p>
