17:T7de5,<h2 id="1-what-is-this-post-about">1. What Is This Post About?<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#1-what-is-this-post-about"><span class="icon icon-link"></span></a></h2>
<p>Notes on Addy Osmani's <a href="https://addyo.substack.com/p/how-to-write-a-good-spec-for-ai-agents">How to write a good spec for AI agents</a>.</p>
<p>The piece opens with a question the author received:</p>
<blockquote>
<p>"I've heard a lot about writing good specs for AI agents, but <strong>haven't found a solid framework yet.</strong>"</p>
</blockquote>
<p>That question is exactly right. Advice to "write a good spec" is everywhere; material that tells you <strong>what to write and how much</strong> is rare. And the answer here runs against intuition.</p>
<blockquote>
<p><strong>Don't write a big spec.</strong> Context window limits and the model's <strong>attention budget</strong> get in the way.</p>
</blockquote>
<p>If the <a href="/en/posts/2026-07-31-context-engineering-claude5/">context engineering post</a> was about <strong>removing rules</strong>, this one sits right next to it: <strong>what's left, and what shape should it take.</strong> Removal is subtraction; spec-writing is <strong>choosing what survives.</strong></p>
<hr>
<h2 id="2-vision-first-details-from-the-agent">2. Vision First, Details From the Agent<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#2-vision-first-details-from-the-agent"><span class="icon icon-link"></span></a></h2>
<p>The first principle is about order: <strong>don't write the full detailed spec yourself before starting.</strong></p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">❌ Human writes 50-page spec → feed it to the agent</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">✅ Human writes short product brief → agent drafts detailed spec → human corrects → execute</span></span></code></pre></figure>
<p>The reasoning is practical. <strong>Elaboration is what models are good at</strong>; <strong>direction is what only humans can set.</strong> Mix the two and do both yourself, and you spend time on what you're worse at while the model never uses what it's best at.</p>
<p>The example brief in the article is this short:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">"Build a to-do app with user accounts and persistent storage."</span></span></code></pre></figure>
<p>The agent expands that into schema, routing, error cases, and a test strategy — and the human <strong>reads it and fixes only what's wrong.</strong> Faster than a blank page, and more importantly, <strong>the gaps become visible.</strong></p>
<h3 id="why-plan-mode-belongs-here">Why Plan Mode Belongs Here<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#why-plan-mode-belongs-here"><span class="icon icon-link"></span></a></h3>
<p>The article recommends <strong>Plan Mode (read-only)</strong> for this stage — refining the spec while the agent cannot touch files.</p>
<p>This matters because <strong>once spec correction and code writing are mixed, code appears before correction finishes.</strong> The moment code exists, the cost of changing the spec jumps. Read-only pins that cost at zero.</p>
<p>And the refined result gets <strong>saved</strong> — as something like <code>SPEC.md</code>. Why it has to be a file rather than a conversation comes back in sections 3 and 6.</p>
<hr>
<h2 id="3-what-2500-agent-config-files-say--six-areas">3. What 2,500 Agent Config Files Say — Six Areas<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#3-what-2500-agent-config-files-say--six-areas"><span class="icon icon-link"></span></a></h2>
<p>The most concrete part of the article. GitHub analyzed <strong>over 2,500 agent configuration files</strong>, and six areas showed up consistently in the good ones.</p>








































<table><thead><tr><th>Area</th><th>What belongs there</th><th>Common failure</th></tr></thead><tbody><tr><td><strong>Commands</strong></td><td><strong>Full executable commands</strong> including flags (<code>pnpm test</code>, <code>pytest -v</code>)</td><td>Written as "run the tests"</td></tr><tr><td><strong>Testing</strong></td><td>Framework · test locations · coverage expectations</td><td>The runner is never named</td></tr><tr><td><strong>Project structure</strong></td><td>Where source, tests, and docs each live</td><td>The agent creates files in the wrong place</td></tr><tr><td><strong>Code style</strong></td><td>Conventions shown as <strong>real code examples</strong></td><td>Written as adjectives only ("keep it clean")</td></tr><tr><td><strong>Git workflow</strong></td><td>Branch naming · commit format · PR requirements</td><td>A human fixes it every time</td></tr><tr><td><strong>Boundaries</strong></td><td>Hard constraints · <strong>what must never be touched</strong></td><td>Missing entirely</td></tr></tbody></table>
<p>Of the six, the one most often empty in practice is <strong>boundaries.</strong> The other five are descriptive, so they fill in as you write. Boundaries are the entries <strong>you only think of after an incident.</strong></p>
<p>One line from the article sums it up:</p>
<blockquote>
<p><strong>"Never commit secrets"</strong> was the single most common — and most helpful — constraint.</p>
</blockquote>

<p>What to notice is <strong>the shape, not the length.</strong> Every entry is <strong>one fact per line</strong>, and it's a <strong>command, a path, or a name</strong> — not an adjective. That's the only shape a model can actually comply with.</p>
<hr>
<h2 id="4-the-curse-of-instructions--bigger-specs-get-followed-less">4. The Curse of Instructions — Bigger Specs Get Followed Less<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#4-the-curse-of-instructions--bigger-specs-get-followed-less"><span class="icon icon-link"></span></a></h2>
<p>This is the theoretical spine of the article: the phenomenon research calls <strong>"the curse of instructions."</strong></p>
<blockquote>
<p>As instructions and data in a prompt increase, <strong>the rate at which each individual requirement is satisfied drops noticeably.</strong> Even GPT-4 and Claude struggle to satisfy many requirements simultaneously.</p>
</blockquote>
<p>This is the line that stayed with me longest. Our motive for growing a spec is usually <strong>"I can't afford to leave this out"</strong> — and the document that motive produces <strong>degrades the entries already in it.</strong></p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Intuition: write 20 rules and 20 rules get followed</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Reality:   write 20 rules and per-rule compliance falls below a 5-rule document</span></span></code></pre></figure>
<p>So writing a spec is <strong>budget allocation, not addition.</strong> Adding a rule isn't free — you <strong>buy it by shaving a little compliance probability off every existing rule.</strong> This meets <a href="/en/posts/2026-07-31-context-engineering-claude5/">context engineering by subtraction</a> at exactly the same point.</p>
<h3 id="four-ways-to-split">Four Ways to Split<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#four-ways-to-split"><span class="icon icon-link"></span></a></h3>
<p>Every remedy in the article is a form of dividing.</p>

























<table><thead><tr><th>Method</th><th>What it means</th></tr></thead><tbody><tr><td><strong>Split by component</strong></td><td>Separate backend and frontend specs; feed <strong>only what's contextually relevant</strong></td></tr><tr><td><strong>Extended TOC with summaries</strong></td><td>A condensed outline referencing detailed sections, <strong>expanded only when needed</strong></td></tr><tr><td><strong>Sub-agents / skills</strong></td><td>Domain-specialized agents carry <strong>only their portion</strong> of the spec</td></tr><tr><td><strong>Sequential focus</strong></td><td>One task per prompt, refreshing context in between</td></tr></tbody></table>
<p>The third connects to the <a href="/en/posts/2026-09-06-skills-governance/">skills governance post</a>. There, sub-agents were characterized as <strong>"mostly existing to protect the context window"</strong> — and this article supplies <strong>the reason that defense matters.</strong> Protecting context isn't a capacity problem; it's a <strong>compliance</strong> problem.</p>
<h3 id="the-caveat-on-parallel-agents">The Caveat on Parallel Agents<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#the-caveat-on-parallel-agents"><span class="icon icon-link"></span></a></h3>
<p>The article also mentions running agents concurrently for independent features — <strong>"one codes, one tests, one reviews."</strong> But with conditions: <strong>start with 2–3</strong>, keep task separation clear, and use orchestration to coordinate shared context.</p>
<p>I'd argue the caveat matters more than the headline. Parallel agents are <strong>a device for splitting context and a device for creating conflicts at the same time.</strong> Scale them up with fuzzy task boundaries and you dodge the curse of instructions by buying <strong>merge conflicts and agents overwriting each other.</strong></p>
<hr>
<h2 id="5-three-tier-boundaries----️--">5. Three-Tier Boundaries — ✅ / ⚠️ / 🚫<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#5-three-tier-boundaries----️--"><span class="icon icon-link"></span></a></h2>
<p>The concrete shape of the area section 3 called most often empty.</p>

























<table><thead><tr><th>Tier</th><th>Meaning</th><th>Example</th></tr></thead><tbody><tr><td><strong>✅ Always</strong></td><td>Do it without asking</td><td>"Always run tests before commits"</td></tr><tr><td><strong>⚠️ Ask first</strong></td><td>Expensive to undo</td><td>"Ask before modifying database schemas"</td></tr><tr><td><strong>🚫 Never</strong></td><td>Hard stop, no exceptions</td><td>"Never commit secrets"</td></tr></tbody></table>
<p>The split into three is the point. Write boundaries as <strong>a single prohibition list</strong> and two things break at once.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Prohibitions only: everything ambiguous drifts into "not prohibited" and just runs</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Prohibitions only: or you put everything in to be safe, and the agent can't act at all</span></span></code></pre></figure>
<p><strong>The ⚠️ tier is the valve that hands a decision back to a human.</strong> Without it every judgment becomes binary — and the decisions that matter in real development are mostly gray, so a valveless spec always fails toward one extreme or the other.</p>
<h3 id="embedding-self-checks-in-the-spec">Embedding Self-Checks in the Spec<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#embedding-self-checks-in-the-spec"><span class="icon icon-link"></span></a></h3>
<p>Beyond boundaries, the article suggests three more:</p>
<ul>
<li><strong>Verify against the spec</strong> — after writing code, have the agent <strong>check its own output against the spec's requirements</strong></li>
<li><strong>LLM-as-a-Judge</strong> — a judging model for items that need subjective evaluation</li>
<li><strong>Conformance tests</strong> — tests <strong>derived directly from the spec</strong></li>
</ul>
<p>The third carries the most value. When a spec sentence becomes a test, the spec shifts from <strong>a document you hope gets read</strong> to <strong>a device that turns red when it isn't followed.</strong> That's exactly the shape described in <a href="/en/posts/2026-08-25-agentic-code-quality/">code quality lives in the constraints</a>.</p>
<hr>
<h2 id="6-the-spec-is-a-living-artifact">6. The Spec Is a Living Artifact<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#6-the-spec-is-a-living-artifact"><span class="icon icon-link"></span></a></h2>
<p>The final principle: not a write-once document.</p>
<blockquote>
<p>Specs become the <strong>shared source of truth</strong> — <strong>living, executable artifacts that evolve with the project.</strong></p>
</blockquote>





























<table><thead><tr><th>Practice</th><th>What it means</th></tr></thead><tbody><tr><td><strong>Test at every milestone</strong></td><td>Catch spec/implementation drift <strong>early</strong></td></tr><tr><td><strong>Update the spec</strong></td><td>When you find a missing requirement, <strong>fix the document</strong> (don't patch it in chat)</td></tr><tr><td><strong>Version the spec</strong></td><td>Put the spec itself under source control</td></tr><tr><td><strong>Log agent actions</strong></td><td>Trace back how instructions were misread</td></tr><tr><td><strong>Context management tooling</strong></td><td>For large specs, pull <strong>only the relevant sections</strong> via RAG, MCP, vector DBs</td></tr></tbody></table>
<p>The last item is the same remedy as section 4. If you can't stop a spec from growing, at least stop <strong>all of it from entering at once.</strong></p>
<h3 id="model-selection-and-cost">Model Selection and Cost<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#model-selection-and-cost"><span class="icon icon-link"></span></a></h3>
<p>One practical note: <strong>capable models for planning and critical steps, cheaper ones for routine expansion</strong> — and throttle context sizes appropriately.</p>
<blockquote>
<p><strong>More tokens don't guarantee better outcomes. Context quality matters more than length.</strong></p>
</blockquote>
<p>The same conclusion as <a href="/en/posts/2026-08-01-choosing-claude-model/">choosing a Claude model</a>. Each stage needs something different, and using the top model everywhere is <strong>laziness paid for in tokens.</strong></p>
<hr>
<h2 id="7-anti-patterns-the-github-study-found">7. Anti-Patterns the GitHub Study Found<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#7-anti-patterns-the-github-study-found"><span class="icon icon-link"></span></a></h2>

































<table><thead><tr><th>Anti-pattern</th><th>Why it fails</th></tr></thead><tbody><tr><td><strong>Vague prompts</strong></td><td>"Build something cool" gives <strong>nothing to anchor to</strong></td></tr><tr><td><strong>Overlong context without summarization</strong></td><td>Dumping 50 pages fails (section 4)</td></tr><tr><td><strong>Skipping human review</strong></td><td><strong>Passing tests ≠ correct</strong></td></tr><tr><td><strong>Conflating prototyping with production</strong></td><td>The spec has to say <strong>where rigor applies</strong></td></tr><tr><td><strong>Missing some of the six areas</strong></td><td>An empty area becomes a gap</td></tr><tr><td><strong>Ignoring speed, non-determinism, cost</strong></td><td><strong>Verification has to keep pace with agent velocity</strong></td></tr></tbody></table>
<p>The fourth shows up constantly. A single repo holds both <strong>throwaway prototypes</strong> and <strong>code that will live a year</strong> — and if the spec doesn't make that distinction, the agent treats both identically. Both outcomes are bad: the prototype gets over-built, and production code gets prototype treatment.</p>
<p>The last one is worth a second pass too. Agents produce code faster than humans do, while review speed stays fixed. As that gap widens you accumulate <strong>an inventory of unreviewed code</strong> — which isn't speed, it's <strong>accruing debt faster.</strong></p>
<hr>
<h2 id="8-applied-to-this-repo--four-of-six-areas-are-empty">8. Applied to This Repo — Four of Six Areas Are Empty<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#8-applied-to-this-repo--four-of-six-areas-are-empty"><span class="icon icon-link"></span></a></h2>
<p>Reading without applying leaves nothing behind, so I measured this blog's <code>CLAUDE.md</code> against the six areas from section 3.</p>








































<table><thead><tr><th>Area</th><th>Current state</th><th>Verdict</th></tr></thead><tbody><tr><td><strong>Commands</strong></td><td>Delegates to "see <code>package.json</code> scripts" + spells out only <code>pnpm fetch:popular</code></td><td>⚠️</td></tr><tr><td><strong>Testing</strong></td><td>Absent — no mention of vitest vs. playwright, or where tests live</td><td>❌</td></tr><tr><td><strong>Project structure</strong></td><td>The <code>contents/blog/YYYY/MM/*.md</code> convention exists. The <code>src/</code> layout doesn't</td><td>⚠️</td></tr><tr><td><strong>Code style</strong></td><td>Absent</td><td>❌</td></tr><tr><td><strong>Git workflow</strong></td><td>The deploy path (<code>develop</code> → <code>master</code> → <code>gh-pages</code>) is detailed</td><td>✅</td></tr><tr><td><strong>Boundaries</strong></td><td>Absent — no ✅/⚠️/🚫 distinction anywhere</td><td>❌</td></tr></tbody></table>
<p>What made this interesting is that <strong>the empty areas overlap with the areas where things have actually gone wrong.</strong></p>
<p>Adding a single post to this repo breaks <strong>four hardcoded test expectations</strong> (post count, category count, latest post date, the count rendered on the About page). <code>CLAUDE.md</code> says nothing about any of it. <strong>The testing area is empty, so the lesson arrives as a red build every time.</strong></p>
<p>Boundaries are the same. This repo already has obvious 🚫 and ⚠️ entries.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">🚫 Don't run </span><span style="--shiki-light:#023B95;--shiki-dark:#91CBFF">`pnpm format`</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6"> over existing posts — it rewrites every table's alignment</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">🚫 Don't commit </span><span style="--shiki-light:#023B95;--shiki-dark:#91CBFF">`public/blog-assets/`</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6"> — it's a gitignored derived artifact</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">⚠️ Running </span><span style="--shiki-light:#023B95;--shiki-dark:#91CBFF">`pnpm fetch:popular`</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6"> on </span><span style="--shiki-light:#023B95;--shiki-dark:#91CBFF">`develop`</span><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6"> and committing it can conflict at merge time</span></span></code></pre></figure>
<p>The third one <em>is</em> in <code>CLAUDE.md</code> — as prose, <strong>not marked ⚠️.</strong> A warning buried in a paragraph and a line tagged <code>⚠️</code> are <strong>not the same information.</strong> The first hopes to be read; the second has been <strong>classified.</strong></p>
<p>So the actual work here narrows to:</p>
<ol>
<li><strong>Add a boundaries section and move the 🚫/⚠️ we already know into it</strong> — this isn't discovery, it's <strong>classifying what's already scattered through prose</strong></li>
<li><strong>Fill the testing area</strong> — runner, locations, and "the four places to update when adding a post"</li>
<li><strong>Don't grow it</strong> — given section 4, leave code style empty until an incident actually costs something</li>
</ol>
<p>Writing down #3 matters. Seeing six areas makes you <strong>want to fill all six</strong> — and that's precisely the direction this article warns against. An empty area isn't a defect; it may just be an area <strong>that hasn't cost anything yet.</strong></p>
<hr>
<h2 id="9-easy-things-to-misread">9. Easy Things to Misread<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#9-easy-things-to-misread"><span class="icon icon-link"></span></a></h2>
<h3 id="misreading-1--writing-specs-means-going-back-to-waterfall">Misreading 1 — "Writing specs means going back to waterfall"<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#misreading-1--writing-specs-means-going-back-to-waterfall"><span class="icon icon-link"></span></a></h3>
<p>The claim is the opposite. A spec isn't <strong>fixed and frozen once</strong>; it's the <strong>living artifact</strong> of section 6. And the draft is written by the agent, not the human (section 2). Waterfall's essence is "finalize a phase and move on" — here you <strong>return to the spec at every milestone.</strong></p>
<p>If anything this is closer to <strong>treat the spec like code</strong>: versioned, tested, changed through commits.</p>
<h3 id="misreading-2--longer-context-models-will-solve-this">Misreading 2 — "Longer-context models will solve this"<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#misreading-2--longer-context-models-will-solve-this"><span class="icon icon-link"></span></a></h3>
<p>Section 4 is the answer to that hope. The curse of instructions is <strong>an attention problem, not a capacity problem.</strong> Widen the window and <strong>satisfying 20 simultaneous instructions</strong> remains exactly as hard.</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast"><code data-language="markdown" data-theme="github-light-high-contrast github-dark-high-contrast" style="display: grid;"><span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Context window: how much fits         → solved by hardware/models</span></span>
<span data-line=""><span style="--shiki-light:#0E1116;--shiki-dark:#F0F3F6">Attention budget: how much is obeyed  → solved by whoever writes it</span></span></code></pre></figure>
<h3 id="misreading-3--filling-all-six-areas-makes-a-good-spec">Misreading 3 — "Filling all six areas makes a good spec"<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#misreading-3--filling-all-six-areas-makes-a-good-spec"><span class="icon icon-link"></span></a></h3>
<p>This is where section 8 caught me. The six areas are <strong>a diagnostic, not a checklist.</strong> Filling an area by guesswork, where nothing has ever gone wrong, produces exactly the <strong>compliance-shaving instructions</strong> section 4 describes. When an area is empty, ask <strong>why</strong> first — nothing has gone wrong, or something went wrong and nobody wrote it down?</p>
<h3 id="misreading-4--with-self-checks-in-place-we-can-cut-human-review">Misreading 4 — "With self-checks in place we can cut human review"<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#misreading-4--with-self-checks-in-place-we-can-cut-human-review"><span class="icon icon-link"></span></a></h3>
<p>The anti-pattern list settles this: <strong>passing tests is not correctness.</strong> And every self-check in section 5 is <strong>the agent measuring its own work against its own spec</strong>, which means <strong>they all pass when the spec itself is wrong.</strong> Whether the spec is wrong cannot be determined from inside the spec — that seat belongs to a human.</p>
<hr>
<h2 id="10-summary">10. Summary<a class="heading-anchor" aria-hidden="true" tabindex="-1" href="#10-summary"><span class="icon icon-link"></span></a></h2>













































<table><thead><tr><th></th><th>Point</th><th>Why</th></tr></thead><tbody><tr><td><strong>1. Vision from humans, detail from agents</strong></td><td>Short brief → agent draft → human correction</td><td>Only humans set direction; models elaborate better</td></tr><tr><td><strong>2. Diagnose with the six areas</strong></td><td>Commands · Testing · Structure · Style · Git · <strong>Boundaries</strong></td><td>The axes common to 2,500 files</td></tr><tr><td><strong>3. Boundaries in three tiers</strong></td><td>✅ Always / ⚠️ Ask first / 🚫 Never</td><td>Without ⚠️, every judgment turns binary</td></tr><tr><td><strong>4. More instructions, less compliance</strong></td><td>The curse of instructions</td><td>New rules are bought by shaving existing ones</td></tr><tr><td><strong>5. So you split</strong></td><td>By component · TOC · sub-agents · sequential</td><td>Splitting context is a compliance device, not a capacity one</td></tr><tr><td><strong>6. Turn spec sentences into tests</strong></td><td>Conformance tests · verify-against-spec</td><td>From a document you hope gets read to one that turns red</td></tr><tr><td><strong>7. Verification must keep pace</strong></td><td>Passing tests ≠ correct</td><td>Otherwise you stockpile unreviewed code</td></tr></tbody></table>
<p>Overlaid on the thread this blog has been following, the position is clear:</p>
<ul>
<li><a href="/en/posts/2026-07-12-product-spec-harness/">Product spec harness</a> — the <strong>procedure for producing</strong> a spec, as a harness</li>
<li><a href="/en/posts/2026-07-31-context-engineering-claude5/">Context engineering</a> — verify when you <strong>remove</strong> rules</li>
<li><a href="/en/posts/2026-08-01-choosing-claude-model/">Choosing a Claude model</a> — <strong>each stage needs a different model</strong></li>
<li><a href="/en/posts/2026-08-25-agentic-code-quality/">Code quality lives in the constraints</a> — verify by what <strong>surrounds</strong> the agent</li>
<li><a href="/en/posts/2026-09-06-skills-governance/">Skills governance</a> — what those rules need once they <strong>pass through many hands</strong></li>
<li>This post — <strong>what shape, and how much</strong> to write them in</li>
</ul>
<p>Back to the original question: the "solid framework" turns out to be <strong>six areas, three tiers of boundaries, and the discipline not to grow it.</strong> The first two are lists you can apply today. The third is the hard one — a spec is a document that always wants to get longer, and <strong>the moment it does, the entries already in it start going unfollowed.</strong></p>
